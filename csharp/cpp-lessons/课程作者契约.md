# C++ 课程作者契约

这份文档是给**并行写课的作者**看的。照着做，你和别人产出的课程才能拼到一起。

## 你要交付什么

一个文件：`csharp/cpp-lessons/Lessons/第NN课_主题.cs`

**只碰这一个文件。** 不要改任何其它文件（别的作者正在同时写别的课）。

## 照抄这个骨架

```csharp
// 第 NN 课：<主题> —— <一句话说明这一课要教什么>
//
// ══ 这一课要教什么 ══
// <两三句。说清"为什么需要这个知识"，而不是复述语法>
//
// ══ 检查设计说明（给维护者）══
// <这一课的"核心检查点"是哪一条？学生能用什么偷懒办法蒙过去？那条检查怎么防住的？>

using System.Linq;
using LearnCode;
using LearnCode.CppLessons;

[课程("NN", "第 NN 课：<标题>",
    "1. <要求一>\n" +
    "2. <要求二>\n" +
    "3. <要求三>")]
public static class 第NN课
{
    public static string 模板 => """
// 第 NN 课：<标题>
//
// 要做：
//   ...（和上面「要做」一致）
//
// 写完后运行：dotnet run --project csharp/cpp-lessons 检查 NN

// ── 在下面写你的代码 ──
""";

    public static string 参考答案 => """
// 参考答案 —— 必须是**真的能通过所有检查**的代码
""";

    [检查说明("<一句给学生看的话，说明这条检查查什么>")]
    public static CheckResult 检查_xxxx(string 代码)
    {
        // ...
    }
}
```

## 硬性规则

1. **文件第一行必须是** `// 第 NN 课：...`，用来生成答题文件的初始内容。
2. **必须**有 `[课程(...)]` 特性，否则运行器发现不了你这一课。
3. **检查方法名必须以 `检查_` 开头**，签名固定是
   `public static CheckResult 检查_xxx(string 代码)` —— 运行器靠反射收集。
4. **每条检查都要加 `[检查说明("...")]`** —— 那是给学生看的，函数名不是。
5. **检查至少要有一条"核心检查点"** —— 防住"能输出对但没学到东西"的偷懒解法。
6. **`参考答案` 必须真的能通过你写的所有检查**（自己跑一遍验证，见下）。

## 可用的工具（都在 `CppCheck` 里）

```csharp
// 学生写「一个函数」的课用这个（会自动包上 #include 和 main）
var run = CppCheck.编译并运行(学生代码);
var run = CppCheck.编译并运行(学生代码, 骨架, 调用点);

// 学生写「完整程序」（自带 main）的课用这个
var run = CppCheck.直接运行(学生代码);

// 现成的检查（返回 CheckResult）
CppCheck.逐个用例(学生代码, new CppCheck.用例("说明","调用表达式","期望输出"), ...)
CppCheck.输出逐行(学生代码, "第一行", "第二行")
CppCheck.输出包含(学生代码, "片段")
CppCheck.能编译(学生代码)
CppCheck.写了函数(学生代码, "函数名", "调用表达式")
CppCheck.运行后(学生代码, run => { ... return CheckResult.过("..."); })
CppCheck.编译失败说明(run)        // 编译失败时的标准提示（含报错翻译）

// 返回
CheckResult.过("给学生看的说明")
CheckResult.不过("给学生看的说明")
```

**`run` 上有什么**：`run.编译通过`、`run.行`（输出行列表）、`run.全部输出`、
`run.编译信息`、`run.Raw.CompileFailed`、`run.Raw.Error`

### ⚠ 两个已踩过的坑（别再踩）

**坑一：学生写完整程序时，不要用 `编译并运行`。**
学生写了 `main`，骨架里也有 `main` → GCC 报 `redefinition of 'int main()'`，
学生会以为是自己写错了。**学生写完整程序就用 `直接运行`。**

**坑二：不要用函数外的探针去访问学生的局部变量。**
学生的变量通常在 `main` 里，函数外看不见。我第一版这么写过，
结果检查永远失败，而且报出的提示是错的（说"你没写 int"，其实写了）。

要验证"变量真的参与了计算"，用**文本替换 + 重编译**：
把 `int 甲 = 6` 改成 `int 甲 = 100`，重新编译，看输出会不会跟着变。
会变 = 真用了变量；不变 = 写死了。参考 `第01课_输出.cs` 里的 `改写初值`。

## 说明文字的要求（这是课程质量的关键）

失败的提示必须让学生知道**下一步做什么**。反面例子：

> ✗ 输出不对。

正面例子：

> ✗ 期望输出 6，实际输出 5。
>      你的循环应该是 `i <= n` 而不是 `i < n` —— 想想 n=3 时要加几个数。

**结构**：发生了什么 → 你写的是什么 → 应该怎么写 → （可选）顺便记住什么。

## 怎么验证你的课（**必做**）

```bash
# 1. 构建
dotnet build csharp/cpp-lessons/CppLessons.csproj

# 2. 列出课程，确认你那一课被发现了
dotnet run --project csharp/cpp-lessons

# 3. 把参考答案写进答题文件，跑检查 —— 必须全过
#    （答题文件在 cpp-answers/NN_xxx.cpp，第一次运行「检查 NN」时自动生成）
dotnet run --project csharp/cpp-lessons 检查 NN

# 4. 反面测试：写一个"能输出对但偷懒"的解法，确认被抓住
#    例如把答案写死、或者用现成库函数绕过要考的知识点
```

**第 3 步和第 4 步都必须做，并把实际输出贴进你的最终回复。**
只写不跑的课不算完成。

  学生不用先过"英文命名"这一关
