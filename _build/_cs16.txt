标题|第 09 课：元组、结构与记录类型 —— 值语义 vs 引用语义
要求|1. 定义 `struct 分数 { public int 得分; }`，写 `static 分数 数值改不掉(分数 s)` —— 里面写 `s.得分 = 90;` 然后 `return s;`
要求|2. 定义记录类型 `record 成绩记录(string 名字, int 分数);`，写 `static (string 名字, bool 及格) 取名字(成绩记录 r)` —— 及格是 `分数 >= 60`
要求|3. 定义 `static (int 最低, int 最高) 取最高最低(int[] 数们)` —— 数组为空时返回 `(0, 0)`
模板|// 第 09 课：元组、结构与记录类型 —— 值语义 vs 引用语义
模板|//
模板|// ══ 先介绍：这一课要拆掉一个几乎所有 C# 新手都有的错误直觉 ══
模板|//
模板|//   你在第 07 课写过 class。从那一课起，脑子里大概有了个印象：
模板|//
模板|//       把东西传给方法，方法改了它，外面就跟着变。
模板|//
模板|//   这个印象**只对一半的类型成立**。C# 的类型分两族，赋值与传参的行为完全不同：
模板|//
模板|//      值类型（value type）：  int / double / bool / struct / record struct
模板|//      引用类型（reference type）：class / record / string / 数组 / List<T> / 接口
模板|//
模板|//   区别的根源就一句话：
模板|//
模板|//      **变量里装的是"值本身"，还是"东西在哪里的地址"。**
模板|//
模板|//   值类型变量装的就是数据本身 —— 所以复制变量 = 复制整份数据。
模板|//   引用类型变量装的是地址 —— 所以复制变量 = 复制地址，两个名字指向**同一个对象**。
模板|//
模板|//   这一课你会发现：`struct` 和 `record` 都能改一个东西的两个名字是否互相影响，
模板|//   而选错会写出"方法里改了、外面没变"这种**不报错、只出错**的 bug。
模板|//
模板|//
模板|// ══ 一、值语义 vs 引用语义：一次看明白 ══
模板|//
模板|//   ┌─ 值类型：赋值 = 复印一份 ────────────────────────────┐
模板|//
模板|//       struct 分数 { public int 得分; }
模板|//
模板|//       分数 a = new 分数();
模板|//       a.得分 = 80;
模板|//       分数 b = a;            // ← 复印：b 是**另一份**数据
模板|//       b.得分 = 50;
模板|//       Console.WriteLine(a.得分);   // 80   ← a 没被影响
模板|//       Console.WriteLine(b.得分);   // 50
模板|//
模板|//   └──────────────────────────────────────────────────────┘
模板|//
模板|//   ┌─ 引用类型：赋值 = 又抄了一个地址 ────────────────────┐
模板|//
模板|//       class 成绩单 { public int 得分; }
模板|//
模板|//       成绩单 a = new 成绩单();
模板|//       a.得分 = 80;
模板|//       成绩单 b = a;          // ← 变量里那份**地址**被复制
模板|//       b.得分 = 50;
模板|//       Console.WriteLine(a.得分);   // 50   ← a 也变了！同一个对象
模板|//
模板|//   └──────────────────────────────────────────────────────┘
模板|//
模板|//   把这张对照表记牢，这一课就过了一半：
模板|//
模板|//       int / double / bool / char / 枚举 / struct / record struct
模板|//                                        ⇒ 赋值、传参都**复制**
模板|//
模板|//       string / 数组 / List<T> / class / record / 接口 / 委托
模板|//                                        ⇒ 赋值、传参都只**复制地址**
模板|//
模板|//   ⚠ string 是引用类型，但它有个额外特性：**不可变**。
模板|//     你以为在"改"字符串，其实每次都造了一个新串。所以它表现得像值类型。
模板|//
模板|//   ⚠ record **默认是引用类型**（`record 名字(...)` 等价于 `record class`）。
模板|//     想要值语义得写 `record struct 名字(...)`。
模板|//     这是最容易记反的一处：record ≠ 值类型，record **只是相等语义是值语义**。
模板|//
模板|//
模板|// ══ 二、那"值语义"到底在哪里咬人？ ══
模板|//
模板|//   不在赋值上 —— 赋值写错了编译器不管，但你自己看得见。
模板|//   咬人的地方是**传参**：方法拿到的是一个副本，改了不影响调用者。
模板|//
模板|//       struct 分数 { public int 得分; }
模板|//
模板|//       static void 加分(分数 s)          // s 是**副本**
模板|//       {
模板|//           s.得分 += 10;                 // ✅ 编译通过
模板|//       }
模板|//
模板|//       var 甲 = new 分数();
模板|//       甲.得分 = 80;
模板|//       加分(甲);
模板|//       Console.WriteLine(甲.得分);       // 还是 80 ❗
模板|//
模板|//   ⚠⚠ 注意这个 bug 的**症状**：**不报错、不警告，方法里那句 `+= 10` 是合法的，
模板|//      编译器只是默默改了一个马上要被扔掉的副本。**
模板|//      你盯着代码看不出问题，只有打印出来才发现数字没变。
模板|//
模板|//   想真的改到外面，只能把"改好的整份"**返回**出去（这一课要写的 `数值改不掉`
模板|//   就是这个演示 —— 返回值里有 90，但外面那个变量纹丝不动）。
模板|//
模板|//
模板|// ══ 三、struct / record / class：三个都写"数据"，怎么选？ ══
模板|//
模板|//   ① `class`  —— 有身份的东西
模板|//        人、订单、连接、窗口…… 两个"内容一样"的订单仍然是**两个**订单。
模板|//        默认比较是"是不是同一个对象"（引用相等）。
模板|//
模板|//   ② `record`（引用类型）—— 一张**内容说了算**的纸
模板|//        一条成绩记录、一个坐标、一条日志行、一个 API 返回值。
模板|//        内容一样就是相等：
模板|//
模板|//            var a = new 成绩记录("甲", 90);
模板|//            var b = new 成绩记录("甲", 90);
模板|//            Console.WriteLine(a == b);      // True  ← 逐字段比内容
模板|//            Console.WriteLine(a.Equals(b)); // True
模板|//
模板|//        如果是 `class`，同样的两行会打印 **False**（比的是地址）。
模板|//
模板|//        ⚠ 还有两个白送的好处：
模板|//           · `ToString()` 自动是 `成绩记录 { 名字 = 甲, 分数 = 90 }` 这种能读的样子
模板|//             （class 默认是 "类型名"，打印出来毫无信息）
模板|//           · `with` 表达式能"改一个字段、其余照抄"：
模板|//                 var 乙 = a with { 分数 = 60 };   // 新对象，a 不变
模板|//
模板|//   ③ `struct`（值类型）—— 一小把数字，**并且你明确要值语义**
模板|//        · 字段少（官方建议 ≤ 16 字节左右，别塞 List 和 string 进去）
模板|//        · 生命周期短、数量多（坐标、颜色、范围）
模板|//        · 你**希望**复制是独立的
模板|//
模板|//   ⚠ 选错的代价不对称：
模板|//      · 该用 record 却用了 class ⇒ 相等判断悄悄变成"比地址"，去重/查找全失效
模板|//      · 该用 class 却用了 struct ⇒ 传参开始复制，改一处不生效（上面那个 bug）
模板|//      两样都不报错。⇒ **拿不准就先用 class 或 record**，struct 留给"我很确定"的场合。
模板|//
模板|//
模板|// ══ 四、元组：不想为"就这两个值"专门造一个类型 ══
模板|//
模板|//   方法只能 return 一个值。以前你要么写个 out 参数，要么专门定义一个类。
模板|//   元组让"一次交回两个结果"变成一行：
模板|//
模板|//       static (int 最低, int 最高) 取最高最低(int[] 数们)
模板|//       {
模板|//           int 低 = 数们[0], 高 = 数们[0];
模板|//           for (int i = 1; i < 数们.Length; i++)
模板|//           {
模板|//               if (数们[i] < 低) 低 = 数们[i];
模板|//               if (数们[i] > 高) 高 = 数们[i];
模板|//           }
模板|//           return (低, 高);
模板|//       }
模板|//
模板|//   定义处写 `(int 最低, int 最高)`，返回处写 `(低, 高)` —— 位置一一对应。
模板|//
模板|//   接的时候两种写法：
模板|//
模板|//       var 一对 = 取最高最低(数们);
模板|//       Console.WriteLine(一对.最低);        // ← 有名字，.名字 取
模板|//
模板|//       var (低, 高) = 取最高最低(数们);      // ← 解构，一次拆成两个变量
模板|//
模板|//   ⚠ 元组是**值类型**（`ValueTuple`），所以它也是复制语义。
模板|//   ⚠ 元组适合"两三个值、就地用完就扔"。超过三四个，或者它要在
模板|//     好几个方法之间传来传去 ⇒ **给它起个名字，用 record**。
模板|//     满屏的 `(int, string, double, bool)` 三周后没人看得懂。
模板|//
模板|//
模板|// ══ 五、常见坑 ══
模板|//
模板|//   坑 1：以为改了 struct 参数，外面就变了
模板|//
模板|//       static void 加分(分数 s) { s.得分 += 10; }
模板|//       加分(甲);
模板|//       Console.WriteLine(甲.得分);    // 80，不是 90
模板|//
模板|//     症状：方法里改了，打印出来没变，也不报任何错。
模板|//     为什么：struct 是按值传参，方法里的 `s` 是一个**副本**。
模板|//     改法：返回值带出来（`return s;`），或者参数写 `ref 分数 s`
模板|//           （`ref` 是第 05 课学的，它绕过复制）。
模板|//
模板|//   坑 2：以为 `record` 是值类型，也以为它传参不会共享
模板|//
模板|//       record 成绩记录(string 名字, int 分数);
模板|//
模板|//       static void 改(成绩记录 r) { r.分数 = 100; }   // ❌ 编译不过
模板|//
模板|//     症状：`error CS0200: 属性或索引器"成绩记录.分数"不能分配给 —— 它是只读的`。
模板|//     为什么：位置式 record 自动生成的是 `{ get; init; }` 属性，
模板|//           **只有 init，没有 set** ⇒ 构造完了就不能再赋值。
模板|//     要改只能造一个新的：`var 新 = r with { 分数 = 100 };`
模板|//
模板|//     还有一层：record 本身是**引用类型**，`r` 参数确实是共享的 ——
模板|//     但它的属性不允许你写，所以这个"共享"反而害不到你。
模板|//     别把"相等是值语义"和"传参是值语义"混成一句话记。
模板|//
模板|//   坑 3：相等判断选错了类型，`Contains` / `==` / `Distinct` 悄悄失灵
模板|//
模板|//       class 成绩记录 { public string 名字; public int 分数; }   // 本该用 record
模板|//       var 表 = new List<成绩记录> { new 成绩记录{名字="甲",分数=90} };
模板|//       Console.WriteLine(表.Contains(new 成绩记录{名字="甲",分数=90}));  // False
模板|//
模板|//     症状：明明"一样"的两条，去重去不掉、查查找不到。
模板|//     为什么：class 的 == 和 Equals 默认比**地址**；两条是不同对象 ⇒ False。
模板|//     改法：类型改成 `record`（或 `record struct`），相等自动逐字段比。
模板|//
模板|//   坑 4：把元组的名字当成了类型的一部分
模板|//
模板|//       static (int 最低, int 最高) 取最高最低(int[] 数们) { ... }
模板|//       var 一对 = 取最高最低(数们);
模板|//       Console.WriteLine(取最高最低(数们).最小);   // ❌ 编译不过
模板|//
模板|//     症状：`error CS1061: "ValueTuple<int, int>" 未包含"最小"的定义`。
模板|//     为什么：`(int 最低, int 最高)` 和 `(int 甲, int 乙)` 是**同一个类型**，
模板|//           名字只是给编译器和你自己看的标签，跟着**定义那一处**走。
模板|//
模板|//   坑 5：数组为空时去读 `数们[0]`
模板|//
模板|//       int 低 = 数们[0];        // 空数组 ⇒ IndexOutOfRangeException
模板|//
模板|//     症状：传进空数组就崩，报 `System.IndexOutOfRangeException`。
模板|//     为什么：`数们[0]` 在长度为 0 的数组上根本没有那个格子。
模板|//     改法：开头先 `if (数们.Length == 0) return (0, 0);`
模板|//          —— 初值也从 `数们[0]` 起（不要写 `int 低 = 0;`，
模板|//          那在全负数时会返回 0，跟第 16 课 C 里那个坑一模一样）。
模板|//
模板|//
模板|// ══ 轮到你了 ══
模板|//
模板|//   写三样东西（都在下面，不用写 Main、不用写 class Program）：
模板|//
模板|//     1. struct 分数 { public int 得分; }
模板|//        再加  static 分数 数值改不掉(分数 s)
模板|//            里面 `s.得分 = 90;` 然后 `return s;`
模板|//        —— 这个函数的**返回值**是 90，而调用者的变量应该一点没变。
模板|//
模板|//     2. record 成绩记录(string 名字, int 分数);
模板|//        再加  static (string 名字, bool 及格) 取名字(成绩记录 r)
模板|//            及格 = `r.分数 >= 60`
模板|//
模板|//     3. static (int 最低, int 最高) 取最高最低(int[] 数们)
模板|//            数组为空返回 (0, 0)；否则返回最小和最大
模板|//
模板|// ⚠ record 那一行**末尾有分号**（是"位置式 record"的简写），
模板|//   写成带 `{ }` 的完整形式也行。
模板|//
模板|// 写完后运行：dotnet run --project csharp/cs-lessons 检查 09

要求|1. 写 `class 学生`：构造器 `public 学生(string 名字, int 成绩)`，属性 `public string 名字 { get; }`、`public int 成绩 { get; private set; }`，方法 `public void 改成绩(int 分)` —— 分不在 0~100 之间就**什么都不做**；`public string 报告()` 返回 `"名字 成绩"` 一行
要求|2. 写 `class 计数器`：属性 `public int 值 { get; private set; }`，方法 `public void 加(int n)`、`public void 设为(int v)`（v 为负数时不做任何事）、`public void 重置()`
要求|3. 两个类里都要有一条 `readonly` 字段
模板|// 第 10 课：属性与访问控制 —— 字段为什么不该是 public
模板|//
模板|// ══ 先介绍：从"谁都能改"到"只有我能改" ══
模板|//
模板|//   第 07 课你已经把数据和行为关在一起了。但那时候你多半是这么写的：
模板|//
模板|//       class 学生
模板|//       {
模板|//           public string 名字;
模板|//           public int 成绩;          // ← public 字段：外面随便写
模板|//       }
模板|//
模板|//       var 甲 = new 学生();
模板|//       甲.成绩 = -999;               // ✅ 编译通过 —— 但这是垃圾数据
模板|//       甲.成绩 = 99999;              // ✅ 也通过
模板|//
模板|//   问题不在"能不能写"，而在**没有任何地方能拦住它**。
模板|//   等到某天要统计平均分，你拿到一堆 -999，回头去查是谁写的 —— 无处可查，
模板|//   因为每一个 `甲.成绩 = ...` 都是一个合法的写入点。
模板|//
模板|//   属性（property）解决的正是这件事：
模板|//
模板|//       class 学生
模板|//       {
模板|//           public int 成绩 { get; private set; }   // 外面只能读
模板|//
模板|//           public void 改成绩(int 分)
模板|//           {
模板|//               if (分 < 0 || 分 > 100) return;     // ← 唯一入口，唯一的规则
模板|//               成绩 = 分;
模板|//           }
模板|//       }
模板|//
模板|//   ⇒ 这就是**封装**：不是"藏起来让你看不见"，而是让
模板|//     **规则只有一个出口**。想把成绩改成 -999？做不到。
模板|//
模板|//
模板|// ══ 一、属性 vs 字段：写起来像字段，其实是方法 ══
模板|//
模板|//   最简形式（自动实现属性，最常用）：
模板|//
模板|//       public string 名字 { get; set; }              // 可读可写
模板|//       public string 名字 { get; }                    // 只读：只有构造器能赋
模板|//       public int 成绩 { get; private set; }          // 外人能读，本类能写
模板|//       public int 值 { get; init; }                   // 只能在**创建时**写
模板|//
模板|//   编译器在背后给你造了一个隐藏字段 + 两个方法（get_名字 / set_名字）。
模板|//   所以 `甲.成绩` 用起来像字段，其实是**调用了一个方法** —— 这正是它能带逻辑的原因。
模板|//
模板|//   想亲手写逻辑时，用完整形式：
模板|//
模板|//       private int 成绩_存;                            // 私有字段，外面看不见
模板|//       public int 成绩
模板|//       {
模板|//           get { return 成绩_存; }
模板|//           set
模板|//           {
模板|//               if (value < 0 || value > 100)             // value = 即将写入的值
模板|//                   throw new ArgumentOutOfRangeException(nameof(value));
模板|//               成绩_存 = value;
模板|//           }
模板|//       }
模板|//
模板|//   `value` 是 setter 里的**关键字**（不是你自己起的名字），表示"外面想写进来的那个值"。
模板|//
模板|//   ⚠ 什么时候用哪种：
模板|//     · 不需要校验、不需要计算 ⇒ **自动属性** `{ get; set; }`，别自己造字段
模板|//     · 需要校验、需要惰性计算、需要触发别的动作 ⇒ 完整形式
模板|//
模板|//
模板|// ══ 二、访问修饰符：默认值是什么？ ══
模板|//
模板|//       public      谁都能访问
模板|//       private     只有**本类内部**能访问          ← 类成员的默认值！
模板|//       protected   本类 + 派生类能访问
模板|//       internal    同一个程序集（同一个项目）能访问  ← **顶层类型**的默认值
模板|//       protected internal / private protected      组合，用到再说
模板|//
模板|//   ⚠⚠ 两个默认值必须记牢，它们相反：
模板|//        **类里面的成员（字段/方法/属性）默认是 `private`**
模板|//        **顶层的 class / struct / record / interface 默认是 `internal`**
模板|//
模板|//     症状 1：只写 `int 成绩;` 不写 public，从外面 `甲.成绩` 会报
模板|//             `error CS0122: "学生.成绩"不可访问，因为它具有一定的保护级别`。
模板|//     症状 2：只写 `class 学生`，别的项目引用你这个库时找不到它 ——
模板|//             因为它是 internal，出了这个程序集就没了。
模板|//     ⇒ 想给外面用，**必须显式写 public**。
模板|//
模板|//   ⚠ 别给什么都加 public。判断标准很简单：
模板|//     "这个成员是不是这个类的**对外承诺**？" 不是 ⇒ 私有。
模板|//
模板|//
模板|// ══ 三、`readonly`：给"不该变的字段"上锁 ══
模板|//
模板|//   `readonly` 只能用在**字段**上（不能用在属性上，也不能用在局部变量上）：
模板|//
模板|//       class 银行账户
模板|//       {
模板|//           private readonly string 账号;        // 开户时定了就不许再改
模板|//           public 银行账户(string 账号) { this.账号 = 账号; }
模板|//       }
模板|//
模板|//   规则：**只能在声明处或构造器里赋值**，之后任何地方再写 `账号 = ...`
模板|//        都是 `error CS0191: 只读字段不能作为赋值目标（除非在构造函数中）`。
模板|//
模板|//   ⚠ 三个容易混的：
模板|//     · `readonly` 字段   —— 运行期不能改，但**值可以是运行时才知道的**
模板|//                            （比如构造器参数）
模板|//     · `const`           —— 编译期就定死，必须写死一个字面量，
模板|//                            而且**自动是 static**，只能配基本类型和 string
模板|//     · `readonly` 修饰引用类型的字段 ⇒ 锁的是"指向哪个对象"，
模板|//                            **不是对象内容**！`readonly List<int> a` 里
模板|//                            照样可以 `a.Add(1)`。
模板|//
模板|//   ⚠ 和 `{ get; }` 属性的区别：
模板|//     · `{ get; }` 外面能读，不能写           ← 给外人看的只读
模板|//     · `readonly` 字段 外面连读都读不到（除非你自己加个属性暴露出去）
模板|//     ⇒ 通常成对用：私有 readonly 字段 + 公开的 `{ get; }` 属性。
模板|//
模板|//
模板|// ══ 四、`required` 与 `init`（现代 C# 的"必须填"）══
模板|//
模板|//   老写法靠构造器强制："想 new 出对象？必须把参数交齐。"
模板|//   新写法可以让属性本身就是必填的：
模板|//
模板|//       class 配置
模板|//       {
模板|//           public required string 名字 { get; init; }
模板|//           public int 超时秒 { get; init; } = 30;      // 有默认值，可不填
模板|//       }
模板|//
模板|//       var c = new 配置 { 名字 = "主库" };              // ✅
模板|//       var d = new 配置();                              // ❌ 编译错误
模板|//       // error CS9035: 必须设置必需成员"配置.名字"
模板|//
模板|//   ⚠⚠ `required` 有一个**极其常见的连锁反应**：
模板|//
模板|//     一旦某个属性写成 `required`，所有 `new 配置()` 的地方都编译不过了 ——
模板|//     包括你自己以前写的、包括测试代码。报错是
模板|//     `error CS9035: 必须设置必需成员`。
模板|//     所以 `required` 适合**新写的类型**；给已有类型补 `required` 之前，
模板|//     先确认所有创建点都改得过来。
模板|//
模板|//   ⚠ 本课的两个类**不要求**用 required（构造器已经把必填项管住了）。
模板|//     记住它是什么、报错长什么样就够了。
模板|//
模板|//
模板|// ══ 五、常见坑 ══
模板|//
模板|//   坑 1：用 public 字段代替属性，规则就散掉了
模板|//
模板|//       class 学生 { public int 成绩; }
模板|//       甲.成绩 = -999;
模板|//
模板|//     症状：程序能跑、能编译，但统计结果离谱；而且**查不出是哪儿写坏的**。
模板|//     为什么：字段没有"入口"，任何一行赋值都直接落到数据上。
模板|//     改法：字段改私有（或删掉换自动属性），公开一个 `{ get; private set; }`
模板|//           + 一个带校验的方法。

模板|//           （不许 `缓冲 = new List<int>()`），**不是**堆上那个列表。

模板|//           或者干脆不要暴露可变集合。
模板|//
模板|//   坑 5：构造器里参数名和属性名撞了，直接写 `名字 = 名字;`
模板|//
模板|//       public 学生(string 名字) { 名字 = 名字; }      // ❌ 什么都没干
模板|//
模板|//     症状：构造完了一打印，属性是 null / 0。

模板|//
模板|// ══ 先介绍：多态是怎么生效的 ══
模板|//
模板|//   第 08 课你让三个图形共用一套调用。那时候你可能没细想：
模板|//   `g.面积()` 里的 `g` 是接口类型，为什么能调到"圆"的实现？
模板|//
模板|//   答案在**方法分派**上。C# 里方法有两种绑定时机：
模板|//
模板|//     编译时绑定：看**变量的类型**，定死调哪个方法
模板|//     运行时绑定：看**对象的实际类型**，到运行时才决定调哪个
模板|//
模板|//   C# 的默认是**编译时绑定**。`virtual` 是唯一把某个方法切换到
模板|//   运行时绑定的开关 —— 而 `override` 是"我要接这个开关"。
模板|//
模板|//   ══ 三个词各管什么 ══
模板|//
模板|//     `virtual`   写在**基类**：这个方法允许被改写
模板|//     `override`  写在**派生类**：我要改写它，并且保持"看实际类型"
模板|//     `new`       写在**派生类**：我要**换一个同名方法**，跟基类那个没关系
模板|//
模板|//   关键在于 `new` 和 `override` 的差别 —— 这一个字的差别，
模板|//   决定了"通过基类类型调用时，到底跑哪一个"。
模板|//
模板|//

模板|//       {
模板|//           public virtual string 叫声() => "...";
模板|//       }
模板|//
模板|//       class 狗 : 动物

模板|//
模板|//       class 玩具狗 : 狗
模板|//       {

模板|//       }

模板|//

模板|//
模板|//   注意：**对象从头到尾只有一个**。变的只是"编译器允许你看见哪个方法"。

模板|//

模板|//       ⇒ `override`（前提：基类那个方法标了 `virtual` / `abstract`）
模板|//
模板|//   · 基类的方法**没有**标 virtual，你就是想提供一个同名的新方法
模板|//       ⇒ 编译器会逼你写 `new`（不写只是警告 `CS0108`，但一定要写）
模板|//       ⚠ 这种"隐藏"通常是**设计事故的信号**：先问一句
模板|//         "是不是该回基类加 virtual？"
模板|//
模板|//   · 想彻底禁止别人继续覆写
模板|//       ⇒ 在 override 上加 `sealed`：
模板|//            public sealed override string 叫声() => "汪汪";
模板|//          这样 `玩具狗 : 狗` 再写 `override 叫声()` 会报
模板|//            `error CS0239: "玩具狗.叫声()": 无法重写继承成员"狗.叫声()"，
模板|//             因为它已密封`
模板|//          —— 本课的玩具狗因此只能用 `new`。
模板|//
模板|//   ⚠ `sealed` 也可以整个加在类上（`sealed class 玩具狗`），
模板|//     意思是"这个类不许被继承"。那和 `sealed override` 是两回事。
模板|//
模板|//
模板|// ══ 三、构造器链 `: base(...)` ══
模板|//
模板|//   派生类**从来不继承构造器**。你必须自己写一个，并且负责把基类需要的东西递上去。
模板|//
模板|//       class 汽车
模板|//       {
模板|//           public string 品牌 { get; }
模板|//           public int 最高速 { get; }
模板|//           public 汽车(string 品牌, int 最高速)
模板|//           {
模板|//               this.品牌 = 品牌;
模板|//               this.最高速 = 最高速;
模板|//           }
模板|//       }
模板|//
模板|//       class 跑车 : 汽车
模板|//       {
模板|//           public int 零百加速 { get; }
模板|//
模板|//           public 跑车(string 品牌, int 最高速, int 零百加速)
模板|//               : base(品牌, 最高速)            // ← 这一行把前两个参数交上去
模板|//           {
模板|//               this.零百加速 = 零百加速;        // ← 然后才轮到自己的
模板|//           }
模板|//       }
模板|//
模板|//   ⚠⚠ **`: base(...)` 是这个顺序里的第一步，永远在派生类构造器体之前跑。**
模板|//     所以派生类构造器里能安全地读基类的属性（因为那时候基类已经初始化好了）。
模板|//
模板|//   ⚠⚠ 忘了写 `: base(...)` 会怎样？**不是运行时出错，是编译不过**：
模板|//
模板|//       跑车(string 品牌, int 最高速, int 零百加速) { ... }
模板|//       // error CS7036: 未提供与"汽车.汽车(string, int)"的所需参数
模板|//       //               对应的实参
模板|//
模板|//     为什么：编译器默认帮你插一句 `: base()`（**无参**的），
模板|//           而 `汽车` 只有带参数的构造器 ⇒ 找不到无参的那个 ⇒ 编译失败。
模板|//     什么时候能省：基类**有**无参构造器时（比如你自己写了一个，
模板|//           或者基类一个构造器都没写、编译器送了它一个无参的）。
模板|//
模板|//   ⚠ 每一步顺序（背下来，报错时对得上号）：
模板|//       ① 派生类的**字段初始化器**（`public int x = 5;`）
模板|//       ② 基类构造器（`: base(...)`，它会递归地继续往上）
模板|//       ③ 派生类构造器的**函数体**
模板|//
模板|//
模板|// ══ 四、常见坑 ══
模板|//
模板|//   坑 1：该写 override 却写了 new ⇒ 变成隐藏
模板|//
模板|//       class 狗 : 动物 { public new string 叫声() => "汪汪"; }
模板|//       动物 a = new 狗("旺财");
模板|//       Console.WriteLine(a.叫声());        // ...
模板|//
模板|//     症状：派生类自己的测试全过，但**别人拿着基类类型一调用就变回基类行为**；
模板|//           而且**不报错**（最多一条 `CS0108` 警告让你加 new）。
模板|//     为什么：new 不会接上运行时绑定，编译时按声明类型定死。
模板|//     改法：把 `new` 改成 `override`。若编译器说"没有可重写的成员"，
模板|//           说明基类那个方法没标 `virtual` —— 回基类补上。
模板|//
模板|//   坑 2：基类漏写 `virtual`
模板|//
模板|//       class 动物 { public string 叫声() => "..."; }        // 忘了 virtual
模板|//       class 狗 : 动物 { public override string 叫声() => "汪汪"; }
模板|//
模板|//     症状：`error CS0506: "狗.叫声()": 无法重写继承成员"动物.叫声()"，
模板|//           因为它未标记为 virtual、abstract 或 override`。
模板|//     为什么：`override` 需要一个"允许被改写"的基类成员，`virtual` 就是那个许可。
模板|//     改法：基类 `public virtual string 叫声()`。
模板|//           —— 这条报错信息本身已经把答案说出来了，照着改就行。
模板|//
模板|//   坑 3：以为派生类会继承构造器
模板|//
模板|//       class 动物 { public 动物(string 名字) { ... } }
模板|//       class 狗 : 动物 { }                    // 什么都没写
模板|//       var d = new 狗("旺财");                 // ❌
模板|//
模板|//     症状：`error CS7036: 未提供与"动物.动物(string)"的所需参数对应的实参`，
模板|//           而且报错**指向 `class 狗` 那一行**，你会以为是狗写错了。
模板|//     为什么：狗需要一个能接收 名字 的构造器，而它一个都没有；
模板|//           编译器送的那个是 `狗() : base()`，而 `动物` 没有无参构造器。
模板|//     改法：给狗写 `public 狗(string 名字) : base(名字) { }`。
模板|//
模板|//   坑 4：在构造器里调用虚方法
模板|//
模板|//       class 基
模板|//       {
模板|//           public 基() { 初始化(); }
模板|//           protected virtual void 初始化() { }
模板|//       }
模板|//       class 派 : 基
模板|//       {
模板|//           private readonly int[] 数据 = new int[10];
模板|//           protected override void 初始化() { 数据[0] = 1; }   // 💥
模板|//       }
模板|//
模板|//     症状：`NullReferenceException`，而且堆栈指向基类构造器那一行 ——
模板|//           看起来完全不像自己写的代码出错。
模板|//     为什么：基类构造器跑的时候，**派生类的字段还没初始化**（顺序见上），
模板|//           `数据` 还是 null，而虚方法已经被派发到派生类的实现上了。
模板|//     改法：构造器里别调虚方法；真要调，就在派生类自己构造完之后再调。
模板|//
模板|//   坑 5：`sealed override` 之后继续 override
模板|//
模板|//       class 狗 : 动物 { public sealed override string 叫声() => "汪汪"; }
模板|//       class 玩具狗 : 狗 { public override string 叫声() => "玩具叫"; }
模板|//
模板|//     症状：`error CS0239: "玩具狗.叫声()": 无法重写继承成员"狗.叫声()"，
模板|//           因为它已密封`。
模板|//     为什么：`sealed` 的语义就是"到此为止"。
模板|//     改法：这一课**故意**让你撞这个错，然后用 `new` 绕过去 ——
模板|//           绕过去了也就能亲眼看到隐藏和覆写的差别了。
模板|//
模板|//
模板|// ══ 轮到你了 ══
模板|//
模板|//     class 动物                          // 名字属性 + virtual 叫声 + 介绍
模板|//     class 狗     : 动物                 // sealed override 叫声 → "汪汪"
模板|//     class 玩具狗 : 狗                   // new 隐藏叫声 → "玩具叫"
模板|//
模板|//     class 汽车                          // 品牌 / 最高速
模板|//     class 跑车   : 汽车                 // : base(...) + 零百加速 + 简介()
模板|//
模板|//   ⚠ 玩具狗必须用 `new`（因为狗的叫声是 sealed override）。
模板|//     这正是本课要看的东西：`动物 a = new 玩具狗(...); a.叫声()` 返回的是
模板|//     狗的实现，不是玩具狗的。
模板|//
模板|//   ⚠ `介绍()` 要写成 `名字 + " 说 " + 叫声()` —— 这样它调的是**虚**方法，
模板|//     运行时按实际类型走。
模板|//
模板|// 写完后运行：dotnet run --project csharp/cs-lessons 检查 11

模板|// 第 12 课：泛型与常用集合 —— List<T> 与 Dictionary<TKey,TValue>
模板|//
模板|// ══ 先介绍：数组不够用的时候 ══
模板|//
模板|//   第 04 课用的是数组：长度定死，一旦建立就改不了。
模板|//   可现实里数据是长出来的 —— 学生一个个录进来、日志一行行写进来。
模板|//   你需要"能加、能删、能查"的容器。C# 里最常用的两个：
模板|//
模板|//       List<T>                       有序的一串，能增能删能按位置取
模板|//       Dictionary<TKey, TValue>      键 → 值 的查表，按键查是**瞬间**的
模板|//
模板|//   `<T>` 里的 `T` 是**类型参数** —— 一个占位符，用来之前替换成真类型。
模板|//   第 04 课你已经用过 `List<int>` 了，这一课把它和泛型本身讲透。
模板|//
模板|//
模板|// ══ 一、为什么需要泛型（而不是啥都装 object 的 ArrayList）══
模板|//
模板|//   老 C# 只有 `ArrayList`，里面装的是 `object`，什么都塞得进去：
模板|//
模板|//       var 旧表 = new ArrayList();
模板|//       旧表.Add(1);
模板|//       旧表.Add("字符串");                 // 也让它进 —— 编译通过
模板|//       int x = (int)旧表[1];              // 💥 运行时 InvalidCastException
模板|//
模板|//   两个问题：
模板|//     ① 装进去 / 拿出来要**装箱拆箱**，慢
模板|//     ② 类型错误要等到**运行时**才炸
模板|//
模板|//   泛型把这两件事都解决了：
模板|//
模板|//       var 新表 = new List<int>();
模板|//       新表.Add(1);
模板|//       新表.Add("字符串");                 // ❌ 编译不过，当场拦住
模板|//       int x = 新表[1];                    // 不用强转，类型已知
模板|//
模板|//   ⇒ **泛型的价值：把类型错误从运行时提前到编译时。**
模板|//     写 `List<int>` 之后，编译器全程知道里面只有 int，
模板|//     所以它既能帮你拦错误，又不用装箱。
模板|//
模板|//
模板|// ══ 二、List<T> 的常用操作 ══
模板|//
模板|//       var 名单 = new List<string>();        // 空表
模板|//       var 数们 = new List<int> { 3, 1, 4 };  // 集合初始化器
模板|//
模板|//       名单.Add("甲");                        // 追加到末尾
模板|//       名单.AddRange(new[] { "乙", "丙" });    // 一次加一串
模板|//       名单.Insert(0, "顶");                  // 插到下标 0
模板|//
模板|//       名单.Count                             // ⚠ 是 Count，不是 Length
模板|//       名单[0]                                // 按位置取（下标从 0）
模板|//       名单[^1]                               // 最后一个（^ 是"从末尾数"）
模板|//       名单.Contains("甲")                    // 有没有
模板|//       名单.IndexOf("乙")                     // 第几个；没有是 -1
模板|//
模板|//       名单.Remove("甲");                     // 按**值**删（删第一个匹配的）
模板|//       名单.RemoveAt(0);                      // 按**下标**删
模板|//       名单.RemoveAll(x => x.Length > 1);      // 删掉所有满足条件的
模板|//       名单.Clear();                          // 清空
模板|//       名单.Sort();                           // 就地排（会改自己）
模板|//
模板|//   ⚠ `List<T>` 的 `Count` 是**属性**，数组的 `Length` 也是属性 ——
模板|//     但一个叫 Count 一个叫 Length。列表用 Count，数组用 Length。
模板|//     （List 上写 `.Length` 编译不过：
模板|//       `error CS1061: "List<int>"未包含"Length"的定义`。）
模板|//
模板|//
模板|// ══ 三、Dictionary<TKey, TValue>：按键查表 ══
模板|//
模板|//       var 分数表 = new Dictionary<string, int>();
模板|//       分数表["甲"] = 90;                    // 写：键不存在就新增
模板|//       分数表["甲"] = 95;                    // 写：键已存在就覆盖
模板|//
模板|//       int s = 分数表["甲"];                  // 读
模板|//
模板|//       Console.WriteLine(分数表.Count);        // 2
模板|//       Console.WriteLine(分数表.ContainsKey("甲"));   // True
模板|//
模板|//       foreach (var 对 in 分数表)
模板|//           Console.WriteLine(对.Key + "=" + 对.Value);
模板|//
模板|//   ⚠⚠ **两种取值方式，行为完全不同 —— 这是这一课最重要的坑：**
模板|//
模板|//       int a = 分数表["不存在的键"];              // 💥 KeyNotFoundException
模板|//       if (分数表.ContainsKey("不存在的键"))       // ✅ 先问再取
模板|//           int b = 分数表["不存在的键"];
模板|//       if (分数表.TryGetValue("不存在的键", out int c))   // ✅✅ 一步到位
模板|//           Console.WriteLine(c);
模板|//
模板|//     · 索引器 `表[键]`：键不存在 ⇒ **抛异常**（不是返回 null / 0）
模板|//     · `TryGetValue`：返回 bool，找到就把值写进 out 参数
模板|//
模板|//   ⇒ 只要键**可能不存在**，就用 `TryGetValue`。
模板|//     它是"查表"这个动作的标准写法，比 ContainsKey + 索引器少查一遍。
模板|//
模板|//   ⚠ 字典**没有顺序**。`foreach` 出来的顺序不保证是你插入的顺序，
模板|//     也不保证每次都一样。要固定顺序 ⇒ 遍历前用 OrderBy 排一下。
模板|//
模板|//   ⚠ 键不能是 null，也必须是"可做哈希"的：
模板|//     用自定义的 class 当键时，它默认按**引用**比较 ⇒ 内容一样的两个对象
模板|//     是两个不同的键。要用内容当键 ⇒ 用 `record`（第 09 课），
模板|//     它自带逐字段的相等与哈希。
模板|//
模板|//
模板|// ══ 四、泛型方法：自己写一个 `<T>` ══
模板|//
模板|//   方法名后面加上 `<T>`，`T` 就成了这个方法里的一个"类型占位符"：
模板|//
模板|//       static int 数满足<T>(List<T> 们, Func<T, bool> 条件)
模板|//       {
模板|//           int 计 = 0;
模板|//           foreach (var 项 in 们)
模板|//               if (条件(项)) 计++;          // 条件 是个"收 T、返回 bool"的函数
模板|//           return 计;
模板|//       }
模板|//
模板|//   用的时候编译器**自己推断** T：
模板|//
模板|//       var 数们 = new List<int> { 1, 2, 3, 4 };
模板|//       Console.WriteLine(数满足(数们, n => n % 2 == 0));      // 2
模板|//
模板|//       var 名单 = new List<string> { "甲", "乙丙" };
模板|//       Console.WriteLine(数满足(名单, s => s.Length == 1));   // 1
模板|//
模板|//   同一份代码，`T` 分别变成了 `int` 和 `string` —— 这就是泛型。
模板|//
模板|//   `Func<T, bool>` 是"**收一个 T，返回一个 bool** 的函数"的类型
模板|//   （`Func<...>` 的最后一个是返回类型；不收参数用 `Action`）。
模板|//   第 08 课你写的接口是"一个对象的契约"，`Func` 是"一个函数的契约"。
模板|//
模板|//   ⚠ 泛型约束 `where`：想在泛型里**用** T 的某个能力，就得先声明它有那个能力。
模板|//
模板|//       static T 取大的<T>(T a, T b) where T : IComparable<T>
模板|//       {
模板|//           return a.CompareTo(b) >= 0 ? a : b;      // ← 有约束才敢调 CompareTo
模板|//       }
模板|//
模板|//     常见的几个：
模板|//       where T : class            必须是引用类型
模板|//       where T : struct           必须是值类型
模板|//       where T : new()            必须有无参构造器（才能写 new T()）
模板|//       where T : 基类名 / 接口名    必须继承自它
模板|//
模板|//     不加约束时，编译器只知道 T 是"某个类型" —— 你连 `a > b` 都写不了，
模板|//     报错是 `error CS0019: 运算符">"无法应用于"T"和"T"类型的操作数`。
模板|//     这不是刁难：泛型代码要为**所有** T 成立，而 T 可能是没有 `>` 的类型。
模板|//
模板|//   ⚠ 约束**不能**写成"随便哪个类型"之外的运行时检查 ——
模板|//     `where T : int` 这种是写不了的（int 是密封值类型，没意义）。
模板|//
模板|//
模板|// ══ 五、常见坑 ══
模板|//
模板|//   坑 1：用 `表[键]` 去查一个可能不存在的键
模板|//
模板|//       var 表 = new Dictionary<string, int> { ["甲"] = 90 };
模板|//       Console.WriteLine(表["乙"]);          // 💥
模板|//
模板|//     症状：`System.Collections.Generic.KeyNotFoundException:
模板|//           给定关键字不在字典中`，程序直接终止。
模板|//     为什么：索引器的语义是"**给我这个键的值**"，键不在就只能报错 ——
模板|//           它没法凭空返回一个值（int 的"没有"是什么？0 吗？那和真的 0 混了）。
模板|//     改法：`表.TryGetValue("乙", out int v)`，先看返回的 bool。
模板|//
模板|//   坑 2：在 `foreach` 里增删这个集合
模板|//
模板|//       foreach (var x in 数们)
模板|//           if (x < 0) 数们.Remove(x);        // 💥
模板|//
模板|//     症状：`System.InvalidOperationException: 集合已修改；可能无法执行枚举操作。`
模板|//     为什么：foreach 内部拿的是一个"版本号"，它要求遍历期间集合的版本不变。
模板|//           你 Remove 一次，版本号就变了 ⇒ 下一轮 move next 直接抛。
模板|//     改法：
模板|//       · 最省事： 数们.RemoveAll(x => x < 0);
模板|//       · 或者倒着用 for：

模板|//                 if (数们[i] < 0) 数们.RemoveAt(i);
模板|//
模板|//   坑 3：以为 `表[键] = 值` 只做"修改"
模板|//
模板|//       表["新键"] = 1;                        // 键不存在 ⇒ **新增**，不报错
模板|//
模板|//     症状：循环里反复写同一个键，结果 Count 一直涨，最后发现多了一堆
模板|//           你以为是重复的键。
模板|//     为什么：索引器的 set 是"有则改、无则加"（upsert）。
模板|//     改法：想"只在键已存在时才写"就 `if (表.ContainsKey(k)) 表[k] = v;`。
模板|//           —— 这也正是"统计词频"里 `表[词] = 表.GetValueOrDefault(词) + 1;`
模板|//           能一行搞定的原因。
模板|//
模板|//   坑 4：`List<T>` 的浅拷贝陷阱 —— `List<int> b = a;` 不是复制
模板|//
模板|//       var a = new List<int> { 1, 2 };
模板|//       var b = a;                              // ← 只是抄了地址
模板|//       b.Add(3);
模板|//       Console.WriteLine(a.Count);            // 3 ❗
模板|//
模板|//     症状：改 b 影响了 a，两个变量像是被绑在一起。
模板|//     为什么：`List<T>` 是**引用类型**（第 09 课那张表）—— 变量里装的是地址。
模板|//     改法：要真的复制一份内容：`var b = new List<int>(a);`
模板|//
模板|//   坑 5：泛型里对 T 用了它不一定有的运算
模板|//
模板|//       static T 加起来<T>(T a, T b) => a + b;      // ❌
模板|//
模板|//     症状：`error CS0019: 运算符"+"无法应用于"T"和"T"类型的操作数`。
模板|//     为什么：不加约束时，T 可能是任何类型，包括没有 `+` 的类型。
模板|//           C# 里没有"数值类型"这个约束可加。
模板|//     改法：别写通用加法 —— 老老实实写具体的重载
模板|//           （`加起来(int, int)` / `加起来(double, double)`），
模板|//           或者用 `dynamic`（那是拿掉类型检查，得不偿失）。
模板|//
模板|//

模板|// 第 13 课：异常处理与 using —— 出错的时候怎么办
模板|//
模板|// ══ 先介绍：什么该用异常 ══
模板|//
模板|//   先分清两类"不对"：
模板|//
模板|//     ① **可以预料的、调用方应该处理的**：用户输入了 "abc" 要转成数字
模板|//        ⇒ 用返回值表达：`int.TryParse(s, out int v)` 返回 bool（第 05 课）
模板|//
模板|//     ② **不正常的、继续往下跑没意义的**：数组下标越界、除数为 0、
模板|//        文件被别人删了、网络断了
模板|//        ⇒ 用**异常**：throw 出去，谁处理谁 catch
模板|//
模板|//   ⚠ 判断标准不是"严重不严重"，而是：
模板|//     **"调用方有没有可能合理地处理它？"**
模板|//     转不了的数字 ⇒ 有（提示用户重输）⇒ 用返回值
模板|//     下标越界 ⇒ 没有（代码写错了）⇒ 抛
模板|//
模板|//   异常还有一个隐藏的好处：**它让"正常路径"保持干净。**
模板|//
模板|//       // 不用异常：每一步都要检查，主逻辑被淹没
模板|//       int a = 读(...);   if (a < 0) return -1;
模板|//       int b = 读(...);   if (b < 0) return -1;
模板|//       int c = 算(a, b);  if (c < 0) return -1;
模板|//
模板|//       // 用异常：正常路径一目了然，"出错"只在发生的地方说一次
模板|//       int a = 读(...);
模板|//       int b = 读(...);
模板|//       return 算(a, b);
模板|//
模板|//
模板|// ══ 一、try / catch / finally 三段各管什么 ══
模板|//
模板|//       try
模板|//       {
模板|//           // 可能出事的代码
模板|//       }
模板|//       catch (特定的异常类型 ex)
模板|//       {
模板|//           // 处理它。⚠ 只有类型**匹配**才进来
模板|//       }
模板|//       catch (Exception ex)
模板|//       {
模板|//           // 兜底。⚠ 必须放在**具体类型之后**
模板|//       }
模板|//       finally
模板|//       {
模板|//           // 无论如何都跑：正常结束、return、异常，都跑
模板|//       }
模板|//
模板|//   ⚠⚠ catch 是**按顺序匹配**的，编译器还额外要求你把具体的写在前面：
模板|//
模板|//       catch (Exception ex) { }             // 放前面
模板|//       catch (ArgumentException ex) { }     // ⇒ error CS0160:
模板|//       // "上一个 catch 子句已经捕获此类型或超类型的所有异常"
模板|//
模板|//     为什么：`Exception` 是所有异常的祖先，第一个 catch 就把一切都吃掉了，
模板|//           后面那个永远轮不到。编译器直接判它多余 —— 这是好事，
模板|//     它省得你在运行时才发现"我的 catch 从来不执行"。
模板|//
模板|//   不写 catch 的 try/finally 是合法的，而且很有用：
模板|//
模板|//       try { ... }
模板|//       finally { 清理(); }        // 没有 catch ⇒ 异常继续往上传，但清理一定会做
模板|//
模板|//
模板|// ══ 二、`throw`、`throw ex`、`throw new`：三者的堆栈差很多 ══
模板|//
模板|//   堆栈跟踪（stack trace）就是"错误是怎么一层层传上来的"那张清单。
模板|//   排查线上问题时，它比错误消息本身更重要。
模板|//
模板|//   ┌─ ① `throw;`   —— 原样再抛，**堆栈完整保留** ────────────┐
模板|//
模板|//       catch (Exception ex)
模板|//       {
模板|//           Console.WriteLine("记一笔日志：" + ex.Message);
模板|//           throw;                 // ✅ 起始点是**最初出事的那一行**
模板|//       }
模板|//
模板|//   └────────────────────────────────────────────────────────┘
模板|//
模板|//   ┌─ ② `throw ex;` —— 从**这一行**重新开始，原始堆栈被砍掉 ──┐
模板|//
模板|//       catch (Exception ex)
模板|//       {
模板|//           throw ex;              // ❌ 堆栈从这里开始
模板|//       }
模板|//
模板|//     症状：日志里堆栈最上面是**你自己的 catch 那一行**，
模板|//           再往上什么都没有 —— 你只知道"出过错"，不知道**在哪里出的**。
模板|//     为什么：`throw ex` 是一次新的抛出，CLR 认为"起点就是这里"。
模板|//           它和 `throw new Exception(...)` 在这一点上没有区别。
模板|//     改法：**只写 `throw;`**，不要带那个 `ex`。
模板|//
模板|//   └────────────────────────────────────────────────────────┘
模板|//
模板|//   ③ `throw new XxxException("...", ex);` —— 想**换成自己的异常类型**时用。
模板|//      把原异常当 `InnerException` 传进去，堆栈虽然重开，
模板|//      但原始的错还在 `ex.InnerException` 里，不算丢。
模板|//
模板|//       catch (IOException ex)
模板|//       {
模板|//           throw new 我的异常("保存失败", ex);     // ✅ 换了类型，但没丢原因
模板|//       }
模板|//
模板|//   ⚠ 三句口诀：
模板|//       要原样上抛    ⇒ `throw;`
模板|//       要换类型上抛  ⇒ `throw new 类型(msg, ex);`
模板|//       `throw ex;`    ⇒ **永远不写**
模板|//
模板|//
模板|// ══ 三、什么时候**不**该 catch ══
模板|//
模板|//   官方的话是："Don't catch an exception unless you can handle it."
模板|//   翻成大白话：**你 catch 了，就得做点什么。**
模板|//
模板|//   什么算"做了点什么"？
模板|//     · 恢复了（用默认值重试、换个路径）
模板|//     · 转成用户能懂的话（"文件不存在，请先保存"）
模板|//     · 加一条有用的日志，然后 `throw;` 继续上抛
模板|//     · 转成别的异常类型上抛，带上 InnerException
模板|//
模板|//   什么不算？
模板|//     · `catch (Exception) { }`                ← 空 catch，"吞异常"
模板|//     · `catch (Exception ex) { }`             ← 变量声明了却不用，编译器还会警告
模板|//     · `catch (Exception ex) { return null; }` ← 把错误伪装成"没有数据"
模板|//
模板|//   ⚠⚠ 空 catch 是**最坏的一种 bug 制造机**：
模板|//     症状是"程序不崩，但结果不对/什么都没发生"，而且**日志里一个字都没有**。
模板|//     你会花一整天去找一个本来一行日志就能指出的问题。
模板|//     如果实在要忽略（极少见），至少写清楚为什么：
模板|//         catch (Exception) { /* 这里确实可以忽略：删临时文件失败无所谓 */ }
模板|//
模板|//   ⚠ 还有一条：**别用异常做正常流程控制**。
模板|//        try { return 表[键]; } catch (KeyNotFoundException) { return 0; }
模板|//     能跑，但异常构造很贵，而且把"正常"和"异常"混成一件事了 ——
模板|//     该用 `TryGetValue`（第 12 课）。
模板|//
模板|//
模板|// ══ 四、`IDisposable` 与 `using` ══
模板|//
模板|//   有些东西**用完必须还**：文件句柄、网络连接、数据库连接、图形资源。
模板|//   C# 用接口 `IDisposable` 表达这件事，它只有一个方法：
模板|//
模板|//       public interface IDisposable { void Dispose(); }
模板|//
模板|//   谁实现了它，谁就承诺"调用 Dispose() 会把我占的资源放掉"。
模板|//
模板|//   老写法（啰嗦，而且容易漏）：
模板|//
模板|//       var w = new StringWriter();
模板|//       try { w.WriteLine("..."); }
模板|//       finally { w.Dispose(); }        // 必须自己记得
模板|//
模板|//   新写法：`using` **声明**
模板|//
模板|//       using var w = new StringWriter();
模板|//       w.WriteLine("...");
模板|//       // 方法/作用域结束的时候，自动 Dispose() —— 出了异常也照样 Dispose
模板|//
模板|//   或者 `using` **语句**，能限定更小的范围：
模板|//
模板|//       using (var w = new StringWriter())
模板|//       {
模板|//           w.WriteLine("...");
模板|//       }   // ← 出了这个花括号就 Dispose
模板|//
模板|//   ⚠ 两者的区别只是**作用域**：`using var` 管到所在块的末尾，
模板|//     `using (...)` 管到那个花括号。功能上等价 —— 编译器都会把它
模板|//     展开成 try/finally + Dispose。
模板|//
模板|//   ⚠⚠ `using` 和 `return` 能共存，而且顺序是确定的：
模板|//
模板|//       static int 带资源算(int 数)
模板|//       {
模板|//           using var w = new StringWriter();
模板|//           w.WriteLine("干活");
模板|//           return 数 * 2;          // ← 先算好返回值，**再 Dispose**，最后才真的返回
模板|//       }
模板|//
模板|//     不用担心"return 会不会跳过 Dispose" —— **不会**。
模板|//     这正是 finally 的语义。这条你要是自己想明白了，这一课就通了。
模板|//
模板|//   ⚠ `using` 只对**实现了 IDisposable** 的类型有效。
模板|//     对一个没实现的类型写 `using var x = new 我的类();` 报
模板|//     `error CS1674: "我的类": using 语句中使用的类型必须可隐式转换为
模板|//      "System.IDisposable"`。
模板|//
模板|//
模板|// ══ 五、常见坑 ══
模板|//
模板|//   坑 1：`catch (Exception) { }` 吞掉一切
模板|//
模板|//       try { 危险操作(); } catch (Exception) { }
模板|//       正常继续();
模板|//
模板|//     症状：程序**不崩**，但后面拿到的数据是错的 / 该保存的没保存；
模板|//           更糟的是**没有任何日志**，你不知道刚才发生过什么。
模板|//     为什么：异常的全部信息（类型 + 消息 + 堆栈）都被扔了。
模板|//     改法：要么真的处理，要么 `catch (Exception ex) { 记日志(ex); throw; }`。
模板|//
模板|//   坑 2：`throw ex;` 而不是 `throw;`
模板|//
模板|//       catch (Exception ex) { throw ex; }

模板|//     症状：日志里的堆栈最上面是你的 catch 那一行，源头不见了。

模板|//
模板|//   坑 3：catch 顺序写反
模板|//

模板|//       catch (ArgumentException ex) { ... }     // ❌

模板|//     为什么：Exception 是 ArgumentException 的祖先，第一个就吃完了。

模板|//
模板|//   坑 4：以为 C# 有 Java 那样的"受检异常"

模板|//     症状：看到别人的签名里没有异常声明，以为"这个方法不会抛异常"。
模板|//     为什么：C# **所有异常都是非受检的**，签名里不体现，
模板|//           编译器也不强制你 catch。能不能抛，只能看文档 / 看实现。
模板|//     改法：把这当成"要自己操心的事" —— 调别人的方法时，
模板|//           想一想"它可能抛什么"。
模板|//
模板|//   坑 5：用异常做正常的流程判断
模板|//
模板|//       static int 取(Dictionary<string,int> 表, string 键)
模板|//       {

模板|//     症状：能跑，但"键不存在"和"值真的是 0"混成同一个结果，无法区分；

模板|//     为什么：异常构造要抓堆栈，是重活；而且语义上"没查到"根本不是异常。
模板|//     改法：`表.TryGetValue(键, out int v)` + 返回 bool（第 12 课的写法）。
模板|//
模板|//   坑 6：自己造的异常没有可读的消息
模板|//
模板|//       throw new Exception("错了");
模板|//
模板|//     症状：线上日志里一堆"错了"，谁也判断不出发生了什么。
模板|//     为什么：消息是**给人看的唯一线索**，得写"哪个值、什么范围、期望什么"。

模板|//           自定义异常留给"调用方需要单独处理"的业务错误。

模板|// 第 14 课：模式匹配 —— 让"判断+取值"变成一件事
模板|//
模板|// ══ 先介绍：老写法里那些重复的啰嗦 ══
模板|//
模板|//   假设你有个 `object 东西`，想知道它是不是 int、是的话值多少：
模板|//
模板|//       // 老写法
模板|//       if (东西 is int)
模板|//       {
模板|//           int n = (int)东西;          // ← 刚刚才判断过，现在又要强转一次
模板|//           Console.WriteLine(n + 1);
模板|//       }
模板|//
模板|//   `is` 判断了一次类型，`(int)` 又转了一次 —— 两次说的是同一件事。
模板|//
模板|//   模式匹配把这两步合成一步：
模板|//
模板|//       if (东西 is int n)              // ← 判断成功的同时，n 就已经是 int 了
模板|//       {
模板|//           Console.WriteLine(n + 1);   // 直接用，不用强转
模板|//       }
模板|//
模板|//   ⇒ 这就是模式匹配的全部动机：**把"检查形状"和"取出里面的东西"合并**，
模板|//     顺带让编译器能证明"你取的时候它一定是对的"。
模板|//
模板|//
模板|// ══ 一、`is` 的五种模式 ══
模板|//
模板|//   ① 类型模式：`东西 is int n`
模板|//
模板|//        if (东西 is string s && s.Length > 0)     // ⚠ && 后面 s 就能用了
模板|//            Console.WriteLine(s.ToUpper());
模板|//
模板|//      ⚠ 在同一个条件里 `is` 之后可以放心用 s ——
模板|//        因为 `&&` 短路：s 有值才可能走到后半句。
模板|//
模板|//   ② 常量 / 关系模式：`is 0`、`is >= 90`、`is < 0`
模板|//
模板|//        if (分 is >= 0 and <= 100)               // 等价于 分 >= 0 && 分 <= 100
模板|//
模板|//   ③ 逻辑模式：`and` / `or` / `not`
模板|//
模板|//        if (分 is < 0 or > 100)   Console.WriteLine("无效");
模板|//        if (分 is not 0)          Console.WriteLine("不是零");
模板|//
模板|//      ⚠ 是关键字 `and` / `or` / `not`，**不是** `&&` / `||` / `!`。
模板|//        两者别混：`分 is >= 0 && 分 <= 100` 里 `&&` 两边必须是完整表达式；
模板|//        `分 is >= 0 and <= 100` 里 `and` 两边是**模式**，右边那个 `<= 100`
模板|//        自己不带左操作数（左操作数就是被匹配的那个值）。
模板|//
模板|//   ④ 属性模式：`东西 is 成绩记录 { 分数: >= 90 }`
模板|//
模板|//        if (r is { 分数: >= 90, 名字: not "" })
模板|//            Console.WriteLine(r.名字 + " 优秀");
模板|//
模板|//      `{ 属性名: 模式 }` —— 意思是"这个对象是成绩记录，而且它的 `分数` 属性
模板|//      本身匹配 `>= 90` 这个模式"。可以一次写好几个属性，逗号隔开（相当于 and）。
模板|//
模板|//   ⑤ 位置模式（record 专用，因为 record 有自动解构）：
模板|//
模板|//        if (r is (var 名, >= 90))
模板|//            Console.WriteLine(名 + " 优秀");
模板|//
模板|//      `(var 名, >= 90)` 按**声明顺序**对应 `成绩记录(名字, 分数)`。
模板|//
模板|//
模板|// ══ 二、switch 表达式：一条链的判断，写成一张表 ══
模板|//
模板|//       static string 描述(int 分) => 分 switch
模板|//       {
模板|//           < 0          => "无效",
模板|//           >= 90        => "优",
模板|//           >= 80        => "良",
模板|//           >= 60        => "及格",
模板|//           _            => "不及格",
模板|//       };
模板|//
模板|//   和老 `switch` 语句的差别，一眼就能看出来：
模板|//
模板|//       老 switch 语句                      switch 表达式
模板|//       ─────────────────────────────       ────────────────────────────
模板|//       switch (分) { ... }                分 switch { ... }
模板|//       case 90: ...                        >= 90 => "优",
模板|//       **每条都要 break;**                  用逗号，不用 break
模板|//       是**语句**，不返回值                 是**表达式**，整体有个值
模板|//       一个 case 只能写一个常量             `>= 90`、`< 0`、`int n` 都行
模板|//
模板|//   ⚠ 四个语法点，写错一个就编译不过：
模板|//     ① `switch` 在**后面**：`分 switch` —— 不是 `switch (分)`
模板|//     ② 每个分支 `模式 => 值`，**末尾是逗号**
模板|//     ③ 整体是一个表达式 ⇒ 可以直接 `return ... ;`，或者用 `=>` 方法体
模板|//     ④ 必须**穷尽**：所有可能的值都要被某个分支（或 `_`）接住
模板|//
模板|//   ⚠ 漏了兜底会怎样？
模板|//
模板|//       static string 描述(int 分) => 分 switch { >= 60 => "及格" };
模板|//       // warning CS8509: 表达式不涵盖其输入类型的所有可能值
模板|//       //                 （它不处理 < 60）

模板|//     症状：**是一条警告，不是错误** —— 编译能过，但你输入 30 的时候，
模板|//           程序在运行时抛"非穷举的 switch 表达式"（SwitchExpressionException）。
模板|//     为什么：switch 表达式要"整体有个值"，没匹配上就没有值可给。
模板|//     改法：加一条 `_ => ...`。**int 这种类型永远需要兜底**，
模板|//           因为编译器不可能枚举完 40 亿个 int。
模板|//     什么时候不用兜底：`bool` 两个都写了，或者枚举每个成员都写了。
模板|//
模板|//   ⚠ 分支是**从上往下**匹配的，第一个命中的赢：
模板|//

模板|//       }
模板|//

模板|//
模板|//   · 匹配**值**（数字、字符串、枚举）⇒ 关系模式 + switch 表达式最好用
模板|//   · 匹配**类型**（一个 object / 基类引用，可能是好几种东西）
模板|//     ⇒ `is` 类型模式 + switch 表达式的类型模式
模板|//
模板|//       static string 描述对象(object 东西) => 东西 switch
模板|//       {
模板|//           int n when n > 0      => "正数 " + n,
模板|//           int n                 => "非正数 " + n,
模板|//           string s when s == "" => "空字符串",
模板|//           string s              => "字符串: " + s,
模板|//           null                  => "什么都没有",
模板|//           _                     => "不认识的类型",
模板|//       };
模板|//
模板|//     顺序在这里是**必须**的：`string s when s == ""` 一定得写在 `string s` 前面。
模板|//
模板|//
模板|// ══ 四、常见坑 ══
模板|//
模板|//   坑 1：`is` 里声明了变量却在外面用
模板|//
模板|//       if (东西 is int n) { }
模板|//       Console.WriteLine(n);          // ❌ 编译不过
模板|//
模板|//     症状：`error CS0103: 当前上下文中不存在名称"n"`。
模板|//     为什么：模式变量的作用域就是"这个 `is` 为真的那个分支"。编译器
模板|//           不能保证它在那之外有值 ⇒ 干脆不让它在外面存在。
模板|//     改法：把要用的代码挪进 if；或者换个名字并预先声明一个变量接住。
模板|//
模板|//   坑 2：`is` 里声明的变量类型不是你以为的那个
模板|//
模板|//       if (东西 is int s) { s.ToUpper(); }   // ❌
模板|//
模板|//     症状：`error CS1061: "int"未包含"ToUpper"的定义`。
模板|//     为什么：模式变量的类型**由模式决定** —— `is int s` 里 s 就是 `int`。
模板|//     改法：想当字符串用就 `is string s`。
模板|//           （另一种写法是 `is var x`，那 x 就是**原来的类型**，别搞混。）
模板|//
模板|//   坑 3：用 `as` 代替 `is`，然后忘了判 null
模板|//
模板|//       string s = 东西 as string;
模板|//       Console.WriteLine(s.Length);      // 💥 东西不是 string 时 s 是 null
模板|//
模板|//     症状：`NullReferenceException`，而且崩在**下一行**，看起来跟 as 无关。
模板|//     为什么：`as` 转换失败时**返回 null，不抛异常**；null 上取 `.Length` 才炸。
模板|//     改法：用 `is` 模式，一步到位：
模板|//             if (东西 is string s) Console.WriteLine(s.Length);
模板|//           非要用 as 就得紧跟着判 null。
模板|//
模板|//   坑 4：switch 表达式漏兜底（见上面）—— 编译只警告，运行时才炸
模板|//
模板|//       static string 分类(int x) => x switch { > 0 => "正" };
模板|//       Console.WriteLine(分类(-1));      // 💥 非穷举的 switch 表达式
模板|//
模板|//     症状：`警告 CS8509` 你可能根本没看，运行到 -1 才崩。
模板|//     为什么：表达式必须在所有情况下都有一个值。
模板|//     改法：`_ => "非正"`。对 int / string 这类开放类型，**兜底是必需项**。
模板|//
模板|//   坑 5：`is` 里面用 `&&`，把模式当表达式写
模板|//
模板|//       if (分 is >= 0 && <= 100)         // ❌
模板|//
模板|//     症状：`error CS1525: 表达式项"<="无效`。
模板|//     为什么：`&&` 是**逻辑运算符**，它两边要的是完整表达式，
模板|//           而 `<= 100` 缺左操作数，不是表达式。`and` 才是**模式**的连接词。
模板|//     改法：`分 is >= 0 and <= 100`。
模板|//
模板|//   坑 6：`and` / `or` 当成 `&&` / `||` 用在整个表达式上
模板|//
模板|//       if (分 >= 0 and 分 <= 100)        // ❌
模板|//
模板|//     症状：也是 `CS1525` / `CS1003` 一类"语法无效"的报错。
模板|//     为什么：`and` 只能出现在 `is` 模式的**里面**。
模板|//           左边那个 `分 >= 0` 是普通比较表达式，接不上 `and`。
模板|//     改法：要么全程普通写法 `分 >= 0 && 分 <= 100`，
模板|//           要么全程模式 `分 is >= 0 and <= 100`。**别混。**
模板|//
模板|//   坑 7：属性模式里把 `:` 写成 `=` 或 `.`
模板|//
模板|//       r is 成绩记录 { 分数 = >= 90 }      // ❌

模板|//       if (东西 == 1) Console.WriteLine("是一");         // 能编译

模板|//
模板|//     症状：`东西 = 1`（装箱的 int）时两种都对，但 `==` 对 object 走的是

模板|//     为什么：`object == object` 比的是引用（string 有自己的 == 重载，是例外）。
模板|//     改法：判类型/判值一律用模式 —— `东西 is int n && n == 1`，意图清楚。

模板|//
模板|//   没有 LINQ 的时候，想挑出所有偶数，你得这么写：
模板|//

模板|//
模板|//   `Where` 收一个"每个元素 → 要不要它"的函数，返回筛选后的序列。

模板|//   ⚠ 但这一课真正的主角不是这几个方法名 —— **是「延迟执行」。**

模板|// ══ 一、五个最常用的操作 ══
模板|//
模板|//       var 分数 = new List<int> { 88, 42, 95, 60, 73 };
模板|//
模板|//   ┌ Where —— 筛选：留下满足条件的 ────────────────────────┐
模板|//       var 及格 = 分数.Where(分 => 分 >= 60);
模板|//       // 88, 95, 60, 73
模板|//   └──────────────────────────────────────────────────────┘

模板|// ══ 二、延迟执行：这一课唯一必须搞懂的东西 ══
模板|//
模板|//   先看一个能让你愣住的例子：
模板|//
模板|//       var 数们 = new List<int> { 1, 2, 3 };
模板|//
模板|//       var 查 = 数们.Where(数 => 数 > 1);      // ← 这一行**什么都没做**
模板|//
模板|//       Console.WriteLine(查.Count());          // 2
模板|//       Console.WriteLine(查.Count());          // 2     （只是又算了一遍）
模板|//
模板|//   再看：
模板|//
模板|//       var 数们 = new List<int> { 1, 2, 3 };
模板|//       var 查 = 数们.Where(数 => 数 > 1);      // 定义查询
模板|//
模板|//       数们.Add(99);                            // ← 定义**之后**改数据
模板|//
模板|//       foreach (var 数 in 查)
模板|//           Console.WriteLine(数);               // 2  3  99
模板|//                                                  //        ↑ 99 也在里面！！
模板|//
模板|//   ⚠⚠ **99 是在查询定义之后才加进去的，但它出现在结果里了。**
模板|//
模板|//   为什么：`Where(...)` 这一行**只是描述了一个查询**，它一个元素都没看过。
模板|//   真正的遍历发生在**你开始枚举它的时候** —— `foreach`、`Count()`、
模板|//   `ToList()`、`ToArray()`、`Sum()`…… 每一次枚举都**重新跑一遍**查询，
模板|//   而且读的是**当下**的数据。
模板|//
模板|//   ⇒ 一句话：**LINQ 查询是"配方"，不是"菜"。**
模板|//     写 `Where` 那一行是在写菜谱；`foreach` 才是真的下锅。
模板|//
模板|//   这个设计有它的道理：
模板|//     · 省事 —— 你写五个 Where 也只是一次遍历
模板|//     · 能用在无限序列、数据库、网络流上（`IEnumerable<T>` 可以一个一个来）
模板|//     · 组合查询不用产生中间集合
模板|//
模板|//   代价就是下面这些坑。
模板|//
模板|//   ⚠ 一个更隐蔽的后果：**同一个查询被枚举两次，就是算了两遍。**
模板|//
模板|//       var 查 = 数们.Where(数 => { Console.WriteLine("看了 " + 数); return 数 > 1; });
模板|//       Console.WriteLine(查.Count());      // 打印了 3 行"看了 x"
模板|//       Console.WriteLine(查.Count());      // **又**打印了 3 行
模板|//
模板|//     如果那个 lambda 里有开销大的操作（读文件、算哈希），
模板|//     你就在不知情的情况下做了两次。⇒ 确定要复用结果时，
模板|//     **立刻收口**：`var 查 = 数们.Where(...).ToList();`
模板|//
模板|//

模板|//

模板|//
模板|//   坑 1：以为 `Where` 已经执行了（本课的头号坑）
模板|//
模板|//       var 查 = 数们.Where(数 => 数 > 1);
模板|//       Console.WriteLine("我筛完了");         // 你以为这里已经筛过了
模板|//       // 其实一个元素都还没看
模板|//
模板|//     症状：断点打在 lambda 里，发现它在 `Where` 那一行**根本不停**，
模板|//           而是停在你 `foreach` / `Count()` 的时候；
模板|//           或者"我已经筛过了，后来又加的数据不该出现"—— 但它出现了。
模板|//     为什么：Where 只是构造了一个查询对象，枚举时才逐个元素调你的 lambda。
模板|//     改法：需要"现在就定下来"就收口 `.ToList()`。

模板|//   坑 2：把同一个查询用两次，以为它缓存了
模板|//
模板|//       var 查 = 数们.Where(慢判断);
模板|//       if (查.Count() > 0 && 查.First().分数 > 60)   // 慢判断跑了不止一遍
模板|//
模板|//     症状：日志里同一个元素被判断了好几次；性能莫名其妙地差。
模板|//     为什么：每次枚举（`Count()` 一次、`First()` 又一次）都从头跑。
模板|//     改法：`var 快 = 查.ToList();` 然后用 `快`。
模板|//
模板|//   坑 3：在 LINQ 的 lambda 里改原集合
模板|//

模板|//
模板|//     症状：`System.InvalidOperationException: 集合已修改；可能无法执行枚举操作。`
模板|//           —— 和第 12 课 `foreach` 里增删是同一个异常。
模板|//     为什么：`Where` 是延迟的、且**共享**原集合的枚举器；
模板|//           你在遍历途中改集合，版本号变了 ⇒ 抛。
模板|//     改法：
模板|//       · 先收口再改：`foreach (var 项 in 们.Where(条件).ToList()) 们.Remove(项);`
模板|//       · 或者 `们.RemoveAll(项 => 条件);`（最省事，一步到位）

模板|//   坑 4：用两个 `OrderBy` 想实现多级排序
模板|//
模板|//       var 排 = 们.OrderBy(项 => 项.班).OrderBy(项 => 项.分数);   // ❌
模板|//
模板|//     症状：班那一级**完全没起作用**，结果只按分数排。
模板|//     为什么：第二个 `OrderBy` 是**重新排序**，它不记得前一次的键。
模板|//     改法：第二级开始用 `ThenBy` / `ThenByDescending`：

模板|//
模板|//     症状：`System.InvalidOperationException: 序列不包含任何元素`。
模板|//     为什么：`First()` 承诺"一定给你一个"，给不出就报错。
模板|//     改法：可能为空就用 `FirstOrDefault()`（值类型给默认值、引用类型给 null），
模板|//           或者先 `Any()` 问一句。
模板|//     顺带一提 `Single()`：它要求**正好一个** —— 0 个抛、2 个也抛。
模板|//

模板|//
模板|//       int 上限 = 60;
模板|//       var 查 = 们.Where(项 => 项.分数 >= 上限);
模板|//       上限 = 90;                                  // ← 改了

模板|//
模板|//     症状：结果和"写查询时的意图"不一致。
模板|//     为什么：lambda 捕获的是**变量本身**（不是当时的值），
模板|//           而且延迟执行让求值发生在**改之后**。
模板|//           两个坑叠在一起，结果非常反直觉。
模板|//     改法：把要用的值先复制到不会变的局部变量里，
模板|//           或者定义完立刻收口 `.ToList()`。
