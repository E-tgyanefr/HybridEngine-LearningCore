# 第 16~25 课：做完之后发现的问题（给维护者）

写这十课的过程中踩到的**真问题**，都值得记下来 —— 有几条不是我的课的问题，
而是**环境**和**课程库**的问题，下一个写课的人一定会再撞上。

## 一、最重要的一条：`CppRunner.清理旧目录` 会删掉**别人**正在用的编译目录

### 现象

检查时不时报：

```
ld.exe: cannot open output file C:\…\Temp\hybridengine_light_cpp\run12336_4\prog.exe: No such file or directory
cc1plus.exe: fatal error: C:\…\Temp\hybridengine_light_cpp\run24968_2\main.cpp: No such file or directory
```

**这不是学生代码的问题**，但学生看到的是「编译没能通过」，
会一头雾水地去改本来没错的代码 —— 正是这个项目一直想避免的那类反馈。

### 定位过程（都是实测，不是猜）

我写了一个小程序，在 `%TEMP%` 下建目录然后盯着看：

```csharp
string dir = Path.Combine(Path.GetTempPath(), "hybridengine_light_cpp", "run" + Environment.ProcessId + "_probe");
Directory.CreateDirectory(dir);
File.WriteAllText(Path.Combine(dir, "main.cpp"), "…");
for (int i = 0; i < 6; i++) { Console.WriteLine(i + " 目录在？" + Directory.Exists(dir)); Thread.Sleep(400); }
```

结果：**第 1 次打印还在，800 毫秒后就没了。** 同一时间建的
`aaa_test1`、`bbb_test2` 两个目录一直好好的 —— 说明删的**只针对 `run*` 名字**。

再看 `CppRunner.清理旧目录` 的逻辑就很清楚了：

```csharp
// 规则二：别的进程留下的一律可清（那些再也不会被用到）
if (本进程的 && 序号 > current - 6) continue;
try { Directory.Delete(d, recursive: true); } catch { }
```

它按 `run{进程号}_{序号}` 解析，**不属于当前进程的一律删**。
写这十课时机器上同时有好几个助手在跑各自的课程检查 ——
于是 A 刚建出来的目录，被 B 的第一次检查顺手删掉了。

### 影响

- 不是必现，但**每次检查的第一次编译**最容易撞上（那时别人也可能刚建目录）。
- 对单人在自己终端跑的学生**没有影响**（同一时刻只有一个进程）。
- 对「几个人同时用这台机器 / 同时跑多个课的检查」**一定会撞**。

### 建议的修法（给维护者）

`清理旧目录` 现在只认「本进程 / 别的进程」两档，加一档「**这个目录还新不新**」就够了：

```csharp
// 规则三：**最近 10 分钟内动过的目录一律不删** —— 不管它是谁的
//（别的进程可能正在用它编译，删掉就是一次假报错）
if (Directory.GetLastWriteTimeUtc(d) > DateTime.UtcNow.AddMinutes(-10)) continue;
```

课程作者侧的临时办法（我在这十课里用了）：给 `CppCheck.编译并运行` 套一层
**失败重试一次**的包装，只对上面这两句报错重试（见每课底部的 `编译并运行`）。

### 还有一条相关的：MinGW 的 `ld.exe` 写不进含中文的路径

同一个报错（`cannot open output file …: No such file or directory`）还有第二个原因：
**目标路径里有中文**。实测：

- 输出写到 `D:\…\引擎\LearnCode\_build\_tmpx\dbg\m.exe` ⇒ **失败**
- 同样一个 `m.cpp`，输出写到 `C:\lc_tmpx\m.exe` ⇒ **成功**

`g++` 读中文路径的源文件没问题，**只有链接器写 exe 时会栽**。
这个项目根目录里就有「引擎」两个字，所以任何"把编译产物放在项目目录下"的做法都会踩到。
⇒ 课程的临时目录必须选在**全 ASCII** 的位置。

## 二、检查写法上踩的坑：**标记不能靠"行"去数**

第 16 课给学生的任务是"把表格一行一行打出来"。我第一版的对答案办法是：

```csharp
// 骨架：std::cout << "行1|"; 打印每行(甲, 3); std::cout << "行2|"; 打印每行(甲, 3); …
// 检查：取 "行2|" 后面那一行
```

**它错了，而且错得很隐蔽**：打印函数自己会在末尾换行，
所以第二组的 `行2|` 到底和上一组最后一个数**同处一行**、还是**另起一行**，
取决于学生把 `'\n'` 打在哪一层循环里 —— **两种写法都对**，按行取就只能认一种。

### 试过、都失败的三种取法

| 取法 | 为什么不行 |
|---|---|
| 按「第几行」取 | 换行位置随学生的写法变（上面那条） |
| 取到「下一个空白」为止 | 内容本身就是空格分隔的（`1 2 4 5 8`），只能取到 `1` |
| 取到「下一个标记」为止 | 空内容的那几组（长度 0 时什么都不打）恰好和**闭标记**挨在一起（`冒泡空\|冒泡空\|`），边界差一格 |

### 最后用的写法

调用点把每个标记**前后各写一次**，而且两组之间用换行隔开：

```cpp
std::cout << "行1|"; 打印每行(甲, 3); std::cout << "行1|\n";
```

检查里取「完整标记（带竖线）之后、**同一个标记下一次出现**之前」那一段。
要点有两个：

1. **必须用带竖线的完整标记去找**，不能只用名字 ——
   `和1|` 会先命中 `和10|` 的前半截（第 19 课实测取到 `55|`）；
2. 右边界用「同一个标记的下一次出现」或「下一个竖线」，**别用"下一个别的标记"**
   —— 空内容那几组会算错一格。

### 附带一条：数字型标记名要当心

第 19 课我一开始想起名 `和1|`、`和10|`、`和万|`。
`IndexOf("和1|")` 会命中 `和10|` 里的前两个字符 —— 这一课我最后改成
`和0| 和1| 和10| 式10| 方10| 和万|`（每个名字都不互为前缀）才干净。

## 三、讲义里的"期望值"必须实测，我凭猜写的三个都错了

写第 22 课时我顺手写了三个自以为是的数：

| 我猜的 | 实际 |
|---|---|
| `是质数(99999937)` = true | **false**（它 = 7 × 14285705…，是合数） |
| `是质数(1000003)` = false（我说它 = 29 × 34483） | **true**（1000003 是质数；**1000007** 才是 29 × 34483） |
| `最大质因数(199999874)` = 99999937 | **2702701**（199999874 = 2 × 37 × 2702701） |

这些数最后全部用 g++ 跑了一遍确认：

```
质 99999936=0  1000003=1  99999989=1  999999937=1
因 1=1 2=2 12=6 36=9 100=9
质因 1=0 2=1 12=3 36=4 1024=10
最大 1=1 97=97 100=5 1024=2 199999978=99999989
π(10^6) = 78498
fib(45)=1134903170   fib(50) mod 1e9+7 = 586268941   fib(1000) mod 1e9+7 = 517691607
爬楼梯(40)=165580141   铺地砖(20)=10946
```

**教训：检查里的每一个期望值都必须跑出来，不能推。** 推错一个，
就是"正确解法被判错"，学生按提示改只会越改越远。

## 四、性能类的核心检查点：先量一量"偷懒写法到底会不会超时"

这一课我用「喂大数据、让它超时」当核心检查点（第 19、22、24 课都是）。实测下来：

| 课 | 偷懒写法 | 实际耗时 | 60 秒超时抓得住吗 |
|---|---|---|---|
| 19 算法复杂度 | `平方和` 两层循环，n=20000 | 约 0.4 秒 | ✗（**必须**自己收窄：真按 n=100000 喂就是 10^10 次、几分钟） |
| 22 初等数论 | `是质数` 试到 n，n≈10^9 | **2.5 秒/个** | ✗ **抓不住**（我原以为会超时） |
| 24 素数筛 | `素数个数` 逐个试除到 10^6 | 约 50 秒 | ✓（勉强，刚好在 60 秒内） |

**第 22 课因此改成了"自己计时"**：调用点里用 `std::chrono` 量两个大质数的耗时，
超过 2000 毫秒就判不过 —— 参考实现是 0 毫秒，偷懒写法实测 **6221 毫秒**。
这比"等 60 秒超时"可靠得多，反馈也快。

⚠ 用 `std::chrono` 要**自己 include `<chrono>`** —— 它不在 `<iostream>` 里
（我第一版想省这一行，编译不过）。

## 五、给自己的两条操作教训

1. **`Assembly.LoadFrom` 不会加载"新版本"**：
   我用一个反射小工具跑检查，工具自己也引用了课程程序集 ——
   `bin` 里那份**旧副本**先被加载，之后再 `LoadFrom(新路径)` 拿到的还是旧的。
   症状是"改了代码、重建了、跑出来还是旧行为"，我因此白调了半小时。
   ⇒ 跑之前先把工具 `bin` 里那份 `*.CppLessons.dll` 删掉。

2. **批量替换要看清自己改的是谁**：
   我给「编译并运行」套重试包装时，用文本替换把 `CppCheck.编译并运行` 全换成了
   `编译并运行` —— 结果**包装函数自己也调用了自己**，一跑就栈溢出、程序直接消失。
   症状是"这一课一条检查都不输出"。⇒ 替换之后要回头看一眼新代码里有没有自引用。
