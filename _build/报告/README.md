## 反复出现的三条教训

### ① 期望值必须跑出来，不能推

C++ 那位凭猜写了三个数，**三个全错**（其中 `1000003` 他判成合数，实际是质数）。
Java 那位说"救回至少 8 处"。我这一轮亲手算错过一次（背包的四种容量）。

⇒ 做法：**写一个临时探针，把参考答案真跑一遍，按标记打印真实输出，
照它写期望值。** 推错一个，就是"正确解法被判错"，学生按提示改只会越改越远。

### ② "输出一样"不等于"学到东西"

这一轮抓到的最有价值的一类问题，全都是**偷懒写法输出与正确解完全相同**：

```
C  21 课  直接调 qsort              → 输出与参考答案一字不差
C++ 27 课 只挪指针不 delete          → 逐字节相同
C++ 38 课 一层一层乘（冒充倍增）      → 完全相同
C++ 39 课 线性扫描（冒充堆）          → 完全相同
C#  22 课 读文件写死                 → 第一份数据上完全正确
```

⇒ 只能靠**源码检查**（`代码包含` / `代码不含`）+ **换一份数据** 兜底。
**正验证（参考答案能过）永远发现不了这些。**

### ③ 计时/爆栈这类判据，规模阈值必须先实测

```
Java 25 课  两百万耗时 → 试除法只要 1.1 秒，抓不住 ⇒ 改两千万 + 计时窗口整个包住
Java 30 课  20000 个有序数 → 某些 JVM 上恰好不爆栈 ⇒ 改 50000
C++  22 课  试到 n≈10⁹ → 2.5 秒，60 秒超时抓不住 ⇒ 改成"自己计时，2000ms 上限"
Python 44 课 阈值定得太松，让错误答案通过了 ⇒ 收紧规模
```

⇒ **别猜"这样应该会超时"**。先量一量偷懒写法实际跑多久，再定阈值。
⚠ 而且**计时窗口要包住整件事** —— 只包一半等于没量。
