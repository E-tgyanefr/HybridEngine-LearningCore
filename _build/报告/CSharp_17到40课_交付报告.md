### 2. ⚠ 一个**额外的共用文件**：`csharp\cs-lessons\课检查工具.cs`（194 行）

这 24 课的检查里，「拼调用点 / 按标记对答案 / 去注释 / 取函数体 / 编译缓存」
五件事完全一样。抄 24 份的代价不是多几行，而是**改一处要改 24 处**。

- 它放在**工程根目录**，不在 `Lessons\` 里 —— 因为 `_build\_verify_compiled.py`
  会把 `Lessons\` 下每个 `.cs` 都当成一课去解析参考答案，多一个文件就会记一笔
  「没验到」，而"没验到"会让整个验收直接判失败。
- csproj 默认包含 `**/*.cs`，所以它照样被编译；验收脚本也**不会**把它当课程
  （结果是 41/41、0 个"没验到"）。
- 第 17 课**没有**用它（自带一份），因为它是这批课的"手写标准件"。

## 四、写课过程中发现的真问题

### 1. 三个"计时判据"都是先实测再定阈值的

| 课 | 判据 | 本机实测 | 阈值 |
|---|---|---|---|
| 25 | `素数个数(50 000 000)` | 埃氏筛 **338 ms**；逐个数试除 n=10^7 就要 **2 795 ms**（折算 n=5×10^7 约 14 s） | 3000 ms（离筛法 8 倍以上、离试除法 4 倍以上） |
| 30 | 20 万个随机数排序 | 快排几十毫秒；冒泡/选择是 200 亿次比较（几十秒） | 3000 ms |
| 20/26/29 | —— | **故意不做时间判据**：大数只用来让 O(n²)/递归写法"跑不完或明显偏慢"，判对错靠**次数/结果**，不靠秒表 | —— |

### 2. 我算错的期望值（都在验证时被参考答对的输出抓出来，已改正）

- 迷宫蛇形长廊 `(0,0) → (6,0)` 是 **14** 步（我原来写 6 —— 左边那一列被墙截断了）。
- `最短路(6, 边, 3)` 到 5 号点是 **13**（3→2→5），不是 9。
- `打家劫舍({4,5,4})` 是 **8**（拿两头 4+4），不是 9。
- `LCS("abcdef","axcyez")` 是 **3**（a、c、e）。
- `路径数有障碍({{0,1},{1,0}})` 是 **0**（右边和下边都是墙，一步都走不了）。
- `二分查找` 的"重复元素"用例：`Array.BinarySearch` 式的返回**任意一个 3 都对**，
  检查改成"1/2/3 都算对"，否则会把正确解法判错。

### 3. ⚠ 一次真实事故：我写的一个批量脚本弄坏了别人（和早期）的课，已还原

为了满足"正文里不能用英文双引号"，我写了个脚本把课程**注释行**里的 `"…"`
换成「」。它的判据太宽：

- 把**相邻字符串字面量之间的胶水**也包了进去
  （`("稳定甲", "甲,乙,丙", …)` → `("稳定甲「, 」甲,乙,丙「, 」…)`），直接编译不过；
- 把**代码示例行**里的字符串也换了（`File.WriteAllText("a.txt", …)` → `(「a.txt」, …)`）；
- 更糟的是它扫了 `Lessons\` 下**所有**文件 —— **00~16 课（不是我的课）也被改了 14 个**。

处理：
1. 立刻 `git checkout --` 把 00~16 课**全部还原**（现在 `git status` 里 00~16 干净）；
2. 写了一个**只针对 17~40 课**的修复脚本 `_cs17_40\修误伤.py`，把胶水还原成 `", "`；
3. 又补了两处跨字面量的残留（第 19 课的探针、第 28 课的汉诺塔标记）；
4. 现在有成套自检脚本：`查误伤.py`、`查残留.py`、`查代码里的引号.py`，
   跑完都是 **0 处**；
5. 最后重跑验收：41/41。

⚠ 教训写在明处：**"批量改文本"的判据一旦宽了，就会跨语法边界误伤；
而且会伤到不在自己范围内的文件。** 后来我改成"只改列出来的那几处"。

### 4. 和 Java 线的关系

- 我的构建里**没有**出现过来自 `java-lessons\` 的 `error CS`（两边是不同工程）。
- 我**没有**碰过 Java 线的任何文件；`git status` 里他的文件在变，那是他自己在写。
- 但两边**共用同一个 `%TEMP%\hybridengine_light_cs`**（CSharpRunner 的临时工程目录）：
  如果 Java 作者也跑 `_verify_compiled.py`（它把 TEMP 指到 `C:\lc_tmpx`），
  和我同时跑就会互相覆盖 `Program.cs` —— 症状是 `✓0 ✗0`（检查根本没跑）。
  我全程用**自己的** `C:\lc_cs_tmp`，并且验收是**独占**跑的。

### 5. 已知的小不足

- 第 20、26、29 课没有时间判据：O(n²) 的写法在"大数"用例上会慢（几秒到十几秒），
  但**答案仍然是对的**，所以是否"用错算法"由**文本判据**（有没有递归 / 有没有用现成排序）
  和**精确的次数/结果**负责，不靠秒表。这是有意的取舍。
- 第 21 课的 n=90 用例放在**一条**检查里：递归写法在那里等一次超时（3 分钟），
  别的检查全用 n ≤ 45，不会每条都超时。
- 计时判据（25、30）在**极忙的机器**上理论上可能误判 —— 阈值都留了 8 倍以上余量，
  失败提示里也打印实测毫秒数。
