# 版本号规则（读这个再改版本号）

## ⚠ 作者的要求

> **第一位（主版本号）保持 `0`。**
> 也就是版本号形如 `0.x.y` —— **不要出现 `1.0.0` 及以上**。

`1.0.0` 的含义是「**已稳定发布**」，这个项目**还没到那一步**。
只有作者**明确说了**，才把第一位提到 1。

（作者的原话是「只要第一版本号不是一就行」；上面是它的展开。）

- 不要因为"功能挺全了"就跳 1.0（功能多 ≠ 稳定）
- 不要因为"tag 看起来该整齐"就跳 1.0
- **第一位锁在 0** 意味着：新功能照样能升 —— 升的是**中间位**
  （`0.1.4` → `0.2.0`），不必死守 `0.1.x`

### 我（AI）犯过的错，留在这里当警示

发 Release 时**自己编了** `v1.0.0`~`v1.0.3`，而代码里写的是 `0.1.0`
—— 两者不一致，而且 `1.0` 暗示稳定，与项目实际状态不符。

**教训**：版本号不是"我觉得该到几了"，而是**作者的定义**。
不确定就取 `0.x` 里最小的增量，**不要自己发明大版本号**。

## 数字怎么变（第一位锁在 0）

| 情况 | 怎么变 | 例子 |
|---|---|---|
| 加了新东西（功能、课程线、**界面**） | 中间位 +1，末位归零 | `0.1.4` → `0.2.0` |
| 只修缺陷、文档、文案 | 末位 +1 | `0.2.0` → `0.2.1` |
| 改动大到"像换了个产品" | 中间位大步跳 | `0.2.0` → `0.5.0` |
| 作者明确说"完成，发正式版" | **才**能动第一位 | `0.x.y` → `1.0.0` |

## 单一真值：只在一处写

```
hybridengine_light/__init__.py  →  __version__ = "0.2.0"
```

其余地方**都从它推导**，不许各写各的：

- 打包脚本 `_build/build_exe.py` 读它来命名 zip
  （`HybridEngine-light-v0.2.0-win64.zip`）
- GitHub Release 的 tag 要**同名**（`v0.2.0`）

> ⚠ 实测踩过：zip 名固定成 `HybridEngine-light-win64.zip`，
> 于是发布目录里躺着两个同名内容（一个带版本号、一个不带），
> **分不清哪个是当前版**。现在名必带版本号，且版本号从代码读。

## 与引擎版本的关系：独立

| 组件 | 版本 | 出处 |
|---|---|---|
| 轻量版（HybridEngine-light） | `0.x.y` | `hybridengine_light/__init__.py` |
| 引擎（专业版） | `0.5.0` | `HybridEngine/CMakeLists.txt` 的 `project(... VERSION ...)` |

**两条线独立** —— 两者发布节奏不同，轻量版不跟着引擎的号走。

## 改版本号时的检查清单

1. 改 `__init__.py` 的 `__version__`
2. 改 README 里那句"当前 **X.Y.Z**"（**判据会检查它一致**）
2. 跑 `python -m unittest discover -s tests -p "test_*.py"`（全绿）
3. 重新构建：`python _build/build_exe.py`
4. 确认 `引擎\发布\` 里的 zip 名带**新**版本号
5. 要发 Release 的话：打**同名** tag，并上传那份 zip
6. ⚠ 旧的 Release **不删**（它们是历史留档）；但要在最新那个的说明里
   注明「请用这一版」
