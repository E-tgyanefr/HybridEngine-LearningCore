## 四、数据源 ↔ 产物一致性（生成式的四条线）

```powershell
python _build\_audit_drift.py
```

**它比的是内容，不是"重新生成看变没变"** —— 后者会把
"我手改过产物"和"数据源本来就对"混为一谈。

**当前实际**（退出码 **0**）：

```

四条线**全部一致** —— 数据源和产物没有分叉
```

（C++/Java/C# 会报"磁盘上多出来的课" —— 那些是**手写课**，本来就不归生成器管，
是正常的。它们只有 00/09~15 那几课是数据源生成的。）

### 4.0 ⚠ 这个脚本原来也是"退出码不能当判据"

它**通篇没有 `sys.exit`** ⇒ 就算报"有 12 个文件不一致"，返回的也是 **0**。
和第三节那个 `_verify_c_neg.py` 是**同一个毛病**，一起补了。现在的判据写死在输出里：

```
  ═══ 判据 ═══
    ①②里有分叉的文件：0 个
    ①里「声明了却没有」的线：无

  结论：数据源和产物没有分叉 ✅
```

什么算失败，说清楚（**「多」不算失败**，那是设计如此）：

| 情形 | 判 |
|---|---|
| ①「少」：数据源声明了、磁盘上没有 | **失败**（学生打不开那一课） |
| ②「变」：重新生成后内容变了 | **失败**（数据源和产物分叉了） |
| ①「多」：磁盘上有、数据源没有 | 只报，不判失败（手写课就是这样） |

⚠ 这三种情形都**实测过**：造一个假仓库（数据源 + 产物 + 假生成器），
四种场景（没分叉 / 分叉 / 少 / 多）的退出码依次是 **0 · 1 · 1 · 0**，全部符合预期。

### 4.1 ⚠ 这里踩过一个很深的坑，值得你知道

**C 线曾经被一个错误的生成器覆盖成编译不过的版本**：

```
python _gen_c16.py                              → c 41/41 ✓
python _gen_c16.py && python _gen_compiled.py c → c 39/41 ✗
```

`_gen_compiled.py` 的线表里**也有一条 `"c"`**，产物目录和 `_gen_c16.py`
一模一样 ⇒ 两个生成器抢同一批文件，**后跑的说了算**。
而它的共享 `打印行()` 会给 C 产出 `printf("%s\n", (…).ToString())` ——
**C 里没有 `.ToString()`**。

⇒ 报的是「编译没能通过」，**而学生的代码一个字都没错**。
⇒ 已把 `"c"` 从 `_gen_compiled.py` 摘掉，并给了一句能照着做的提示。

## 十、这张清单**没覆盖**的（诚实列出来）

1. **全量反验证**：见第三节 —— 现在**有一条统一命令**了
   （`python _build/_verify_negative_all.py`，退出码 0），
   它实跑 **211 条错例**（C 17 · Python 16+52 · C# 9 · GESP 38 · **C++ 38 · Java 41**）**全被拒**。
   ⚠ 但它**只覆盖 143/219 课**（Python 36 · C 17 · C# 8 · C++ 41 · Java 41）；
   而且 **143 是名义覆盖** —— 其中 **C++ 09/11/24 三课是空转的**（错答案照样全过），
   另有 **Java 19/22 两课各有一条具名检查能被绕过**。**课级强证据 = 140/219**，见 3.2.0。
   账本会逐课列出缺口，见 3.2。
   **仍然没有一条"覆盖全部 219 课"的反验证命令。**
   要全覆盖就得每课准备错答案，量很大 —— 目前靠"写课时逐课做 + 抽样复核"。
2. **界面（GUI）的实际观感**：我验的是"能生成、课数对、命令能跑"，
   **没有**逐课肉眼看过界面里的显示效果。
3. **课程内容的"教学效果"**：我只验了"检查真的在管事"，
   **验不了**"学生看了能不能懂" —— 那需要真人试。
4. **每个 `CHECK_` 的健康度**：验的是"参考答案过、错答案被拒"，
   **没有**逐条检查"这个检查函数本身写得对不对"
   （子代理报告里出现过 `分解质因数(0)` 这类**检查自己写错**的情况，
   是靠参考答案那轮抓出来的 —— 说明这个方式是有效的，但不是系统性的）。
5. **课程内容的"手算期望值"**：多个子代理都报告"手算的期望值一定会错"
   （Java 那位说救回至少 8 处）。我这一轮也亲手算错过一次（背包）。
   **这个环节只能靠"把参考答案真跑一遍取真实输出"来防**，
   而它是每课各自的作者在做的，不是有一个统一校验。
6. **界面按钮的实际点击**：`test_gui_flow` 验的是后端流程，
   不是真人点按钮的体验。

## 附二：这一轮抓到的四个真 bug（都修了、都实测验证过）

它们有个**共同点**：都不是"某处代码写错了"，而是
**"没人问过那个问题"**。

| # | 问题 | 症状 | 根因 |
|---|---|---|---|
| 1 | `CppRunner.清理旧目录` 删掉**别人正在用**的目录 | 学生看到「编译没能通过」，**代码却没错** | 假设"别的进程的目录再也不会被用到"——**那个假设是错的** |
| 2 | `JavaRunner.清理旧目录` 解析对不上命名 | 临时目录**永远清不掉**，越攒越多 | 命名改成带进程号了，清理函数还在用老解析 |
| 3 | `CSharpRunner` 固定临时目录名 | 两进程互写 `Program.cs` ⇒ `✓0 ✗0` | 一个进程内的并发有锁，**跨进程的没有** |
| 4 | 两个生成器抢同一批产物 | C 线被覆盖成编译不过的版本 | 一个产物目录**只能有一个生成器** |

⚠ 第 1~3 条是**同一个毛病的三次出现**：
**凡是"固定路径 + 可写文件"的地方，都要问一句：两个进程同时来会怎样？**

⚠ 还有一个同类：`_verify_compiled.py` 和别的脚本抢 `answers` 目录
（实测 40 秒内被清空 11 次）⇒ 现在把"一个 ✓ 和 ✗ 都没有"判为**"没跑到"**
而不是"没过"，并重试。
6. **`0 个 git tag`**：见第八节。版本号规则写着"单一真值"，但没有 tag 的话，
   GitHub 上分不清哪个 commit 对应 0.8.0。**要不要打 tag 由你定。**
