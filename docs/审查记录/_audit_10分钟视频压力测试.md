# ⭐ 「10 分钟视频 · 大量 3D 模型」压力测试（2026-10-14 · Round 8）

> **作者的澄清**：「渲染任务大概是渲染一个**大量 3d 模型的 10 分钟视频**就行」
>
> ⇒ 这一份是**针对这个具体任务**的实测。复现：`C:\gs_link\video_render.cpp`
> ⚠ 而它**推翻了我前面用的口径**（"三角形吞吐"）—— 见第三节。

---

## 一、场景定义（照着作者那句话定的）

```
帧数：60 fps × 10 分钟 = **36,000 帧**（24 fps 则是 14,400 帧）
"大量 3D 模型" ⇒ **每帧 N 个模型、每个模型一次 `Submit`**
   ⚠ 依据：`GpuRenderer` 只有 `Submit(mesh, world, tint)` 一个入口，
     **没有任何 instancing / batch 接口**（我 grep 过公开头）
分辨率 1280×720 · 模型 = `MakeCube`（12 个三角形）+ 一点自身形变（禁止"全同"被优化）
模型都摆在相机前方、不重叠、不被剔除（否则测的是"剔除"不是"渲染"）
```

---

## 二、⭐ 实测数（1280×720 · 每帧换世界矩阵 · 40 帧/档 · 预热 5）

| 模型数 | ms/帧 | 帧/秒 | 三角形/帧 | 60fps 可行? | **10 分钟(36,000 帧)墙钟** |
|---|---|---|---|---|---|
| 1 | 0.0762 | 13,126 | 12 | ✅ | 2.7 秒 |
| 64 | 0.1405 | 7,118 | 768 | ✅ | 5.1 秒 |
| 512 | 1.0011 | 999 | 6,144 | ✅ | 36 秒 |
| **2,048** | **4.4705** | **224** | 24,576 | ✅ | **2.7 分钟** |
| 8,192 | 18.3517 | 55 | 98,304 | ❌ | 11 分钟 |
| 32,768 | 72.9134 | 14 | 393,216 | ❌ | 44 分钟 |

### ⇒ 对作者那句话的直接回答

```
⭐ **可行** —— 条件是**每帧 ≤ ~2,000 个模型**（60 fps 下）
   2,048 个模型/帧 ⇒ 4.47 ms/帧 ⇒ **10 分钟视频约 2.7 分钟渲染完**
❌ 8,192 个模型/帧 ⇒ 18.35 ms/帧 ⇒ **掉出 60 fps** ⇒ 10 分钟视频要 11 分钟
   ⇒ 若要保住 60 fps，可以 **降到 30 fps**（18.35 < 33.3）或 **减少模型数**
```

## 三、⚠⚠ 而它**推翻了"三角形吞吐"这个口径**（这是本份最重要的发现）

我前面用"三角形/秒"报数（`gpu_stress`：饱和 **3.07×10⁷ 三角形/秒**）。
⚠ 但如果**每个模型各一次 Submit**，那个口径会**骗人**：

```
把"每帧三角形数 ÷ ms"算出来（本份数据）：
   24,576 三角形/帧 ⇒ 4.4705 ms ⇒ **5,497 三角形/ms**
  393,216 三角形/帧 ⇒ 72.9134 ms ⇒ **5,393 三角形/ms**
⇒ **每毫秒约 5,400 个三角形，与模型数几乎无关**（**线性**）

而上一轮"一个大网格"（gpu_stress）：
   30,696,594 三角形/秒 = **30,697 三角形/ms**
⇒ ⚠ **差了 5.7 倍**，而且差距**不随负载缩小**
⇒ ⭐ **那 5.7 倍就是「每个模型一次 Submit」的 CPU 开销**
   粗算：4.4705 ms ÷ 2048 模型 = **2.18 µs/模型**
```

⇒ ⭐ **结论：瓶颈在 draw call 的 CPU 开销，不在 GPU 的三角形吞吐。**
  ⚠ 所以**"三角形/秒"这个指标在"多模型"场景下会给出乐观 5.7 倍的错觉**。
  ⇒ **报性能时必须同时说清"几个 draw call"。**

## 四、⚠ 还有一个"模型在动"的代价没测（**明确标出**）

```
本份用的是 `--rebuild 否` ⇒ **顶点缓冲不重建**，只换世界矩阵
⚠ 但真场景里"模型在动"分两种：
   ① 只**整体移动/旋转** ⇒ 换世界矩阵就够（**本份测的就是这个**）✅
   ② **蒙皮/变形**（顶点本身在变）⇒ **每帧要重建顶点缓冲** ⇒ **本份没测**
   ⇒ 我给了 `--rebuild` 开关，但**没跑**（时间/上下文用完了）⇒ **如实记：没验**
```

---

## 五、⇒ 唯一值得做的那个优化（给下一步）

```
❌ 继续优化"三角形吞吐" —— **没用**，瓶颈不在这（5.7 倍差距是 CPU 提交）
⭐ **减少 Submit 调用次数** —— 三条路：
   ① **合批**：把多个模型的世界矩阵乘进顶点，合成**一个网格**再一次提交
      ⚠ 但顶点数会 ×N ⇒ 内存/带宽涨；且"每个模型独立剔除/动画"会丢
   ② **实例化（instancing）**：D3D11 原生支持，一次 draw call 画 N 个实例
      ⇒ ⚠ **需要给 `GpuRenderer` 加接口**（现在没有）—— 这是**真值得做的一件事**
   ③ **静态合批 + 分层**：不动的模型合一次，动的各自提交
```

⚠ **而 ② 的收益可以从本份数直接估**：
```
若把 2,048 次 Submit 合成 1 次（三角形数不变 24,576）：
   按 gpu_stress 的饱和吞吐 30,697 三角形/ms ⇒ **0.8 ms/帧**
   而现在 4.47 ms/帧 ⇒ **约 5.6 倍的差距**
⇒ ⭐ **也就是说：一个 instancing 接口就能让"10 分钟视频"从 2.7 分钟降到 ~30 秒**
   （⚠ 这是**推算**，不是实测 —— 要实测必须先把接口写出来）
```

## 六、⚠ 没验到的（逐条）

1. **`--rebuild`（每帧重建顶点缓冲）** —— 开关写了，**没跑**
2. **多分辨率**（只 1280×720）· **带纹理** · **透明/混合**
3. **中位数**（本份每个数单次）
4. **功耗 / GPU 占用** —— 没测
5. **instancing 的收益** —— **推算 5.6 倍，未实测**（要写接口）
6. **CPU 侧 + 另两个引擎** —— 归 `task-16` / `task-17`

## 七、⚠ 我这支探针的边界（别当成"引擎的极限"）

```
· 模型是 `MakeCube`（12 三角形）—— **很小的模型**。真实 3D 模型往往几百~几万三角形
  ⇒ ⚠ **若每个模型几万三角形，瓶颈会从"draw call"转回"三角形吞吐"** —— 本份没覆盖那个区间
· 一次 `Submit` = 一次 draw call（推断），但我**没在 D3D11 层计数**（没拿 PIX / 没插桩）
· 单个窗口 1280×720 · 无 vsync
```
