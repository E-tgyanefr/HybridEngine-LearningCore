## 一、⚠ 先纠正我自己一个错判

我在 Round 2 说过：「专业版 C++ 真线程 ⇒ 能吃 24 核」。
**那个说法不准确。** 我把 `std::thread` 的命中数（9 处）当成了"渲染并行"的证据。

**实测（逐个调用点看）**：

```
std::thread ×9 全部在 **src/editor/ai_assistant.cpp**（AI 助手的异步检查）
   ai_assistant.cpp:274/277/280  std::thread([this, ...]{ ... })
其余命中都不是"计算并行"：
   ms_bind.cpp:44  std::atomic<int> gLiveEngines{0};     ← 引擎实例计数
   ms_bind.cpp:45  std::thread::id gMainThread;          ← **线程归属校验**（回调必须回主线程）
   winmm_audio.cpp:19 std::atomic<int> gAliasSeq{0};     ← 音频别名序号
```

⇒ ⭐ **专业版的渲染与游戏循环：单线程。**
  ⚠ 而 `gMainThread` 的存在说明：**引擎有意把回调约束在主线程**（那是 API 语义，不是没做）。

## 二、⭐⭐ 而两个队友**主动选择了"不并行"** —— 理由是逐位确定性

`task-18`（工业仿真）的 `sparse.hpp:26`：
```
//  （与 task-7 神经模拟里踩过的同一条纪律：**并行/遍历顺序不得影响浮点求和**）
```
`task-19`（AI 地基）的 `autograd.hpp:47` / `nn.hpp:35`：
```
//   ⚠ 反向里**不做任何并行归约** —— 浮点归约次序一变，结果就不逐位相同了。
//   ⚠ **不做并行**：浮点加法次序一变，"同种子逐位相同"就没了。
```

⇒ ⭐⭐ **这不是"忘了并行"，是一个明确的取舍**：
```
**浮点归约的次序一变 ⇒ 结果不再逐位相同**
⇒ 而"同种子逐位相同"是本仓铁律（多处判据依赖它：
   `neural_brain --selfcheck` · `ai_train` 的 C1 · `_engine_fingerprint` · `diff_python` 75/75）
⇒ ⇒ **在这套引擎里，"多核并行"和"逐位确定性"是冲突的。**
```

## 三、⇒ 「核心调度」这一栏的真实答案（三引擎）

| 引擎 | 渲染 | 游戏/仿真循环 | 并行能力 | 原因 |
|---|---|---|---|---|
| **专业版 HybridEngine** | ✅ 有 GPU（D3D11） | **单线程** | 仅 **AI 助手** 用线程（非计算） | 回调约束在主线程；浮点确定性 |
| **轻量版 LearningCore** | C++ 软光栅（**单线程行扫描**） | 单线程 | **零**（`std::thread`/atomic/omp **全 0**） | Python GIL **+** C++ 侧根本没写并行 |
| **次旗舰 SampleCore** | 同 LearningCore | 单线程 | 零 | 它是 LearningCore 的副本 |

⇒ ⭐ **结论：三个引擎在 CPU 上都是单线程的（专业版仅 AI 助手例外）。**
```
⚠ 所以"核心调度"能报的不是"专业版吃了 24 核"，而是：
   · 24 核里**实际只用了 1 个**（对渲染/仿真路径）
   · 而**不用多核是一个有理由的取舍**（逐位确定性），不是疏忽
```

## 四、⇒ 那"能效"这一栏怎么报（**口径要说清**）

```
❌ 不能说"能效低" —— 单线程不是浪费，是**为了确定性付的代价**
✅ 应该说清三件事：
   ① 每个引擎在**单核**上的吞吐（那个我有：GPU 侧 3.07e7 三角形/秒 · 提交 ~2.18 µs/个）
   ② **多核用不上**（原因：浮点确定性 / 回调主线程约束 / GIL）
   ③ ⭐ 若想用多核，**要先解决"并行归约的确定性"**（例如：按固定块序归约、
      或每线程独立缓冲再按固定次序合并）—— 那是**一个可以做的设计**，不是不可能
```

⚠ 而 ③ **正好和 `task-17`（给轻量版 C++ 光栅化器加并行）撞上**：
  光栅化的填充是**逐像素独立写**（没有归约）⇒ **并行是安全的**（我正在让它先取基线）
  ⇒ ⭐ **所以"并行"这件事：光栅化能做，归约类不能做（除非有确定性方案）** —— 界线很清楚。
