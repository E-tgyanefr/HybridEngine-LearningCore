## 一、⭐ 回读的净代价：**0.812 ms/帧（轻）→ 1.137 ms/帧（重）**

1280×720 = 921,600 像素 = **3.52 MB/帧**

### 轻负载（1 个立方体 · 60 帧/档）

```
① 不回读 + 呈现（我上一份的口径）        0.0676 ms/帧
② 回读 + 不呈现                          0.8013 ms/帧
③ 回读 + 呈现（**引擎的真实路径**）       0.8795 ms/帧
⇒ 回读净代价 ≈ **0.812 ms** · 占 60fps 预算 **4.9%** · 10 分钟视频光回读 **29.2 秒**
⇒ 有效回读带宽 ≈ 3.52 MB ÷ 0.812 ms ≈ **4.3 GB/s**
```

### 重负载（2000 个立方体 · 40 帧/档）

```
① 4.4721 · ② 5.7604 · ③ 5.6090
⇒ 回读净代价 ≈ **1.137 ms** · 占 60fps 预算 **6.8%** · 10 分钟视频光回读 **40.9 秒**
```

### ⭐ 结论：**回读不是固定开销 —— 它随 GPU 负载放大**（0.812 → 1.137，涨了 40%）

```
为什么：**回读必须等 GPU 把这一帧画完** ⇒ GPU 越忙，CPU 在 Map 上等得越久
⇒ ⚠ 所以"回读只占 5%"这个说法**只在轻负载下成立**
```

⚠ **而我这次重负载的测法有缺陷（必须记）**：
```
2000 个立方体**用的是同一个世界矩阵**（全部叠在一起）
⇒ **像素覆盖没变** ⇒ 那是"**提交重**"、不是"**光栅化重**"
⇒ ⇒ **"回读随负载涨"这条只在【提交负载】下验过；【光栅化负载】下未验。**
```

## 二、⇒ 「10 分钟视频 · 大量 3D 模型」的**修正后可行性**

把两份数合起来（都含引擎的真实路径 = 有回读）：

| 每帧模型数 | 不含回读 | **含回读（引擎真实）** | 60 fps? | **10 分钟视频墙钟** |
|---|---|---|---|---|
| 512 | 1.00 | ~1.8 | ✅ | ~1 分钟 |
| **2,048** | 4.47 | **~5.6** | ✅ | **~3.4 分钟** |
| 8,192 | 18.35 | ~19.5 | ❌ | ~11.7 分钟 |

⇒ ⭐ **修正后的回答：每帧 ≤ ~2,000 个模型 ⇒ 10 分钟视频约 3.4 分钟渲染完**（60 fps 内）
  ⚠ 比我上一轮说的 2.7 分钟**多了 ~26%** —— **那 26% 就是回读**。

## 三、⚠⚠ 而这份"可行性"有**四个未验的边界**（别把它当成产品承诺）

```
① **模型很小**：每模型 12 个三角形（MakeCube）。真模型几百~几万三角形
   ⇒ ⚠ 若模型大，瓶颈从"提交次数"转回"三角形吞吐" ⇒ 本份**没覆盖**
② **模型全叠在一起**（重负载那档）⇒ **像素覆盖没变** ⇒ **光栅化负载没压到**
   ⇒ ⚠ 真场景 2000 个**不重叠**模型的填充量 = 本份的多少倍，**没测**
③ **`--rebuild`（每帧重建顶点缓冲 / 蒙皮变形）没跑**（开关写了）
④ **单次测量，无中位数** · 单分辨率 · 无纹理 · 无透明混合
```

## 四、⇒ 优化优先级**被这份数改了**

```
❌ 我上一轮建议"做 instancing"（推算 5.6 倍）—— ⚠ **那个推算的前提错了**：
   它按"合成一次 draw call ⇒ 0.8 ms/帧"算，但**没算回读**，也没算填充量
   ⇒ ⭐ 而本份实测：2,048 个模型 5.6 ms/帧里，
     **回读只占 1.14 ms（20%）** ⇒ 剩下 4.47 ms 才是提交+光栅化
   ⇒ **省掉全部回读 ⇒ 最多快 20%**（不是 5.6 倍）
   ⇒ **而省掉 2,048 次 Submit（instancing）⇒ 可能省掉那 4.47 ms 的大部分** ⇒ **仍是最值得做的**

⭐ 结论：**instancing 依然值得做**（它是那 80% 里的主要成分），
   但**收益不是 5.6 倍**，而是"把 5.6 降到 ~1.5~2"这个量级 —— ⚠ **且这仍是推算**。
```
