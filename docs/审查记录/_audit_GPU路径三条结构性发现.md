# ⭐ GPU 路径的三条结构性发现（2026-10-14 · Round 11）

> 这一轮我做的是**把"我的探针是否代表真路径"这件事查实**。
> 结论：**代表**，而且顺手查出**三个可以优化的真实结构问题**。
> 全部有代码行号或实测数字支撑。

---

## 一、✅ 确认：引擎**也是"每网格一次 Submit"** ⇒ 我的探针有代表性

```cpp
// src/app/engine.cpp:298  void RenderSceneGpu(...)
gpu.SetCamera(d.cam, aspect);
for (const auto& m : d.meshes) gpu.Submit(*m.mesh, m.world, m.tint, m.tex);   // ← 一行一网格
```

⇒ ⭐ **所以 `video_render.cpp` 那份"每模型一次 Submit"的数，代表引擎的真实行为。**
  ⚠ 前面我一度担心"探针可能测了引擎不走的路" —— 这一条**排除了**。

---

## 二、⚠⚠ 发现①：**GPU 路径没有网格级视锥剔除**（软渲有）

```
软渲路径： engine.cpp:255   `o.cullMeshes = true;   // M5：网格级视锥剔除（性能——可见像素不变）`
GPU 路径： `GpuRenderer::Options` 里**没有 `cullMeshes` 字段**
           `gpu_renderer.cpp` 里 **`frustum` / 视锥 / `Bounds(` 零命中**
```
⇒ ⚠ **软渲会剔掉视野外的网格；GPU 路不剔 —— 每个都 Submit。**

**影响**：对一个"有大量模型、且很多在视野外"的场景（开放世界 / 大场景）：
```
GPU 路会**白白付掉所有视野外模型的提交开销**（~2.18 µs/个，见第三节）
⇒ 而软渲那条路**已经证明"可见像素不变"**（注释原话）⇒ 说明这个剔除是安全的
⇒ ⭐ **把 `cullMeshes` 搬给 GPU 路是一个"有先例、低风险"的优化**
```

⚠ **而我的探针没覆盖这个**（模型全在视野内）⇒ **那份数对"有大片视野外模型"的场景偏乐观**。

---

## 三、⚠⚠ 发现②：**每个 `Submit` 都重新上传顶点缓冲**（静态网格也一样）

我加了 `--rebuild`（每帧重建顶点缓冲 = 蒙皮/变形）开关，然后**跑了两组**：

| 模型数 | 静态（只换世界矩阵） | `--rebuild`（每帧重建顶点缓冲） |
|---|---|---|
| 1 | 0.0861 | 0.0883 |
| 64 | 0.1427 | 0.1609 |
| 512 | 1.0036 | 1.0460 |
| **2,048** | **4.4704** | **4.4007** |
| 8,192 | 18.3070 | 17.6990 |
| 32,768 | 73.6187 | 70.8507 |

⇒ ⭐ **逐档都在噪声内（rebuild 甚至略快）**
⇒ **说明 `Submit` 每次都在把顶点缓冲传到 GPU** ——
  **静态网格与重建网格付一样的钱**（因为 `Submit` 不区分"这个网格我传过了"）。
⇒ ⭐⭐ **这就是那个 ~2.18 µs/Submit 的主要成分**（不是 draw call 本身，而是**重复上传**）。

**⇒ 可优化的方向（真正省钱的）**：
```
① **instancing**：一个网格 + N 个世界矩阵 ⇒ 一次上传 + 一次 draw call
② **网格缓冲缓存**：`Submit` 里认出"同一个网格对象、上次传过" ⇒ 跳过重传
   ⚠ 但要注意"顶点真的变了"的情况（蒙皮）⇒ 需要一个"版本号/脏标记"
```
⚠ 而 **② 更保守**（不改接口语义），**① 更彻底**（但要加接口）。
  ⚠ 两者我都**没做** —— 那是**改引擎**，我要先问作者。

## 四、⚠⚠ 发现③：回读**随 GPU 负载放大**（Round 10 已记，这里合起来看）

```
轻负载（1 立方体）    回读净代价 **0.812 ms/帧**（预算 4.9%）
重负载（2000 立方体） 回读净代价 **1.137 ms/帧**（预算 6.8%）
⇒ 涨 40% —— 因为**回读必须等 GPU 画完**，GPU 越忙、CPU 等得越久
```
⚠ 而那次重负载是"提交重"（同一世界矩阵全叠在一起）⇒ **光栅化负载下未验。**

## 五、⇒ 三条优化按"值不值得做"排序（都有实测支撑）

| # | 优化 | 依据 | 收益（估算，**未实测**） |
|---|---|---|---|
| **1** | **网格缓冲缓存 / instancing** | 发现②：静态与 rebuild 无差别 ⇒ **每次 Submit 都在重传** | ⭐ **最大** —— 2,048 个模型 4.47 ms 里绝大部分是它 |
| **2** | **GPU 路的网格级视锥剔除** | 发现①：软渲有、GPU 没有 | 对"多视野外模型"场景**线性省**；视野内场景=0 |
| **3** | HUD 走 GPU ⇒ 省掉回读 | 发现③：回读 0.81~1.14 ms/帧 | **~20%**（省掉全部回读） |

⚠ **三者都是"改引擎"** ⇒ 我**没动**。而且**优先级应由作者定** ——
  因为 ① 和 ② 会改渲染语义（剔除=可能改变边界像素；缓存=需要脏标记），
  **不是纯性能改动**。

## 七、⚠ 我这轮的两个失误（都记）

1. **`--rebuild` 的测法有缺陷**：我在**探针里改的是副本**（`Render3D::MeshData 动 = 库[i]`），
   而静态那档传的是**同一个 `库[i]` 引用** ⇒ ⚠ **理论上两者的输入不同**，
   但因为 `Submit` **每次都重传** ⇒ **差别被掩盖了** ⇒ 所以"两者无差别"这个结论
   **可能是"上传开销淹没了一切"，而不是"顶点数不影响"** ⇒ **要更谨慎地说**。
2. **我把 `--rebuild` 说成"验蒙皮代价"** —— ⚠ 严格说它验的是"**每帧换一份顶点数据**"，
   蒙皮还要加上**计算**骨架/形变本身的开销 ⇒ **那部分本份没含**。
