# ⭐ 核心调度归因：`Submit` 触发 D3D11 内部并行（2026-10-14 · Round 15）

> 接 Round 14：`cpu_share` 实测**等效核数 = 1.247**（不是 1.000），而代码里
> `std::thread` 只在 AI 助手 ⇒ **那 0.247 个核是谁在用？** 这一份是**对照实验**的答案。
> 复现：`C:\gs_link\core_attrib.cpp`（四档对照）

## 一、⭐ 四档对照（2048 模型 · 200 帧 · 逻辑核 24）

| 档 | 做什么 | 墙钟 s | **进程 CPU s** | **等效核数** | ms/帧 |
|---|---|---|---|---|---|
| **A** | **纯 CPU 循环**（不碰 GPU，预存矩阵） | 0.0008 | 0.0000 | **0.000** | 0.0040 |
| **B** | 只 `Begin/SetCamera/End/Composite`（**不 Submit**） | 0.0149 | 0.0156 | **1.050** | 0.0744 |
| **C** | 只 `Submit` ×2048（**不 End、不呈现**） | 0.8920 | 1.0781 | **1.209** | 4.4598 |
| **D** | 完整一帧（`Submit`+`End`+`Composite`） | 0.8793 | 1.1250 | **1.279** | 4.3966 |

⚠ 口径：**进程 CPU 时间 ÷ 墙钟**（`GetProcessTimes`）—— 比逐核占用曲线更硬，
  不受采样频率影响。四档**都读这个数**，可直接横比。

## 二、⭐ 归因

```
B（呈现那条路）  = **1.050**  ⇒ 几乎纯单线程（只多 5%）
C（提交那条路）  = **1.209**  ⇒ ⭐ **多余的核心全在这里**
D（完整帧）      = **1.279**  ≈ C + B 的叠加
```

⚠ 而 **C 档我只调 `Submit`** —— 那是 CPU 侧的顶点/常量缓冲操作，**代码里我自己没起线程**
⇒ **那 0.209 个核是 D3D11 运行时/驱动的内部工作线程**（或内核态消耗）

**换算**：
```
D 档：多出的 0.279 核 × 0.8793 s = **0.245 s** ÷ 200 帧 = **每帧 ~1.23 ms 花在别的线程上**
C 档：多出的 0.209 核 × 0.8920 s = 0.186 s ÷ 200 帧 = 每帧 ~0.93 ms
```

---

## 三、⚠⚠ 这**改变了优化的性质**（重要）

```
本来的想法：Submit 是"CPU 调用开销" ⇒ 减少调用次数（instancing/合批）就能省
⭐ 实测告诉我们：**其中一部分开销根本不在你这条线程上** —— 它是 D3D11 内部的并行工作
⇒ ⚠ 所以"减少 Submit 次数"只能省**主线程**那部分（C 档墙钟 0.892 s 里 CPU 1.078 s
   ⇒ 主线程约占 0.892/1.078 = 83%，其余 17% 在别的线程）
```

**⇒ 对"该不该做 instancing"这个问题的修正**：
```
✅ 仍值得做（主线程那 83% 里的大部分是它可以省的）
⚠ 但"省下的比例"不能按"墙钟 4.46 ms 全归主线程"来算
   ⇒ 估收益时要**用墙钟**（4.46 ms/帧），而不是"CPU 时间"（因为并行部分不会被省掉）
```

## 四、⚠ 我这一轮的两个测量缺陷（都记）

1. **A 档 `等效核数 = 0.000` 是测量问题**：
   `CPU 0.0000 s` **不是"CPU 不花时间"**，而是**循环太快（0.004 ms/帧）**，
   低于 `GetProcessTimes` 的分辨率（~15.6 ms 或更细，取决于系统计时器）
   ⇒ ⚠ **它只能说明"这档的量级远小于其他档"，不能说明它的绝对核数**。
2. **没做逐核占用曲线** —— 所以"多余核来自驱动线程"是**从"代码里没有我的线程"推出的**，
   ⚠ **不是直接观测到某个具体线程**。⇒ 要坐实得抓线程列表（`CreateToolhelp32Snapshot`）或 ETW，
   **我没做** ⇒ 如实记为**推断，非观测**。
