# ⭐ 「三引擎性能到理论极限」—— 可验证的账（2026-10-14 · Round 21）

> 目标原话：「**同时继续优化三引擎性能，直到理论极限**」。
> ⚠ **"理论极限"这句话本身不可验证** —— 除非把它换成**一组具体的、可测的上界**。
> 这一份就是那本账：**每个引擎的当前数 · 上界 · 差距 · 差距的成因**。
> ⚠ 所有数都来自本会话的实测（出处标在每行），**推算的标"推算"**。

---

## 一、⭐ 专业版（GPU 渲染）—— **上界已被测到，差距 = 5.7 倍**

| 项 | 数 | 出处 |
|---|---|---|
| **单网格饱和吞吐** | **≈2.9~3.1×10⁷ 三角形/秒** | `tools/bench3/bench_gpu.cpp`（队友复现我的探针，峰值 2.6~3.0e7） |
| **多模型场景（每模型一次 Submit）** | **≈5,400 三角形/ms** ⇒ **比单网格低 5.7 倍** | `video_render.cpp`（1280×720，2048 模型 ⇒ 4.47 ms/帧） |
| **每次 Submit 的固定开销** | **≈2.18 µs**（4.4705 ms ÷ 2048） | 同上 |
| 空载帧底 | **0.0510~0.0594 ms/帧** | 队友的 `N=0` 档（⚠ 我原来没有这一档，是它补的） |
| 回读代价 | **0.812 ms（轻）→ 1.137 ms（重）** | `readback_cost.cpp`（⚠ 随 GPU 负载放大 40%） |
| 回读带宽 | ≈ **4.3 GB/s**（3.52 MB/帧） | 同上 |

### ⇒ 差距在哪（**三条结构性发现，全部读代码查实**）

```
① ⚠ **GPU 路没有网格级视锥剔除**（软渲有：`engine.cpp:255` `o.cullMeshes = true;` "可见像素不变"）
   ⇒ 视野外的网格**也走完整条 Submit**（逐顶点变换 + 缓冲上传）
② ⚠ **每个 `Submit` 都重新上传顶点缓冲** —— 实测依据：静态网格 vs 每帧重建顶点，**逐档无差别**
   ⇒ 那 ~2.18 µs/Submit 的**主成分是重复上传**，不是 draw call 本身
③ 回读**必须等 GPU 画完** ⇒ GPU 越忙、CPU 等得越久（所以它随负载放大）
```

### ⇒ 理论上界（**推算，不是实测**）

```
若把 2048 次 Submit 合成 1 次（instancing，三角形数不变 24,576）：
   按单网格饱和吞吐 30,697 三角形/ms ⇒ **0.8 ms/帧**（现在 4.47）⇒ **≈5.6 倍**
⚠ 而这是**推算**；要做实必须先加 instancing 接口（**改渲染语义，等作者拍**）
```

### ⇒ 另外两个上界

```
· **回读**：省掉它最多快 **~20%**（2,048 模型 5.6 ms 里回读占 1.14 ms）
  —— 而"省掉"需要 HUD 也走 GPU（`gpu2d_renderer_win32.cpp` **已存在**，37,505 B）
  ⚠ 但 `engine.cpp:578` 注释说"窗口面可以走 D3D11" —— **而 838 行那条路还在回读**
    ⇒ ⭐ **这两件事为什么并存，我没查清** ⇒ 记为待查（可能是历史遗留，也可能是别的原因）
· **帧底 0.05 ms**：1280×720 下的固定开销（清屏+呈现）⇒ 小负载场景的**硬地板**
```

## 二、⭐ 轻量版（CPU 软件光栅）—— **上界已测到，且"目标场景并行不赚"已证明**

| 项 | 数 | 出处 |
|---|---|---|
| 目标场景（1000 个 r=9 圆 · 800×450） | 串行 **0.1098** → 并行 **0.1092** ⇒ **1.005x · 0 派发** | `task-17`（队友，我独立复核） |
| 大图元（1920×1080 + r=600 大圆） | 串行 0.4187 → 并行 **0.2670** ⇒ **1.568x**（等效核数 1.000 → **6.5~7.8**） | 同上 |
| **逐位相同（主判据）** | **12 例扫描 0 处不一致**（3 例真走并行） | 同上 |
| Tk 后端（同场景，接入后） | **15.5 ms/帧**（1000 个可见 item） | `_cmp_two_backends.py` |
| C++ 后端（接入后） | **2.08 ms/帧** ⇒ **7.2~7.7 倍** | 同上（五次测量 7.2/7.3/7.5/7.6/7.7） |

### ⇒ 差距的成因（**一句可复用的规律**）

```
⭐ **「检查本身比被检查的事还贵」** —— 队友三代栽在同一句话上，且留了数：
   门槛放低 ⇒ **慢 5.2 倍** · 每图元读 `hardware_concurrency()` ⇒ **慢 4.6 倍（一个线程都没起）**
   · 缓存成原子读 ⇒ 慢 16% · 包进模板函子 ⇒ 慢 11%
   ⇒ 最终把**判断放调用方**（先比行数，编译期常量）⇒ **1.005x · 0 派发**
⇒ ⭐ 所以这个引擎的"上界"**不是一个倍数，而是一条条件**：
   **只有当单个图元的填充量足够大（>1M 像素）时，并行才赚**
```

### ⇒ 还没做的（**已判定"不该做"或"要改语义"**）

```
❌ 跨图元并行 —— **要动 z 序语义** ⇒ 判为不做（队友自己就"倾向不做"）
❌ 目标场景提速 —— **物理上不赚**（整帧 ~110 µs，每个圆 ~110 **ns**，一次派发是微秒级）
⇒ ⭐ **"目标场景的极限 = 0.11 ms/帧"** —— 而那已经是串行数了
```

## 四、⚠ 「核心调度」的账（目标点名要看）

```
口径：**进程 CPU 时间 ÷ 墙钟 = 等效核数**（比逐核曲线硬，不受采样频率影响）
⭐ 但**只有窗口 ≥1 s 才可信** —— 我踩过：模型 8·200 帧报 **0.000**、模型 64·200 帧报 **0.487**
   （墙钟 0.013~0.032 s，低于 `GetProcessTimes` 分辨率）**而两个数都不报错**

三引擎（队友的全表）：**0.87 ~ 1.34** ⇒ **都只用到 ≈1 个核**
专业版四档归因（我）：呈现 1.050 · 提交 1.209 · 完整帧 1.279 · 纯 CPU 0.000（测量问题）
逐档（队友）：N=0 **1.130** · 2048 **1.344** · 262144 **1.012**
⇒ ⭐ **多出的部分来自 D3D11 内部（present / swap chain / 提交路径），与画多少无关或在中档最大**
   —— **不是可被应用利用的并行**
⇒ ⭐ **真差距不是"有没有并行"，是"有没有 GPU 通路"**（专业版有；另两个**没有**）
```

## 五、⇒ 这本账的一句话总结

| 引擎 | 当前 | 已证上界 | 差距 | 差距能不能消 |
|---|---|---|---|---|
| **专业版** | 多模型 5,400 三角形/ms | 单网格 **30,697 三角形/ms** | **5.7 倍** | ⚠ **能，但要加 instancing（改语义，等拍板）** |
| **轻量版** | 目标场景 0.11 ms/帧（**已达极限**） | 同 | **0** | ✅ **已到**（并行在那形态下不赚，已证明） |
| **轻量版（大图元）** | 1.568x（并行后） | ⚠ 未测更大 | ? | 待测 4K |
| **次旗舰** | = 轻量版 | = 轻量版 | **定位未分化** | 需产品决定（`task-14`） |

⚠ **所以"直到理论极限"这条：**
  **轻量版在目标场景上已经到了**（0.11 ms/帧，且证明了并行不赚）；
  **专业版还差 5.7 倍，而差距已定位到"每次 Submit 重传顶点缓冲"** ——
  **消它需要 instancing（改渲染语义），我没有擅自做。**
