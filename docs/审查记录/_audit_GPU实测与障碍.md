# GPU 渲染压力测试：**实测实证 + 障碍链**（2026-10-14 · Round 6~7）

> 目标里有一条：「结束后三引擎统一进行 **GPU**，CPU 渲染压力测试，看能效与核心调度」。
> 这一份是 **Lead 自己去跑、去读、去链**的结果 —— 不是转述任何人的报告。
> ⚠ **结论有好有坏**，而且**大部分障碍是我自己踩出来的**，一并记下。

---

## 一、✅ 实证①：**GPU 渲染通路真的能用**（端到端）

```
build-ninja-release\tools\gpu_test.exe --save frame.bmp --vsync off   ⇒ 退出码 0
  gpu ok 640x400 · saved frame.bmp 640x400 · gpu_test done frames=600
```

**画面是真的**（全像素扫描 256,000 像素，不是采样）：
```
2 种颜色：RGB(18,10,8) 背景 79.6% · RGB(23,24,9) 立方体 20.4%
立方体包围盒 **234×240 像素** · 每行像素数纵向抽样 208→212→216→220→224→228→230→230→174
⇒ 恒定宽度 + 突然收口 = **标准立方体轮廓**
```
⚠ **我第一版判据写错了**：它说"只有 2 种颜色 ⇒ 纯色 ⇒ 可能没画出来"。
  **纯色立方体 + 纯色背景本来就该是 2 色** —— 该查的是**几何形状**，不是"颜色数"。
  ⇒ 又一条「**判据错了，不是被测物错了**」。

## 二、⚠ 障碍②：仓里 `gpu_test.exe` 的**吞吐数不能用**

`tools/gpu_test.cpp` 主循环里有 `sleep_for(16ms)`：
```
实测 600 帧 17.3 s = 28.9 ms/帧，**其中 16 ms 是 sleep** ⇒ 真正干活 ~13 ms/帧
⇒ 拿它当 GPU 吞吐**会错一倍以上**
vsync off/off/on 三次 = 34.6 / 32.9 / 32.8 帧每秒 ⇒ **这个口径下 vsync 没区别**（sleep 已压到 60 以下）
```
⇒ ⚠ **要真吞吐必须去掉限速。** 而**它已经不是一个 CMake 目标了**
  （`tools/CMakeLists.txt` 只有 `ms_ctl`；那个 exe 是**历史构建残留**）
  ⇒ 我给它加的 `--nosleep` + 计时（**纯追加、默认行为不变**）**编不出来** —— **我改的那份没进构建**。

## 三、⚠ 障碍③：**那个 dll 只导出 C ABI** —— 链 C++ 必须用静态库

我依次排除了三层，最后定位到真因：

### 层 1（错的结论）：我以为是"另一个编译器"
```
可疑：MinGW 链 ⇒ ~15 个 C++ mangled 符号 undefined reference，而 C 符号（ms_*）能链
```
### 层 2（也是错的）：我以为 `nm` 读不到导出表 ⇒ 以为是别的 ABI
```
`nm --defined-only <含中文路径>\libhybridengine.dll.a` ⇒ **输出为空**
```
### 层 3（⭐ 真因，两个一起）：
```
① ⚠ **MinGW 的 ar / nm 处理不了中文路径** —— 拷到 ASCII 路径后立刻能读：
   `ar t` 在中文路径报 "No such file or directory: D:\...\����\HybridEngine\..."
   ⇒ **不是符号缺失，是路径编码坏了**（本仓那条老坑的又一个变种）
   拷到 C:\symcheck 后：rel.dll.a **2550 个符号** · old.dll.a **1398 个**

② ⭐ **那个 dll 里一个 C++ 符号都没有**：
   `GpuRenderer` 0 命中 · `_ZN12HybridEngine` 0 命中 · `CreateWindow` 0 命中
   ⇒ **它只导出 C ABI（`ms_*`）** —— 完全符合设计（`ms_bind.h` 是给外部用的唯一接口）
   ⇒ ⚠ **所以拿它链 C++ 类永远链不上** —— 不是 ABI 问题，是**它不对外导出 C++**
```

**顺便验了一个有用的**：旧的 `build\release` 导入库确实缺 `ms_save_set_path`
（新库有、旧库没有）⇒ Round 20 那个 `undefined reference` 是**真的引错了库**，**代码没问题**。

### ⇒ 正确的路：**静态库**
```
build-ninja-release/src/ 下有完整静态库：
  render3d  1,281,040 B   ← GpuRenderer 在这
  platform  1,556,782 B   ← CreateWindow 在这
  core      2,986,066 B
  animation · app · bind · collision · editor · plugin · render2d · rhythm · uikit
```
⚠ **我用它们重链了一次，仍然失败**，但**链接器输出我读不出来**（PowerShell 把它截没了）。
  ⇒ **没验完**，如实记：**"静态库能链通 C++"这条我还没证明。**

## 四、⚠ 障碍④：**没有无窗 GPU 通路**

```
`GpuRenderer::Init` **硬性要求窗口句柄**（要建 DXGI swap chain）
⇒ 没有 compute shader / 离屏 target / buffer 计算通路
⇒ ⚠ **"AI 训练用 GPU"目前无路可走**（要新写）
⇒ 而 `WindowDesc` 有"建窗口但不显示"的选项（注释写着"自动化测试无人值守跑 GPU 覆盖"）—— **可用**
```

## 七、⭐ 这一轮最值钱的一条（元教训）

**我连着下了三个错结论才找到真因**：

| # | 我的结论 | 真相 |
|---|---|---|
| 1 | "另一个编译器，ABI 不兼容" | 是**同一个** MinGW（`CMakeCache` 里的路径与我的一模一样） |
| 2 | "`nm` 读不到导出表" | **MinGW 工具处理不了中文路径** ⇒ 换 ASCII 立刻能读 |
| 3 | "库是坏的/代码有问题" | **dll 只导出 C ABI** ⇒ 链 C++ 本来就该用静态库 |

⇒ ⭐ **三次都是我拿"看起来合理的解释"当结论，而没去把证据读到底。**
  ⚠ 而本仓的规矩本来就是：**证据没读到，就说"没验到"** —— 我这次是**先说了结论**。
