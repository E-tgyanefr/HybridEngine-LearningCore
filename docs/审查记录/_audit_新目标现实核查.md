# 现实核查：新目标（2026-10-14 · Round 1）

> **新目标**：
> 「把专业版功能所有功能补齐成为真正的混合引擎，可以进行所有工业模拟，所有商业操作，
>   以及 ai 训练等大任务，同时继续优化三引擎性能，直到理论极限，结束后三引擎统一进行
>   GPU，CPU 渲染压力测试，看能效与核心调度」
>
> ⚠ 这一份是**开工前的现实核查** —— 而不是先动手。

## 二·补、⚠⚠ 我自己写错过一条：**轻量版底层也是 C++**

⚠ 作者点了我一句：「**轻量版也是 C++ 底层啊**」—— **他是对的**，我第一版写成"纯 CPU + tkinter"，
**不准确**。重新量的准确数据：

```
轻量版语言构成：C/C++ **10 个文件 · 2,320 行** · Python 44 个文件 · 13,742 行
   native/hblight/hblight.h 14,322 B · hblight.cpp 33,209 B
   native/hblight/raster.cpp 6,243 B · window_win32.cpp 7,304 B
   hybridengine_light/pyengine_c/{__init__,backend}.py  ← ctypes 绑定
⇒ **Python 那层是绑定/胶水，计算在 C++ 里。**
```

### ⭐ 而它同时纠正了"核心调度"的预期结论

```
轻量版 C++ 侧的线程事实 —— **全部是 0**：
   std::thread 0 · pthread 0 · CreateThread 0 · _beginthreadex 0
   std::async 0 · omp parallel 0 · OpenMP 0 · hardware_concurrency 0 · mutex 0 · atomic 0
光栅化器内部：`for (int y = y0; y <= y1; ++y)` —— **单线程行扫描**
编译标志：只有 `/W4` / `-Wall -Wextra -Wpedantic` —— **零并行开关**
```

| 我第一版写的 | 实际的 |
|---|---|
| 「轻量版 GPU 命中 2 ⇒ 纯 CPU」 | ⚠ **不准** —— 它有 **C++ 光栅化器**，只是单线程、无 GPU |
| 「Python **GIL** ⇒ 吃不到多核」 | ⚠ **GIL 不是主要限制** —— **C++ 侧根本没有线程**才是。**即使解除 GIL，也只有一个核在跑** |

⇒ ⭐ **"核心调度"这条的真实结论：三个引擎的差距不是 GIL，是"有没有真的并行"。**
  ⇒ 而轻量版的填充是**逐行独立**的（`for y` 行扫描）⇒ **最容易正确并行化的形态**
  ⇒ **已派 `task-17`**（`blocked_by: task-16`，**先量基线再并行**）。

⚠ 所以「**继续优化三引擎性能，直到理论极限**」这条，**在轻量版上有非常具体的一件事**：
  **把 C++ 侧 24 核用起来**（现在用 1 个）。

## 三、⚠⚠ 一条**硬冲突**（作者已裁决：法律允许范围内放宽）

```
目标要：AI 训练（GPU 计算）+ 工业仿真（大规模数值）
铁律：  **零第三方依赖**（实测 CMakeLists 里 find_package / FetchContent = **0**，守得很干净）
```

⇒ **CUDA / cuBLAS / MKL / Eigen / PyTorch 一个都不能引** ⇒ 都得手写。
⇒ **这不是"难"，是天花板被锁死**：手写 GEMM 再好也比 cuBLAS 慢一个数量级。

**作者裁决**：「**可以在法律允许的范围内放宽**」
⇒ ⚠ 我把它实现为**许可证白名单**（**不是"随便引"**）—— 因为本仓是
  **PyInstaller 打包 + 公开 GitHub 发布**的发行物：

```
✅ 可引：MIT · BSD-2/3 · Apache-2.0 · Zlib · ISC · BSL-1.0 · public domain
❌ 禁引：GPL / AGPL / LGPL(静态链) / SSPL / 任何 "非商业" 条款
   ⇒ 静态链接 + 单一发行物 ⇒ copyleft 会**传染整个仓库**
   ⇒ 那不是"法律允许"，那是**把一个公开仓库变成 GPL**
✅ 系统 API（D3D11 / Vulkan / win32 / X11 / getrusage / PDH）**不算第三方库**，不受限
```

⚠ 而我要**先把预期结论说清**（免得大家以为发现了什么）：

```
专业版   C++ · 真线程 · 有 GPU 通路   ⇒ 能吃 24 核
轻量版   Python · **GIL** · tkinter    ⇒ **吃不到多核**
次旗舰   Python · **GIL**              ⇒ **吃不到多核**

⇒ "核心调度"这一项，预期结论就是「C++ 那条真并行，Python 那两条不能」——
  ⚠ 那是 **GIL 的语言事实，不是引擎写得差**。
  ⇒ 而这个对比**本身有价值**：它精确解释了"三个引擎的定位差异从哪来"。
```

⚠ 两条会被误读成 bug 的事，先写在这：
1. **`SampleCore` 与 `LearningCore` 逐字相同** ⇒ **它们的压力测试数会几乎一样**。
   **那不是 bug**，是**定位还没分化**（作者刚给 LearningCore 派了"负优化"，还没落地）。
2. **功耗大概率读不到**（笔记本 / 可能虚拟化）⇒ 若只能给"每帧 CPU 时间"而不是"每瓦"，
   **就照实写**。⚠ **编一个瓦数比"没有"更糟** —— 报告的数是给人当证据的。

## 五、⚠ 我对这个目标的诚实判断

**四件事里，只有 ⑥（压力测试）和 ⑤（性能）是"现状之上可推进"的。**
②③④ 是**从零建三个新领域**，而其中：

| 条目 | 真实的量级 |
|---|---|
| 工业模拟 | 一个**可用的** FEM/CFD 求解器 = 数千到数万行 + 数值验证基准。而"**所有**工业模拟"是没有边界的 |
| 商业操作 | **不是引擎功能**。账本/库存/排程是**应用层**，且需要业务规格（谁的账、什么税、什么合规） |
| AI 训练 | 张量库 + 自动微分 + 优化器 + GPU kernel。**"能训练"和"能训练大模型"差 3~4 个数量级** |

⇒ ⚠ **我不会假装这些能一次性做完。** 我会：
1. **把可验证的先做扎实**（压力测试 + 性能推极限）——**已开工**
2. 另外三块**先做骨架 + 一条端到端判据**（能跑通一个小例子），而不是铺开写
3. **每轮如实报"到哪了、没到哪"**

⚠ 而**"直到理论极限"这句话本身需要被量化** —— 否则它不可验证。
  我已经有一个具体的靶子（见 `docs/能效比-并排实测.md`）：
  **当前 7.2~7.7 倍 · 推算上限 ~140 倍 · 差距在"接口粒度"**
  ⇒ **把那 ~140 倍做实，就是"理论极限"的一个可验证定义。**
