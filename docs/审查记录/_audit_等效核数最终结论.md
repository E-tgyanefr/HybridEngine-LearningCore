## 二、⚠⚠ 我 Round 17 的读法是错的

我当时写：「**64 个模型 = 1.560 = 最高** ⇒ 多出的核是**每帧固定开销**……模型越多越被摊薄」
⇒ ⚠ **"被摊薄"这个说法对了，但"负载越高越多核"的直觉是错的** —— 而 `task-16` 的逐档表把它钉死了：

```
⭐ **N=0（什么都不画）就已经 1.130 核**
   ⇒ ⚠ 那部分**不是渲染工作产生的**，是 **present / swap chain 的固定底**
   ⇒ ⭐ 所以：**"多出的核"是一个【常量底】+ 一个【提交路径的增量】，而增量在中档最大**
```

**更准的三段式**：
```
① **固定底 ≈ 1.0~1.13 核**（present / swap chain / D3D11 内部）—— **与画多少无关**
   ⚠ 证据：N=0 就是 1.130；而我的"1 个模型"是 0.985（那一档只有一个 Submit，
     呈现路径的固定底还没被算进去，因为它太短 —— 见第三节的分辨率问题）
② **提交路径增量 ≈ +0.2 核**（多次 `Submit` 触发 D3D11 内部工作）—— **中档最大**（2048: 1.344）
③ **重负载回落 ≈ 1.01**（渲染工作主导 ⇒ 主线程占满 ⇒ 比值趋 1）
```

⇒ ⭐⭐ **所以"三引擎都只用到 ≈1 个核"这个结论成立**，而"偶尔 1.3~1.5"的部分
   **全部来自驱动/呈现路径，不是可被应用利用的并行。**

## 三、⚠ 而这一轮又一次证明：**尺子的分辨率**

```
① 短窗口 ⇒ 垃圾：模型 8·200 帧 报 **0.000**、模型 64·200 帧 报 **0.487**
   （墙钟 0.013~0.032 s，低于 GetProcessTimes 分辨率）—— **而它们看起来完全正常**
② `task-16` 的仪器要求间隔 >0.2 s ⇒ **`bench_backend.exe` 单次只跑 0.038 s ⇒ 采不到**
   ⇒ ⚠ 它会得到"**采不到**"而不是"**等于 1**"
   ⭐ 而它**主动提醒了我**这条（"量等效核数时必须把负载/帧数调大"）
③ 我 Round 17 那条"用长窗口"的规矩 ⇒ 现在**升级成**：
   ⭐ **"先确认尺子的分辨率，再确认被测量级；两者不匹配时，数会看起来正常但是错的"**
```

## 四、⇒ 归档：对目标里「看能效与核心调度」的**最终答案**

```
✅ **核心调度**：三引擎的渲染/仿真路径**都只用到 ≈1 个核**（0.87~1.34）
   而 >1 的部分**全来自 D3D11 内部（present / swap chain / 提交路径）**，**与负载无关或在中档最大**
   ⇒ ⭐ **不是"没有并行"，是"这些路径本来就不需要并行"**
   ⇒ 而真正的差距是 **有没有 GPU 通路**（专业版有；轻量版/次旗舰**没有**）
✅ **能效**：GPU 侧有（`nvidia-smi` 实测 24.5~32.6 W）· **CPU 侧功耗拿不到（不折算成瓦）**
✅ **GPU 吞吐**：饱和 **≈2.9~3.1×10⁷ 三角形/秒**；60 帧预算 ≈19 万三角形/帧
✅ **10 分钟视频**：每帧 ≤~2,000 模型 ⇒ 约 3.4 分钟渲染完（含 3.52 MB/帧 回读）
⚠ 缺：逐核曲线 · 具体线程身份（都要 ETW / 线程快照）· 另两个引擎没有 GPU 通路（结构性的，不是没测）
```
