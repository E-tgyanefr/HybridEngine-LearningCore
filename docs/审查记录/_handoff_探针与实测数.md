## 二、⭐ `video_render.cpp` —— 「10 分钟视频 · 大量 3D 模型」

**作者的澄清**：「渲染任务大概是渲染一个**大量 3d 模型的 10 分钟视频**就行」
⇒ 60 fps × 10 分钟 = **36,000 帧**；"大量模型" = **每帧 N 个对象、N 次 `Submit`**

**实测（1280×720 · 每帧换世界矩阵 · 40 帧/档 · 预热 5）**：

| 模型数 | ms/帧 | 帧/秒 | 三角形/帧 | 10 分钟视频墙钟 |
|---|---|---|---|---|
| 512 | 1.0011 | 999 | 6,144 | 36 秒 |
| **2,048** | **4.4705** | 224 | 24,576 | **2.7 分钟** |
| 8,192 | 18.3517 | 55 | 98,304 | 11 分钟 |
| 32,768 | 72.9134 | 14 | 393,216 | 44 分钟 |

**⭐ 最重要的发现（口径级）**：
```
"每帧三角形数 ÷ ms" 在两种场景下差 **5.7 倍**，且不随负载缩小：
   多模型：约 **5,400 三角形/ms**（与模型数几乎无关 —— **线性**）
   单大网格：**30,697 三角形/ms**
⇒ 那 5.7 倍 = **每次 Submit 的固定开销**（4.4705 ms ÷ 2048 ≈ **2.18 µs/模型**）
⇒ ⚠ **"三角形/秒"这个指标在"多模型"场景下会给出乐观 5.7 倍的错觉**
   ⇒ **报性能必须同时说清"几个 draw call"**
```

**`--rebuild`（每帧重建顶点缓冲）实测：与静态【无差别】**（逐档在噪声内）
⇒ ⭐ **说明 `Submit` 每次都重新上传顶点缓冲** —— 静态网格与重建网格付一样的钱
⚠ **这个结论要谨慎**：无差别**也可能**是"上传开销淹没了一切"，不是"顶点数不影响"
⚠ 而且它验的是"**每帧换一份顶点数据**"，**蒙皮的计算开销没含**

## 三、⭐ `readback_cost.cpp` —— 回读代价（**引擎每帧都在做**）

`src/app/engine.cpp:838` 的真实路径：
```
GPU 渲染场景 → **ReadbackFrame（像素读回内存）** → 软渲 BlitRect → HUD 叠加 → Present
```
⚠ 而 `video_render.cpp` 用的是 `gpu.Composite()`（**直接 Present，跳过了回读**）

| | ① 不回读 | ② 回读+不呈现 | ③ **回读+呈现（引擎路径）** | **回读净代价** |
|---|---|---|---|---|
| 轻负载（1 立方体） | 0.0676 | 0.8013 | 0.8795 | **0.812 ms**（预算 4.9%） |
| 重负载（2000 立方体） | 4.4721 | 5.7604 | 5.6090 | **1.137 ms**（预算 6.8%） |

```
⇒ 有效回读带宽 ≈ 3.52 MB ÷ 0.812 ms ≈ **4.3 GB/s**
⭐ **回读不是固定开销 —— 它随 GPU 负载放大**（涨 40%）
   因为**回读必须等 GPU 把这一帧画完** ⇒ GPU 越忙、CPU 在 Map 上等得越久
⚠ 而我那次"重负载"**用的同一个世界矩阵（全叠在一起）** ⇒ 那是"**提交重**"不是"**光栅化重**"
   ⇒ **"回读随负载涨"只在提交负载下验过；光栅化负载下未验**
```

## 四、⭐ `cpu_share.cpp` + `core_attrib.cpp` —— 「核心调度」

**口径：进程 CPU 时间 ÷ 墙钟 = 等效核数**（`GetProcessTimes`；比逐核曲线更硬，不受采样频率影响）

```
cpu_share：2048 模型 200 帧 · 逻辑核 24
   墙钟 0.8768 s · 进程 CPU 1.0938 s ⇒ **等效核数 = 1.247**  （1.00 = 严格单线程）

core_attrib（四档归因）：
   A 纯 CPU 循环（不碰 GPU）            等效核数 **0.000** ⚠ 见下
   B 只 Begin/SetCamera/End/Composite  等效核数 **1.050**
   C 只 Submit ×2048（不 End 不呈现）    等效核数 **1.209**   ← ⭐ **多余的全在这**
   D 完整一帧                           等效核数 **1.279**
⇒ 归因：**多余的核心来自 Submit 那条路** —— 而代码里 `std::thread` 只在 AI 助手
⇒ ⭐ 那 0.209 个核是 **D3D11 运行时/驱动的内部工作线程**
   换算：D 档多出的 0.279 核 × 0.8793 s = 0.245 s ÷ 200 帧 = **每帧 ~1.23 ms 在别的线程上**
```

⚠⚠ **这条改变了优化的性质**：
```
"减少 Submit 次数"只能省**主线程**那部分（主线程约占 0.892/1.078 = **83%**，其余 17% 在别的线程）
⇒ ⚠ **估 instancing 收益时不能用"CPU 时间"，要用【墙钟】上能省的那部分**
```

⚠ **两个测量缺陷（必须一起交接，别当成结论）**：
1. **A 档 `0.000` 是测量问题** —— 循环太快（0.004 ms/帧）低于 `GetProcessTimes` 分辨率
   ⇒ 只能说"量级远小于其他档"，**不能说它的绝对核数**
2. **没做逐核曲线** ⇒ "多余核来自驱动线程"是**推断**（从"代码里没有我的线程"），
   ⚠ **不是直接观测到某个具体线程** ⇒ 要坐实得抓线程列表或 ETW

## 五、⚠ 我从代码里查实的三条结构性事实（**不是实测，是读代码**）

```
① 引擎**也是"每网格一次 Submit"**（`src/app/engine.cpp:298`）：
      for (const auto& m : d.meshes) gpu.Submit(*m.mesh, m.world, m.tint, m.tex);
   ⇒ ⭐ 所以 `video_render` 的"每模型一次 Submit"**代表引擎的真实行为**（我一度担心量错了路）

② ⚠⚠ **GPU 路径没有网格级视锥剔除**（软渲有）：
      软渲：`engine.cpp:255` `o.cullMeshes = true;  // M5：网格级视锥剔除（性能——可见像素不变）`
      GPU： `GpuRenderer::Options` **没有 cullMeshes 字段** · `gpu_renderer.cpp` 里 `frustum` **零命中**
   ⇒ 软渲剔掉视野外的网格，GPU 路不剔 ⇒ **对"大片视野外模型"的场景会白白付提交开销**
   ⭐ 而软渲那条注释说它"**可见像素不变**" ⇒ **这个剔除是有先例、低风险的**

③ 那个 dll **只导出 C ABI**（`ms_*` 2550 个；`GpuRenderer`/`_ZN12HybridEngine` **0 个**）
   ⇒ ⭐ **链 C++ 必须用静态库**（`build-*/src/*/libhybridengine_*.a`，14 个模块）
   ⇒ 而 `libhybridengine.dll.a` 只能链纯 C 的 `ms_*`（那是对的，符合 `ms_bind.h` 的设计）
```
