## 四、还没排除的（下一轮该从这儿接）

1. ⭐ **`C:\lc_android\app\`（构建区）的缓存污染**
   `build_android.py` 用 `robocopy /E` 同步，**但 `obj` / `bin` 是排除的** ——
   而 `.NET Android` 的**程序集存储是在 `obj/` 里生成的**。
   ⚠ 如果 `obj/` 里残留了**上一次的中间产物**（比如程序集清单和实际 dll 对不上），
   就可能出现"描述符索引越界"这种错。
   ⇒ **下一轮第一件：把 `C:\lc_android` 整个删掉，从零重建一次。**

2. **`<AndroidEnableAssemblyCompression>`**（MSBuild 属性）
   `Invalid compressed assembly descriptor` 里的 "compressed" 指向这个 ——
   它默认是 `true`。可以试 `-p:AndroidEnableAssemblyCompression=false`。

3. **`android/app/obj`**（源工程里的）
   构建区排除了它，但**源工程里那份**可能被 `build_android.py` 的
   "素材新鲜度检查" 之类碰到过。⇒ 删掉它 + 构建区，一起重建。

4. **真机日志的读取姿势**（这轮踩的坑）：
   崩溃日志要 `adb logcat -d -b crash` 读 —— 用默认缓冲读**会被后续日志刷掉**
   （我为此白抓了三轮）。

## 六、⚠ 一个教训（这轮我绕了好几轮）

**"加了实验之后应用崩了" → 我第一反应怀疑产品，第二怀疑实验，
 第三才想到"回退 + 重建"这个最能分辨的做法。**

正确的顺序应当是：

    ① 先 `adb logcat -b crash` 看**原生栈**（不是看应用日志 —— 应用日志一行都没有）
    ② 再**回退到已知能跑的 commit + 重建**：一次就能分辨
       "是我的改动"还是"构建/环境"
    ③ 别在"改一版 → 重建 → 装 → 试"的循环里连试五次

⚠ 我连试了五次（`界面` → 反射版 → 等页面 → 撤销 → 再撤销），
  **每次重建+装机 1~2 分钟**，而这些都建立在"崩溃是我的改动造成的"这个**错误前提**上。
