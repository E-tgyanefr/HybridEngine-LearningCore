# `learncode-ctl` 控制协议（轻量版）

> 协议**逐字相同**的规范在 `HybridEngine/docs/控制协议.md`（第 66/67 轮定案）。
> **本文件只写"轻量版这一侧实现了什么、与专业版怎么对齐、哪些没做"**，
> 不重复那份规范 —— 重复的文档会分叉，而分叉的文档比没有文档更糟。

---

## 一、它是什么

`learncode-ctl` 是 LearnCode 的**控制接口**：**stdio 上跑一行一条 JSON**，
请求 → 响应一一对应，`id` 必回显。

```
→ {"id":1,"cmd":"emu.ping"}
← {"id":1,"ok":true,"r":{"pong":true,"pid":12368}}
→ {"id":2,"cmd":"lesson.show","args":{"id":"ai 01"}}
← {"id":2,"ok":true,"r":{"line":"ai","id":"01","title":"第 01 课：…","requires":"1. 写一个函数…"}}
→ {"id":3,"cmd":"不存在"}
← {"id":3,"ok":false,"err":{"code":-1,"msg":"未知命令: 不存在"}}
```

三条硬约定（与专业版一致）：**不静默**（失败必须 `ok:false` + 非空 `err.msg`）·
**`id` 必回显** · **一行一响应**（调用方可以同步读写，不需要分帧）。

**为什么值得有**（规范 §3.4）：LearnCode 的核心本来就**已经是控制层**
（`run.py` 跑课程、`check.py` 判对错、`exam.py` 出题判分）。套一层协议之后：

- **同一段客户端代码可以驱动两个产品**（`emu.info` 的 `product` 区分）
- 可以**自动投放作业 / 批量批改**，而不必每次写一次性脚本
- 课程是**数据**（`lessons/`、`exams/`），所以"列课 / 看课 / 判分"能被程序驱动

⚠ 关键认识：**本接口没有新增任何教学能力**，它只是把既有 API 的返回值
从 "print 的文字" 变成 "结构化的 JSON"，并补上**会话**（一次进程、多次调用）。
详见第四节。

## 二、怎么启动

三种方式等价（都**不需要**先 `pip install`，也都不弹窗）：

```bash
python -m learncode.ctl              # 最保底：只要有 Python 就能跑
learncode-ctl                        # 项目根下的启动器（自己把根插进 sys.path）
learncode-ctl.cmd                    # Windows 命令行里打 learncode-ctl 用的就是它
```

```bash
learncode-ctl --help                 # 用法
learncode-ctl --version              # 版本 + 协议版本
learncode-ctl --commands             # 只列命令，不进协议循环（给人看的）
```

手工试一条（PowerShell）：

```powershell
'{"id":1,"cmd":"emu.info"}' | python -m learncode.ctl
```

⚠ **响应走 stdout，日志一律 stderr** —— 所以 `2>$null`（丢掉 stderr）
不影响协议。这是规范第四节的约定，也是本产品**踩过之后**刻意保证的（见第五节 ①）。

⚠ **不弹窗**：`learncode/ctl.py` **不 import tkinter**（画布那条线会建窗口）。
`code.run` 是进程内 `exec`，所以它也不会顺带把窗口建起来。
端到端脚本还额外给子进程设了 `LEARNCODE_NO_DISPLAY=1` 作第二道保险。

## 三、命令集（21 条）

⚠ **以 `ctl.commands` 为准**，不要以本表为准 —— 本表会过期，`ctl.commands` 不会。

### 3.1 协议层（与专业版**逐字相同**）

| 命令 | 作用 | 响应要点 |
|---|---|---|
| `emu.ping` | 活着吗 | `{"pong":true,"pid":…}` |
| `emu.info` | 产品自述 | ⚠ `product="learncode"`、`version`、`protocol`、`lines`、`lessons` |
| `ctl.commands` | 自省 | `{"commands":[…],"product":…,"detail":{…}}` |
| `emu.quit` | 结束并退出 | `{"id":N,"ok":true}`（**r 为空，与专业版同形**），随后进程退出 |

### 3.2 课程（对应 `run.py` + `check.py`）

| 命令 | 作用 | 主要参数 |
|---|---|---|
| `lesson.list` | 课程线与课程列表（**真读目录**，带 `answered` 表示答题文件在不在） | `line`（缺省=全部） |
| `lesson.show` | 标题 + 「要做」+ 课程全文 | `id`（`"01"` 或 `"嵌入式 01"`）、`line` |
| `lesson.answer` | 参考答案（读 `*-solutions/`，**不是**学生的 `*-answers/`） | `id`、`line` |
| `lesson.check` | 跑这一课的 `CHECK_*`，给**逐条结构化结果** | `id`、`line` |
| `lesson.run` | **真起子进程**跑你写好的脚本，收回 stdout/stderr/退出码 | `id`、`line`、`path`、`timeout` |

### 3.3 代码

| 命令 | 作用 | 主要参数 |
|---|---|---|
| `code.run` | 跑一段 Python 源码：收 stdout/stderr，报错带**人话翻译** | `source` |
| `code.check` | 按隐藏用例判一段代码（对应 `examrun._grade_code`） | `id`+`answer`，或 `answer`+`expected` |

### 3.4 考试（对应 `exam.py` + `examrun.py` + `cmd_exam.py`）

| 命令 | 作用 | 主要参数 |
|---|---|---|
| `exam.list` | 题库概览：题数、主题、考级元数据 + **题库自检结果** | — |
| `exam.start` | 起一场**考试会话**；`seed` 可复现抽题 | `n`、`topic`、`exam`、`mode`、`seed` |
| `exam.answer` | 答一题并**立即判分** | `session`、`i`/`id`、`answer`、`choice` |
| `exam.answerAll` | 一次交多题 | `session`、`answers` |
| `exam.report` | 当前得分与按主题正确率（不写历史） | `session` |
| `exam.grade` | 出成绩 + **逐题订正**（复用 `examrun.render_report` 的排版） | `session`、`record` |

### 3.5 进度 / 助手

| 命令 | 作用 | 主要参数 |
|---|---|---|
| `progress.get` | 成绩历史与弱项（弱项 = 正确率<70% 且样本≥3） | `limit` |
| `progress.reset` | ⚠ **破坏性**：清空成绩历史，必须显式 `{"yes":true}` | `yes` |
| `coach.hint` | 卡住了？给**下一步动作与追问**，不给答案（`Coach.问我`） | `question`、`lesson` |
| `coach.review` | 读一段代码指出常见坑（不判断对错） | `source`、`lesson` |

⚠ `coach.hint` **故意不给答案**：`coach.py` 自己写明了理由 ——
调试能力的核心是"会把问题拆小、会观察现象"，直接给答案会让学生越来越依赖。

### 3.6 别名（本地化写法，不在 `ctl.commands` 里）

CLI 是中文的（`python -m learncode 嵌入式 检查 01`），所以中文调用方会顺手写
`课程.检查`。协议**接了这些别名**，但 `ctl.commands` **只报规范名** ——
自省表要干净、不能有歧义（同一件事两个名字，客户端就无法用它做主键）。

```
课.列表/课程.列表 → lesson.list      考试.开始 → exam.start
课.看/课程.看     → lesson.show      考试.作答 → exam.answer
课.答案           → lesson.answer    考试.交卷 → exam.grade
课.检查           → lesson.check     考试.成绩 → exam.report
课.运行           → lesson.run       成绩.查看 → progress.get
代码.运行         → code.run         成绩.清空 → progress.reset
代码.检查         → code.check       助手.提示 → coach.hint
题库.列表         → exam.list        助手.看代码 → coach.review
```

### 3.7 参数速查（最容易搞错的一处）

**课程线名**：`python` / `embedded` / `raspi` / `ai`，别名收 `py`、`嵌入式`、`单片机`、
`mcu`、`树莓派`、`rpi`、`人工智能`。**缺省是 `python`**（与 `python -m learncode 01` 一致），
也可以把线名写在 `id` 里：`{"id":"嵌入式 01"}`。

**选择题的答案**：

```json
{"session":"s1-7017","i":0,"answer":3}        ← 0 起下标
{"session":"s1-7017","i":0,"choice":4}        ← 1 起的"人看的序号"
{"session":"s1-7017","i":0,"answer":"import random as rd  →  rd.randint(1, 10)"}   ← 选项原文
```

⚠ 这是**踩出来的**：初版让 `answer` 同时兼容两种起法，靠 `1 <= 值 <= n` 猜 ——
结果 `n=4` 时传 `3` 被判成"第 3 个选项"（下标 2），而调用方说的是"下标 3"。
**中间那一段永远有歧义**，所以现在：`answer` 一律 **0 起下标**，要序号就用 `choice`。
`tools/e2e_ctl.py::test选择题下标的两种写法` 就是这条的回归测试。

### 3.8 错误码

| `err.code` | 含义 | 与专业版的关系 |
|---|---|---|
| `-1` | 未知命令（msg 逐字同形：`未知命令: X`） | **与专业版一致** |
| `-2` | 参数错（命令存在，参数不合法） | 本产品新增 |
| `-3` | 内部错（命令自己崩了；`msg` 带异常类型与位置） | 本产品新增 |

⚠ 专业版协议层只有 `-1`（它把 ABI 错误码留在 `call` 的返回值里）。
这里多分两档的理由：**调用方要能区分"这条命令我不支持"和"我参数写错了"** ——
前者该换实现，后者该改请求。而对**未知命令**这一条，措辞与码都逐字对齐。
"不静默"是硬约定：`-2`/`-3` 同样**必须有非空 `err.msg`**。

## 四、既有能力是怎么被"套"进来的

**本接口不重新实现任何判定逻辑。** 每一层都指向既有模块：

| 协议命令 | 复用的既有实现 | 复用的是哪一部分 |
|---|---|---|
| `lesson.list` | 各线 `_课程们` / `_标题` 的 glob 约定 | 课程发现 |
| `lesson.show` | `run.py::_title_of` 的"第一个注释行当标题" | 标题 + 「要做」段落 |
| `lesson.answer` | `run.py::_cmd_answer` 的目录约定 | `*-solutions/` 单文件 / 多文件 |
| `lesson.check` | `run.py::_load_answer` + `check.run_checks` | ⚠ 见下 |
| `lesson.run` | 直接 `subprocess` 跑**学生那个文件** | "按 F5 的样子" |
| `code.run` | `examrun._grade_code` 的同一思路（进程内 exec） | + `explain.explain` 的人话 |
| `code.check` | `examrun._grade_code` | 隐藏用例判定 |
| `exam.*` | `exam.load_banks` / `normalize` / `Progress` / `examrun.render_report` | 题库、判分、报告排版 |
| `progress.*` | `exam.Progress.topic_stats` / `weak_topics` | 历史与弱项 |
| `coach.*` | `Coach.问我` / `Coach.看代码` | 助手 |

### ⚠ 为什么 `lesson.check` 复用了 `run.py` 的**私有**函数

它调 `run._lessons` / `run._find` / `run._load_answer` / `run._title_of`。
理由：那套逻辑（单文件作业 / **目录形态**作业 / 首次自动生成模板 /
`answers` 与 `solutions` **必须分开**）都是**踩过坑才写成那样的**：

- `lessons/solutions/02_模块化/main.py` 曾经存的是**错的参考答案**，
  被检查抓出来是 8/9（`README.md` 有完整记录）
- 参考答案与学生作业放同一个目录时，"参考答案"读到的会是**学生写错的版本**

抄一份必然分叉。复用它的**必要条件**是：`ctl.py` **不得被 `run.py` 反向 import**
（否则成环）—— 目前没有，且按设计不需要。

→ 代价：本文件依赖 4 个下划线开头的函数。**如果它们改名，本文件会断**。
   端到端脚本的 `lesson.check` 冒烟就是为了让这种断裂**当场可见**，而不是等学生踩到。

### ⚠ 三条新线的行为差别（既有事实，不是新引入的）

| 线 | 答题文件形态 | 首次 `lesson.check` |
|---|---|---|
| `python` | 单文件 `lessons/answers/01_x.py`，**或目录** `lessons/answers/02_x/main.py` | 生成模板，返回 `reason:"未作答"` |
| `embedded` / `raspi` / `ai` | 平铺 `embedded-answers/01_x.py` 等 | 同上（用各线自己的 `_生成模板`） |

⚠ 两条路都**不静默**：`ok:true` + `reason:"未作答"` + `templateCreated:true` ——
"还没写"不该被伪装成"检查失败"。

⚠ `embedded` / `raspi` 的响应里额外带 `disclaimer`：**"检查通过只说明程序逻辑对；
限流电阻、接线、正负极、I2C 地址冲突这些电路问题模拟器发现不了。"**
这句话在既有 CLI 里每条检查后面都有（`embedded.py::_检查`），
协议层**必须原样带上** —— 否则"检查通过"会被读成"插上板子就能亮"，
而那正是这两条线最怕的误读（`README.md` 把它写成诚信底线）。

## 五、与专业版的对齐点

| # | 对齐点 | 轻量版 | 专业版 |
|---|---|---|---|
| ① | **一行一条 JSON**，`id` 必回显 | `learncode/ctl.py::run_stdio` | `tools/ms_ctl/main.cpp::main` |
| ② | **不静默** | `_分派` 里任何异常 → `ok:false` + 非空 msg | `写响应(id,false,…)` |
| ③ | **未知命令**措辞与码 | `未知命令: X`，`code=-1` | 同 |
| ④ | **`emu.info` 的 `product`** | `"learncode"` | `"hybridengine"` |
| ⑤ | `emu.quit` 的**响应体为空** | `{"id":N,"ok":true}` | 同 |
| ⑥ | **stdout 只跑协议，日志进 stderr** | `_协议通道()`：`dup(1)` + `dup2(2,1)` | `_dup(1)` + `freopen`+`_dup2(2,1)` |
| ⑦ | **响应不走缓冲**（调用方阻塞读一行） | `os.write(协议fd,…)` 循环写全部 | `_write(协议fd,…)` |
| ⑧ | **逐字符读 stdin**（不预读） | `流入.read(1)` | `fgetc(stdin)` |
| ⑨ | **`ctl.commands` 由命令表生成** | `COMMANDS` → `命令名列表()` | 手写列表（C++ 侧还没数据驱动） |
| ⑩ | 客户端形状（`Ctl` 类） | `tools/e2e_ctl.py::Ctl` | `tools/msctl.py::Ctl` |
| ⑪ | 空行跳过、坏 JSON 回 `id:0` | 同 | 同（`long long id = 0`） |
| ⑫ | 命令行形状 `--stdio` / `--product=` | 同名（`--commands=` 见第七节） | 同 |

### ⚠ ⑥ 是"吃过亏"才定下的 —— 轻量版的污染源更直白

专业版是被**引擎**坑的：它建窗口时往 stdout 打
`[engine] window2d backend: software` ⇒ 日志混进协议 ⇒ 严格客户端直接
`JSONDecodeError`。修法是 **fd 级重定向**（不是"改每个 printf"，
因为引擎在另一个库里，改不到）。

轻量版这边**同样会踩**，而且更直白：`code.run` / `lesson.check` 都要
**执行学生代码**，而学生代码里就有 `print`。"指望他们不打印"是把协议的
正确性押在学生身上。所以这里用了**同一个做法**（`os.dup(1)` + `os.dup2(2,1)`），
不是"Python 层面换掉 `sys.stdout`" —— 后者盖不住 `os.write(1,…)`、
盖不住子进程继承的 fd 1、也盖不住将来可能加的 C 扩展。

⇒ 对应判据：`Test协议流纯净` —— 跑一段带 `print` 的学生代码，
**紧接着**再发一条 `emu.ping`，`json.loads` 必须还能成功。

**代价（诚实记下来）**：fd 1 被搬走之后，本进程**之后启动的子进程** stdout
也指向 stderr。所以：

- `ctl.py` 自己**不 spawn 子进程**（`code.run` 是**进程内** `exec`）
- `lesson.run` 必须真起子进程（那一课考的就是"你的脚本在命令行里是什么样"），
  所以它在子进程期间用 `_还原fd1()` **临时把 fd 1 还原**成协议通道

### ⑤ 跨产品判据怎么保证（**怎么和"专业版对齐"**）

判据原文："**同一段客户端代码**驱动的两个产品，靠 `emu.info` 的 `product` 区分"。

`tools/e2e_ctl.py` 里的 `Ctl` 类**就是那段客户端代码**：它只认协议
（`id`/`cmd`/`ok`/`r`/`err`），**不认产品** —— 产品身份是运行期从
`emu.info` 读出来的。`Test跨产品.test同一段客户端代码驱动两个产品` 用它
依次驱动两个可执行文件，断言：

1. 两边 `emu.ping` 都 `pong:true`
2. `product` 分别是 `learncode` 与 `hybridengine`，且**不相等**
3. 两边的 `ctl.commands` 都非空、且**命令集不同**（各自做各自的事）
4. **协议层四条命令两个产品都有** —— 这才是"同协议"的定义
5. 未知命令的行为**逐字一致**（同 `code=-1`、同措辞）

⚠ 该测试**只读地找** `HybridEngine/build-ninja-release/tools/ms_ctl.exe`
（**本次没有构建、也没有改 HybridEngine 的任何文件**）。找不到就
`SkipTest` 并在输出里说明"这条判据没跑" —— 而不是假装通过。

**注意本任务只对 LearnCode 侧实现了新命令**：专业版那一侧不需要改
（它的 7 条命令早已落地）。所以跨产品证据是"**协议层 + 客户端**共用"，
不是"命令集共用" —— 命令集按设计**就该不同**（规范第三节的分层）。

## 六、端到端（可重复运行）

```bash
python tools/e2e_ctl.py                  # 14 项，含跨产品
python tools/e2e_ctl.py --no-cross       # 明确不跑跨产品（会报告"跳过"）
python tools/e2e_ctl.py -v               # 详细
```

覆盖的判据：

| 测试 | 判据 |
|---|---|
| `test_ping_info_未知命令_quit` | 起进程 → ping → info → 未知命令（`ok:false` + 非空 msg + `code:-1`）→ quit |
| `test_quit后进程真的退出` | `emu.quit` 之后进程**真的**退出（退出码 0），不是"回了 ok 还赖着" |
| `test_坏请求不静默` | 非 JSON / 数组 / 缺 cmd / `args` 不是对象 —— 四种都要有明确 err |
| `test_空行被跳过` | 空行不当成空请求 |
| `test_commands与实现不分叉` | `ctl.commands` 与 `COMMANDS` **完全一致**（不是手抄的文档） |
| `test_每条命令都能被调用至少一次` | 21 条**逐个冒烟**，失败必须是"参数错"且带 msg（ⓘ `emu.quit` 必须**最后**跑） |
| `test_学生代码的print不会污染协议流` | fd 级通道：学生 `print` 之后协议仍是干净 JSON |
| `test_报错也走协议不含原始print` | `code.run` 的报错带 `explain`（人话翻译）且协议未污染 |
| `test出题作答判分订正` | 出题 → 题面**不含答案** → 全答对 → 100% + 订正段 |
| `test答错必须判错` | ⚠ **判据必须能失败**：故意答错必须判错，且给出"为什么" |

## 七、落地过程中踩到的坑（每条都值得记）

### ① ⚠⚠ 选择题答案的"0 起 / 1 起"歧义（**真的踩了**）

初版让 `answer` 同时兼容两种起法，靠 `1 <= 值 <= n` 猜：

```python
下标 = 选中 - 1 if 1 <= 选中 <= n else 选中      # ← 错的
```

`n=4` 时传 `3`：调用方说"下标 3"，代码算成"第 3 个选项"= 下标 2 ⇒ **判错**，
而两边都觉得自己对。这个 bug 让 `test出题作答判分订正` 第一次跑就红。

**修法**：不猜。`answer` 一律 **0 起下标**；要 1 起序号用 `choice` 字段。
**教训**：**两个约定重叠的区间，永远不要靠值域去猜** ——
要么拆成两个参数，要么把其中一个约定作废。

### ② ⚠⚠ `emu.quit` 在自省表里排第 4 —— 照它的顺序冒烟会把进程关掉

"`ctl.commands` 列出的命令都能被调用"这条判据，最自然的写法是
`for 名 in ctl.commands()["commands"]`。而 `emu.quit` 排第 4 ⇒
第 5 条就报 `进程提前退出（cmd=lesson.list）`，后面 16 条**全部**没测到。

**修法**：**先跑完所有其它命令，`emu.quit` 放最后**。
**教训**：判据的**顺序**也是判据的一部分 —— "遍历一个表"这种写法，
遇到"表里有一条会终止进程"时，会安静地少测一大半。

### ③ ⚠ 题面必须走**白名单**，否则一条 `exam.start` 就把答案发出去了

`Question` 是个 dataclass，`dataclasses.asdict` 或"复制一份再删几个键"
都会把 `answer`（选项下标）、`expect`（标准答案）、`tests`（**隐藏用例闭包**）、
`explain`（为什么）一起送出去。

**做法**：`_题面()` 逐字段挑（白名单），并且测试里断言
题面**不含** `answer`/`expect`/`tests`/`explain`。
**教训**：泄题检查必须是一条**断言**，不能靠"我写的时候记得删了"。

补一条相关决定：**答对了不给 `explain`**。答错才给"为什么"——
否则连考几次就能把整套答案刷出来，"暴露盲点"这个设计目标就废了。

### ④ ⚠ 路径要转义 —— 但这次不用手写

专业版为 `capture.writeBmp` 的 `path` 手写了一遍 `\` 转义
（实测报过 `Invalid \escape: line 1 column 63`）。
轻量版**所有响应都过 `json.dumps`** ⇒ 这一类问题不存在。
**教训**：与其在每个拼字符串的地方记得转义，不如让"拼 JSON"这件事根本不存在。

### ⑤ ⚠ fd 重定向的代价：子进程的 stdout 也被搬走了

第一次实现 `lesson.run` 时，子进程的 `stdout` **永远是空的** ——
因为 fd 1 已经被指向 stderr，子进程继承的是那个。
**修法**：`_还原fd1()` 上下文管理器，只在起子进程的那个窗口里把 fd 1 还原。
**教训**：fd 级重定向能盖住全部来源（这是它的优点），
但它是**进程级**的开关 —— 需要"两条通道并存"时要显式临时还原。

### ⑥ ⚠ 别把 `learncode/ctl.py` 和 `learncode/ctl/__main__.py` 放一起

我先写了 `learncode/ctl/__main__.py`（想支持 `python -m learncode.ctl`），
结果那会把 `learncode.ctl` 变成**包**，与 `learncode/ctl.py` 冲突。
实测确认：Python 3.12 用 `-m` 跑**平铺模块**没问题（runpy 会造
`__main__` spec）—— 所以 `ctl.py` 保持平铺，`__main__.py` 已删除。

### ⑦ ⚠ 空 `r` 要不要写出来

C++ 侧 `emu.quit` 写的是 `{"id":5,"ok":true}` —— **没有 `r`**。
Python 里 `if 体:` 对 `{}` 为假，正好同形。但这条**看起来是细节**的地方
值得写下来：客户端的 `r.get("…")` 在 `r` 缺失时会崩，
所以"有 `r` 但为空"和"没有 `r`"对客户端**不是同一件事** ——
两个产品必须选同一种。这里选了**跟专业版一样**。

## 八、未做的部分（诚实清单）

| 没做的 | 为什么 | 代价 / 什么时候该补 |
|---|---|---|
| **`--commands=<json>` 数据驱动命令表** | 专业版用它做到"加命令=改 JSON"（`action: call:<MS_API>`）。**轻量版的命令是函数**（要判分、要读文件、要管会话），不是"按签名调一个 C ABI" ⇒ 数据驱动的收益拿不到，反而会把命令表与实现**分叉**（而分叉正是 `ctl.commands` 要消灭的东西）。⚠ 开关**保留并给出明确答复**（不假装支持） | 真要让课程/题库**作者**加命令时再补。那时该做的是"插件式命令注册"，不是 JSON 签名表 |
| **`call`（直通任意 API）** | 那是专业版专有：它的能力在 C ABI 里（168 个导出）。轻量版的能力是 Python 函数，`getattr` 直通**没有边界**（能 `os.remove`）⇒ 与"零依赖教学工具"的定位冲突 | 若真需要，应当做成**白名单**直通（只放既有 API 的公开名），并默认关闭 |
| **`code.run` 的超时/中断** | 进程内 `exec`。真要能杀掉一个死循环，得起子进程 —— 而子进程的 fd 1 已被搬走（见第五节 ⑥），得再做一遍通道管理。⚠ **所以 `code.run` 遇到死循环会挂住整个协议会话**（`lesson.run` 有 `timeout`，那条是安全的） | 用 `subprocess` 重做 `code.run` + 复用 `_还原fd1` + `timeout`。**这是最该优先补的一条** |
| **游戏线（`games/`）** | `games/*.py` 是**给学生直接跑**的交互式程序（`猜数字` 要 `input`，`井字棋` 要画布）。协议层跑它们 = 抢焦点 / 建窗口 / 卡在 `input` ⇒ 与后台作业约束直接冲突 | 不值得做。要看游戏，让 `lesson.run` 跑它并设 timeout（已经能用） |
| **`exam.answer` 的 code 题在 stdio 下的可答性** | 协议版**能**考 code 题（作答随请求送进来）——这是协议相对命令行的真实增益。但 `exam.start` 抽到 code 题时，客户端**必须**自己去写那段代码 | 已可用；只是没有"跳过 code 题"的开关。真需要时加 `{"types":["choice","output","fill"]}` |
| **C#/C++/Java 那三条线**（`csharp/` 下） | 它们是 **dotnet 项目**，不是 Python 包。协议循环在 Python 里 ⇒ 要驱动它们只能起子进程（`dotnet run …`），而且每次编译要几秒 | ⚠ 这是**有意的边界**：本接口对齐的是"Python 侧的 LearnCode"。要覆盖那三条线，应当在**那个**侧加同协议的入口（规范 §3 的分层本来就允许各自实现） |
| **协议版本的向后兼容策略** | 现在只有 `protocol:"1"`，还没有"第二个版本"的经验 | 真改协议时再定（现在写就是猜） |
| **`HybridEngine` 侧的改动** | 任务明确要求专业版**只读**。本次**没有改它任何文件**，跨产品测试只**跑**了它已经构建好的 `ms_ctl.exe` | — |
