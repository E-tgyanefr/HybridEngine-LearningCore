# 能效比：**同一口径**的对照结果（2026-10-14）

> ⚠ 这一份是为了纠正一个**口径错误**而写的。
> 前面几轮我报过「tkinter 4.855 ms」，队友报过「C++ 后端 0.1130 ms」——
> **那两个数的分母不同**，直接比就是"两个口径硬凑"（本仓犯过这个错）。
> 下面是**统一到"真实可见 item 数"**之后的数。

---

## 一、⚠ 先说清口径错在哪

| 来源 | 场景 | **真实可见 item** |
|---|---|---|
| 我（10-13） | 1000 个对象按世界坐标铺 | **42 ~ 250**（绝大多数被裁掉） |
| 队友（task-12） | 1000 个圆**铺满视野** | **1000** |

⇒ 分母差 4~24 倍 ⇒ **那个"快 43 倍"是虚的**（队友自己也主动声明了这一点，是他先发现的）。

**正确的分母是「真画了多少个」，不是「世界里有多少个」。**

---

## 二、Tk 后端的成本：**与 item 数严格线性**

复跑：`python _build/_cmp_items.py`（800×450，对象全落在可见区内）

| 可见 item | 中位 ms/帧 | **每个 item** |
|---|---|---|
| 100 | 1.9181 | 19.18 µs |
| 300 | 5.1910 | 17.30 µs |
| **1000** | **16.1817** | **16.18 µs** |

⇒ **16~19 µs/item**，与数量无关（印证前面"每个图元固定成本"的结论）。

⭐ **这解释了 60 帧预算为什么卡在那**：

    16.67 ms（60 帧预算） ÷ 16.18 µs/item ≈ **1030 个 item**
    ⇒ **tkinter 大约只能画 1000 个图元就满帧**，再多就掉帧。

---

## 三、C++ 后端（队友 `task-12`）

同一个"铺满视野"的 1000 个圆（他自己量的，**我独立复跑过，校验和逐位相同**）：

| | ms/帧 |
|---|---|
| 纯光栅化 | **0.1107**（我复跑）· 0.1086~0.1130（他多次跑） |
| 含 Win32 上屏 | 0.2317 |

⇒ 每个 item 约 **0.11 µs**。

---

## 四、⇒ 同一口径下的结论

```
每个可见 item：
    Tk 后端    16.18 µs
    C++ 后端    0.11 µs
    ⇒ 约 **146 倍**
```

⚠ **但这仍然是"两个不同代码画的"** —— 两个后端的场景定义、圆的半径/位置、
  甚至"画圆"这个操作本身的实现都不同。
⚠ 所以这个 146 倍**只能当量级参考**，不是"逐像素同画面"的严格对照。
  ⇒ **严格对照要等 C++ 后端真的接进 `pyengine` 的后端接口之后**，
    用**同一份场景定义**跑两条后端 —— **那一步没做。**

---

## 五、但有一条结论**不依赖那个比值**，而且它足够下判断

```
tkinter 的 60 帧上限   ≈ 1000 个可见图元
C++ 后端的 60 帧上限   ≈ 220,000 个可见图元（按 0.11 µs/item 反推）
```

⇒ 作者要的"**能效比提高一倍**" = **60 帧下能画的图元数翻倍** = 2000 个。
  ⇒ C++ 后端**远远超过**这个目标（余量约 200 倍）。

⚠ 而**前提是它真的接进去** —— 现在它还是一个**独立的 benchmark 程序 + 自己的窗口**，
  没接进 `pyengine.后端` 接口，所以**学习内核还用不上它**。
  ⇒ 这是下一步的事，而且它是**架构决定**（新窗口怎么和现有 tkinter GUI 共存）。

---

## 六、诚实结论

| 问题 | 答案 |
|---|---|
| 「能效比翻一倍」有了可行路径吗 | ✅ **有**，而且余量很大（C++ 后端 ~146x） |
| 做到了吗 | ❌ **还没** —— 它没接进引擎，学习内核还用不上 |
| 前端那些小优化（换图元/复用 item） | ❌ 已量死，都是小钱 |
| 下一步 | ① 把 C++ 后端接进 `pyengine.后端` 接口 ② 定"新窗口怎么和 tkinter GUI 共存" |

⚠ **而且步骤 ② 是架构决定，不是技术问题** —— 它决定学习内核长什么样。
