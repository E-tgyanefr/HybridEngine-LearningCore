# ⚠ 作者裁决：**轻量版不得委托专业版渲染**（2026-10-14）

> 我问的是：「轻量版把渲染委托给专业版」算不算违反
> 「**两个不同的程序，完全不共用，各写一份**」？
>
> **作者裁决：算违反。**
>
> ⇒ 这一份记下**这个裁决推翻了什么**、**还剩下哪条路**、**以及那条路上已知的硬墙**。

---

## 一、被否掉的方案：`引擎后端`

`render.py:11` 里预留了：

```
· `引擎后端` —— 有 `hybridengine.dll` 时改用它（**留接口**，见 `可用引擎后端`）
```

而 `可用引擎后端()` **只有探测、没有实现** —— 它一直是"用专业版 C++ 光栅化器"的入口。

**实测它能带来的收益**（同场景）：

| | 1000 对象 |
|---|---|
| 专业版 | **1.237 ms/帧** |
| 轻量版 | 4.855 ms/帧 |

⇒ 快约 3.9x，**远超那"一倍"**。

⚠ **但它现在被裁决否掉了** ⇒ **这条路关闭。**

---

## 二、剩下唯一的路：轻量版**自己**的 C++ 光栅化器

    轻量版自己的 libhblight（已有）
        + 自己的光栅化器（要新写，C++ 标准库 / 直写像素）
        + 自己的窗口/呈现路径（要新写）

⚠ **不共用专业版任何东西** ⇒ 两条都得自己写。
⚠ 这**不违反裁决**，也**符合"所有引擎都是 C++ 构建的"**。

---

## 三、⚠⚠ 但这条路上有一堵**我已经量死的墙**

光栅化出来的像素**怎么上屏**？在轻量版当前的技术栈上是 tkinter，而：

```
Tk 版本                                 8.6.15
PhotoImage 有 frombuffer                **False**      ← 要 Tk 8.7+
每帧 put() 整帧（800×450，十六进制）      **64.306 ms**  ← 慢 15 倍
一帧 = delete + create_image + update     0.219 ms
每个图元（create_oval）                   14.54 µs
```

⇒ **`PhotoImage.put()` 要 Tcl 逐字符解析 288 万个字符 ⇒ 64 ms/帧。**
  ⇒ **"C++ 光栅化 → 整帧贴进 tkinter"这条路在 Tk 8.6 上不成立。**
  ⇒ 而 `frombuffer`（快路径）**Tk 8.7+ 才有**，本仓铁律是**零第三方依赖** ⇒ 不能为它换 Python/Tk。

**⇒ 所以"轻量版自己的 C++ 渲染"必须连带解决"自己开窗"** ——
  那是 Win32 / Cocoa / X11 三套，**又是一个大工程**，而且**跨平台成本很高**。

---

## 四、⇒ 那"能效比翻一倍"还剩哪条路

| 路线 | 能不能做到一倍 | 代价 |
|---|---|---|
| 裁剪 | 真实大世界 **3.2x**（已做）· 但**基准场景里无可裁** | 已付 |
| 换图元 / 复用 item / 少删少建 | ❌ 小钱（最多 30%） | 已量死 |
| **委托专业版渲染** | ~3.9x | ❌ **作者否掉** |
| **自己写 C++ 光栅化 + 自己开窗** | 理论能到 | ⚠ 三平台窗口层，**大工程**，且**仍需证明** Tk 之外能否嵌进现有 GUI |
| 数值逻辑搬 C++ | ❌ **实测慢 4.5 倍**（+351%） | 已量死 |

⇒ **诚实结论：在"不共用 + 零第三方 + 保留 tkinter GUI"这三条同时成立时，
  「能效比翻一倍」我目前没有一条已证可行的路。**

⚠ 而这不是"做不到"，是**"需要作者在三条约束里松一条"**：

    甲）允许轻量版有自己的窗口（不再嵌 tkinter）⇒ 自己写 C++ 渲染，可行
    乙）允许用 Tk 8.7+（`frombuffer`）⇒ 光栅化 + blit 可行
        ⚠ 但本仓是**便携 Python**（PyInstaller / Chaquopy），换 Tk 版本影响面很大
    丙）把"一倍"的目标改成**实测能到的数**（比如裁剪那 3.2x，
        或"大世界场景下翻倍"这个更准的表述）

---

## 五、⚠ 这件事的元教训

**我在量死 blit 之前，一直把"能效比翻一倍"当成一个"还没优化够"的问题。**
量完之后才看清：它其实是**一个架构约束的冲突**，不是优化空间的问题。

⇒ **"先量再定目标"** —— 如果我先量到 64 ms/帧，就不会把"翻一倍"当成待办那么久。
⚠ 而我**确实先量了渲染占 90%**，但**没接着量"那条出路通不通"**，
  于是又在"换图元/复用 item"这些小钱上花了两轮。
**⇒ 教训：找到瓶颈之后，下一步该量的是"最粗的那条出路通不通"，而不是次优的那几条。**
