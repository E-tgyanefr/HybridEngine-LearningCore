# C++ 移植：**"搬到 C++"和"更快"是两件事** —— 实测 +351%

> 这一份记一条**用真金白银量出来**的结论，免得后人再走一遍。
> 对象：`hybridengine_light/pyengine`（轻量引擎本体）→ `libhblight`（C++ 内核）。

---

## 一、实测（1000 对象 · 300 帧 · 录制后端）

| 配置 | ms/帧 | item 数 | 对象数 | 全 C++? |
|---|---|---|---|---|
| ① Python 版 | **0.7335** | 1001 | 1000 | False |
| ② 第 1 层 C++（`向量` + `变换`） | **2.9047** | 1001 | 1000 | False |
| ③ 第 2 层 C++（再加 `相机2D`） | **3.3097** | 1001 | 1000 | **True** |

```
①→②  **+296.0%**
②→③  **+ 13.9%**
①→③  **+351.2%**       ⇒ 慢了 4.5 倍
```

⭐ **三组的 `item` 数都是 1001**（1000 个圆 + 1 条清屏）
⇒ 三组**做的工作完全一样**，这个对比是**公平的**。
⚠ 而这也说明：那个 1001 **不能**当渲染工作量的代表 ——
  换 `Tk后端` 会因为 `允许裁剪=True` 少得多。

复跑：`python native/hblight/tests/paths_and_cost.py`

---

## 二、为什么慢

`向量` 的**每个运算符**、`变换.位置` 的**每次 getter/setter** 都是**一次 ctypes 调用**。

```
1000 对象 × 300 帧 × (每个组件每帧要 getter + setter + 若干算术)
    ⇒ **几百万次**跨语言往返
而 ctypes 一次往返约 **0.5~1 µs**
    ⇒ 正好就是那 2.2 ms
```

⇒ **不是"没赚到"，是"亏了 3 倍"。** ⚠ 错的是**接口粒度**，不是方向。

---

## 三、这条结论和另一条实测**互相印证**

我在别处量过（同样 1000 对象）：

```
录制后端（纯逻辑 + 记账）   0.469 ms/帧
Tk后端（真画到 tkinter）    4.855 ms/帧     ⇒ **绘制占 90.3%**
组件更新 0.2679 · 相机 0.0000 · 绘制(记账) 0.4333 ms
```

⇒ **数值内核只占总时间的 ~10%。**
  ⇒ 就算把它搬到 C++ **且零成本**，上限也只有 10%；
  ⇒ 而实测**跨语言往返的成本远超那 10%** ⇒ **净亏**。

**两条独立测量指向同一个结论。** 这类"互相印证"比单条数可信得多。

## 四、⇒ 三条由此定下的规矩

### 4.1 `pyengine_c` **默认关**（`HBLIGHT_ENABLE=1` 才启用）

⚠ 不是保守，是**必须** —— 否则**产品默认慢 4.5 倍**。

⚠ 而"默认关"**本身也是产品行为**（手机版 Chaquopy 装不到 `.so`，靠的就是"不在就退回"）
  ⇒ 所以 CI 里有一条**反面判据**钉住它：
  「**默认必须退回 Python，而且不许崩**」。

### 4.2 "内核在" **不等于** "内核在用"

```
默认      可用=True  但 向量.__module__ = pyengine.scene   ← 走 Python
ENABLE=1  可用=True      向量.__module__ = pyengine_c       ← 走 C++
```

⚠ ⇒ **想验 C++ 路，必须「显式开 + 断言真的走了」两步**，
  不能靠 `可用()`，更不能靠"测试通过了"推断。
  （这条是被一次**假绿**逼出来的：dll 依赖 `libstdc++-6.dll` 加载失败
    ⇒ 按设计静默退回 ⇒ `test_pyengine` 全绿，**但绿的是 Python 版**。）

### 4.3 真要快，得换**粒度**，不是"逐层搬"

```
现在：每个 向量 运算 / 每次 getter ⇒ 一次调用        ⇒ 几百万次往返
该做：一次调用干完**整个场景的一帧**                  ⇒ 往返次数降 5~6 个数量级
      （C++ 侧持有场景/对象的真状态，Python 只发一条 hb_scene_step(scene, dt)）
```

⚠ 那是**另一个 ABI 设计**，**不是"逐层搬"能到的**。
⚠ 而且**优先级低于渲染** —— 详见下条。

## 五、⚠ 真正该去的地方：渲染那 90%

| 路线 | 状态 |
|---|---|
| 裁剪（少画） | ✅ 已做，真实大世界 **3.2x** |
| 换图元 / 复用 item / 少删少建 | ❌ 实测都是小钱（方块省 30%，线更慢，复用省 10%） |
| **C++ 光栅化 + 整帧 blit 进 tkinter** | ❌ **量死了**：`PhotoImage.put()` **64.3 ms/帧**（比老实画 300 个图元慢 15 倍），快路径 `frombuffer` 要 **Tk 8.7+**（本机 8.6.15，零依赖装不了） |
| **`引擎后端`**（`render.py:11` 预留的接口） | ⚠ **只有探测函数，没有实现** —— 而它是那"一倍"唯一的路 |

⚠ 而 `引擎后端` 要不要做，**卡在作者的一句裁决**：
  「轻量版把渲染委托给专业版」算不算违反「**两个不同的程序，完全不共用，各写一份**」？

---

## 六、诚实结论

| 问题 | 答案 |
|---|---|
| 能效比**翻一倍**做到了吗 | ❌ **没有** |
| C++ 移植让它更快了吗 | ❌ **反而慢 4.5 倍**（+351%）—— **但那是粒度问题，不是方向问题** |
| 那移植白做了吗 | **没有**。它兑现的是**规格**（作者要求引擎是 C++）+ **零第三方依赖**，而且**逐位对账 75/75 相同**，等于给 C++ 版发了一张"和 Python 版算的是同一件事"的证书 |
| 下一步该做什么 | ① 作者的架构裁决（渲染委托）→ ② 若同意，"整帧粒度"的 C++ 渲染才是那"一倍"的来处 |
