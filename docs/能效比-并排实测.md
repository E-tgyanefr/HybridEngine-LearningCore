# ⭐ 能效比总判据：**同一份场景并排对照**（2026-10-14 · Round 25）

> 作者的目标：「在原来的性能基础上**提高能效比**，**尽量提升到原先的一倍**」。
>
> ⚠ 而在这之前，**两个后端从来没有用同一份场景并排量过** ——
> 我报过 `tkinter 4.855 ms`（分母：1000 个对象里 **250 个可见**），
> 队友报过 `0.11 ms`（分母：**1000 个全可见**）⇒ **两个数不能比**（我为此纠过一次口径）。
>
> 这一份是**并排**的数。复跑：`python _build/_cmp_two_backends.py`

---

## 一、⭐ 结果

同一份场景：**1000 个圆铺满视野** · 画布 800×450 · `size=100` ·
两边**裁剪规则相同**（都照 `render.py::Tk后端._在视野内` 的 `MARGIN×(宽/size)`，`MARGIN=10.0`）

| | ms/帧 | 真实画了多少 |
|---|---|---|
| **① Tk 后端** | **15.4701** | 画布 item = **1000** |
| **② C++ 后端** | **1.9993** | 写过的像素 = 52,677,216 · 呈现 81 帧 |
| **⇒ 倍数** | **7.7 倍** | |

**60 帧预算（16.67 ms）下能画的图元数**：

```
Tk   ≈ **1,078 个**      ← 刚好卡在 60 帧线上（这也解释了"为什么卡在这"）
C++  ≈ **8,338 个**
```

⇒ ⭐ **作者的"翻一倍" = 2000 个 ⇒ 实际 7.7 倍，远超目标。**

⚠ **但必须同时说清下面这条。**

---

## 二、⚠⚠ 7.7 倍**不是**这条路的极限 —— 它被"接口粒度"卡住了

```
C++ 后端纯光栅化（队友 benchmark，1000 圆铺满）    **0.1107 ms**
C++ 后端接进引擎后的实测（本份）                  **1.9993 ms**
⇒ 多出来的 **1.89 ms（94.5%）是 Python→C++ 的逐图元 ctypes 开销**
```

⇒ **同一份场景、同一个光栅化器，只因为"每个图元过一次语言边界"，慢了 18 倍。**
⚠ 而这**正是队友在 `task-10` 量到的那个结论**（它当时量出逐操作 ctypes **+351%**）——
  **现在是同一个病，换了个地方发作**：

| | 当时（数值逻辑搬 C++） | 现在（渲染搬 C++） |
|---|---|---|
| 往返次数 | 几百万次 | 1000 图元/帧 × 60 帧 × … |
| 结果 | **+351%（净亏）** | **仍然净赚 7.7 倍**（因为省掉的 Tk item 重建更多） |

⇒ 差别在于：**Tk 那边每个图元的原生代价（~15.5 µs）本身就比 ctypes 往返（~1.9 µs）贵 8 倍**，
  所以即使交了过路费，还是赚。⚠ **但赚的没有本可以赚的多。**

### ⚠ 真上限在哪（**推算，不是实测**）

```
如果图元提交也能"一次调用干完一帧"：
    1000 个圆 ≈ 0.11 ms（光栅化） + 极少量提交开销
    ⇒ 对 Tk 的 15.47 ms ⇒ 理论 **~140 倍**
⇒ 而现在只有 **7.7 倍** ⇒ **94% 的潜力被接口粒度吃掉了**
```
⚠ **这个 140 倍是推算，不是实测** —— 要做实需要改 ABI（C++ 侧持有整个场景）。
⇒ **那是另一个设计，本轮没做。**

## 四、⚠ 一个**没解决**的现象（如实记）

```
b.子窗口可见()  →  **False**
```
- 队友的探针报过 `CHILD_VISIBLE=1`
- 本份里父子窗**没 `withdraw`** 时也报 `False`
- ⚠ 但 **`写过的像素 = 365,023`** ⇒ **像素确实写了**；而"上屏"走的是
  `StretchDIBits` 直写 DC，**和"可见性"不是一回事**

⇒ **我没有深挖这一条**（时间用在了拿那个倍数上）。
  ⚠ **但它是个明确的待办**：`子窗口可见()` 这个 API 的语义**要查清**
  （是它判错了？还是"窗口被遮挡/未激活"时它就该是 False？）
  ⇒ ⚠ 而**一条会误报的可见性判据，比没有更糟**（会让人去查错的地方）。
