# HybridEngine-light —— 学编程，从第一行代码看到画面

**本项目由 AI 协作完成** —— 人类定方向与验收，AI 负责实现、测试与文档。详见文末[「关于这个项目是怎么做出来的」](#关于这个项目是怎么做出来的)。

一个**零依赖**的编程教学项目。教 **Python / C# / C++ / Java / C** 五门语言。

```python
from hybridengine_light import Stage
Stage().dot(50, 50, r=20, color="红").wait()
```

---

## 为什么做这个

市面上的入门教程有个共同毛病：**前几课屏幕上什么都没有**。
新手坚持不下去，往往不是因为难，而是因为**没有反馈**。

这个项目只解决三件事：

| 设计决定 | 为什么 |
|---|---|
| **零依赖** | 学编程最不该卡在装环境上。装完就能跑，不用编译、不用配 PATH。 |
| **报错说人话** | 见下，这是整个项目最花心思的地方。 |
| **检查自动化** | 学生写完代码立刻知道对不对，不用等人批改。 |

## 真正的主角：报错翻译

新手放弃的时刻，通常不是"写不出来"，而是**报错看不懂**。

```
TypeError: unsupported operand type(s) for +: 'int' and 'str'
```

它说的是"你拿数字去加了文字"——但这句英文里没有一个词是新手认识的。

四条刻意遵守的约束：

1. **不猜测意图去自动改代码** —— 那样新手学不到东西，而且会改错
2. **不吞掉原始报错** —— 原文始终附在末尾（老师和搜索要用）
3. **认不出来就承认** —— 明说"我的规则表里没有它"，给通用排查办法，**而不是编一段像模像样的解释**
4. **每条解释四段式**：发生了什么 → 出在哪一行 → 怎么改 → 顺便记住

最后一段是它区别于搜索引擎的地方：查一次报错应该**学到一点东西**，
而不是只把这一个坑填上。

## 五门语言，各自的坑不一样

报错翻译**不能照搬规则表** —— 每门语言让新手卡住的地方完全不同：

| | Python | C# | C++ | Java |
|---|---|---|---|---|
| 运行方式 | 解释 | 编译（dotnet） | **编译（要装 g++）** | **编译（要装 JDK）** |
| 识别依据 | 异常类型 + 消息 | 异常类型 + `CSxxxx` | **错误消息 + 退出码** | 异常类型 + `error:` |
| 头号杀手 | `NameError` | `NullReferenceException` | **报错行不是真凶行** | `NullPointerException` |
| 内存 | 自动 | 自动 | **全交给你** | 自动（有 GC，检查下标） |

### 几条最值得看的语言特有规则

**C++：报错行往往是错的。**

```
第 3 行： int x = 5           ← 这里漏了分号
第 4 行： error: expected ',' or ';' before 'std'
```

新手会盯着第 4 行改半天。翻译器直接指出「真凶在第 3 行」。

**C++：数组越界不一定崩。** 实测：

```
int a[3] = {1,2,3};
std::cout << a[10];    // 正常退出，输出 32758（别人变量的内存）
```

不报错、不崩溃、结果悄无声息地错了。这是 C++ 里最难查的一类 bug。

**C++：未初始化的变量会「碰巧算对」。** 实测中学生写 `int s;` 然后累加，
程序真的跑出了正确答案（那块内存碰巧是 0）。
**判它通过等于奖励一个真实的 bug**，所以 `-Wall` 的警告被当成必须修正的问题。

## 七条课程线（41 课，全部逐课验收通过）

一个入口看全部：`python -m hybridengine_light`

| 课程线 | 命令 | 课数 | 说明 |
|---|---|---|---|
| **Python** | `python -m hybridengine_light` | 2 | 变量、模块化 |
| **C++** | `dotnet run --project csharp/cpp-lessons` | 8 | 输出 → 指针与引用 |
| **Java** | `dotnet run --project csharp/java-lessons` | 8 | 输出 → 类与对象 |
| **嵌入式/单片机** | `python -m hybridengine_light 嵌入式` | 5 | 模拟器：按钮、闪烁、状态机、防抖 |
| **树莓派** | `python -m hybridengine_light 树莓派` | 5 | 模拟器：传感器、数据记录、温室监测器 |
| **人工智能** | `python -m hybridengine_light AI` | 5 | 零依赖：线性回归、感知机、梯度下降、KNN |

每条线都是同一个循环：**看课程 → 写答案 → 自动检查 → 拿到具体反馈**。

### 三套模拟器 / 三种验证方式

| 语言/平台 | 怎么验证学生的代码 |
|---|---|
| Python / C# / C++ / Java | **真编译真运行**，比对输出 |
| 嵌入式 / 树莓派 | **模拟器**：跑代码，观察引脚/传感器/文件的状态 |
| 人工智能 | 真运行，检查算法结果（换数据必须跟着变） |

⚠ **模拟器保证程序逻辑，保证不了电路。** 限流电阻、LED 正负极、接线位置、
I2C 地址冲突 —— 这些模拟器一个都发现不了。所以每条检查结果后面都会提醒一句。
最坏的情况是"检查通过、插上板子不亮"，学生会去怀疑自己的代码。

## 课程系统怎么设计的

每一课是**一个可以单独阅读的文件**，装三样东西：

```
# 第 01 课：变量 —— 给东西起个名字        ← 标题
# 要做：                                  ← 要求
def CHECK_xxx(答案): ...                  ← 检查（任意多条）
```

检查函数返回 `(是否通过, 说明)`。说明必须**具体**——
不能只说"错了"，要说"期望什么、你写的是什么、怎么改"。

C++ / Java 课程换了个形式（因为要编译），但形状一样：

```csharp
[课程("01", "第 01 课：输出 —— 让程序开口说话", "要做：...")]
public static class 第01课
{
    [检查说明("变量是不是真的参与了计算（不是把答案写死）")]
    public static CheckResult 检查_变量真的在用(string 代码) { ... }
}
```

### 课程的"核心检查点"

每一课都必须有一条检查，防住**"能输出对但没学到东西"**的偷懒解法：

| 课 | 偷懒解法 | 怎么防住 |
|---|---|---|
| Python 01 变量 | 把名字写死在句子里 | 换掉变量，看输出会不会跟着变 |
| Python 02 模块化 | 把模块里的算法抄一份到 main | 换掉模块里的函数，看输出会不会跟着变 |
| C++ 01 变量 | `cout << 13;` 写死答案 | 改掉变量初值，重编译，看输出会不会跟着变 |

**共同手法**：不检查"看起来对不对"，而是**改掉依赖的东西，看结果会不会跟着变**。
真用了 → 会变；写死的 → 不变。

## 嵌入式 / 单片机（模拟器，不需要真板子）

```bash
python -m hybridengine_light 嵌入式              # 列出课程
python -m hybridengine_light 嵌入式 01           # 看第 1 课
python -m hybridengine_light 嵌入式 检查 01      # 检查答案
```

```python
from hybridengine_light.mcu import 模拟器

板 = 模拟器(引脚数=8)
led = 板.输出引脚(2, 名字="LED")
按钮 = 板.输入引脚(3, 名字="按钮", 上下拉="上拉")

led.高()                 # 点亮
板.按下(按钮)
板.读到(按钮)            # True
板.时间推进(0.5)         # 让模拟的时间往前走
板.报告()                # 看这一轮都发生了什么
```

### ⚠ 模拟器保证什么、保证不了什么

| ✅ 能保证 | ❌ 保证不了 |
|---|---|
| **程序逻辑**：引脚编号、状态机、时序、边界 | **电路**：限流电阻、LED 正负极、接线位置、电压 |

**这个边界写在每一课的说明里，不是藏起来。** 因为最坏的情况是
"代码检查通过了，插上板子不亮" —— 学生会去怀疑自己写的代码，
而真正的原因是忘了串限流电阻。

所以模拟器在每个检查结果后面都提醒一句「这只验证了逻辑」。

### 三条刻意的设计决定

**① 引脚号写错要报错。** 真实硬件上写错引脚号**不会报错** —— 板子只是毫无反应。
模拟器报错是为了帮学生养成"先确认引脚号"的习惯。

**② 按下 = 读到 True（教学语义，不是电压语义）。**
真实电路里上拉的按钮按下时引脚是**低**电平。但那个反转对学编程毫无帮助：
学生按下按钮却读到 False，只会怀疑自己写错了代码。
（我第一版就是照搬电压语义，结果"没按"和"按下"都返回 False。）

**③ 两个反向输出接一起要报短路。** 真实硬件上这会烧引脚。模拟器报错是在替学生省钱。

## 树莓派（模拟器，不需要真板子）

```bash
python -m hybridengine_light 树莓派              # 列出课程
python -m hybridengine_light 树莓派 检查 01      # 检查答案
```

```python
from hybridengine_light.raspi import 树莓派, GPIO

派 = 树莓派()
led = 派.接LED(17)                 # 配好引脚并拿到一个顺手的小对象
led.亮(); led.灭(); led.翻转()

派.GPIO.设模式(2, GPIO.输入)        # 按钮
派.按下(2); 派.GPIO.读(2)          # True

派.加传感器("温度", "°C", (0, 50), 25.0)
派.温度.读()                       # 25.0
派.温度.设为(38.5)                 # 模拟"环境变了"

派.写文件("/home/pi/数据.csv", "25.0\n")   # 记录数据（追加，不覆盖）
派.报告()                          # 看这一轮发生了什么
```

### 树莓派和单片机最大的差别

| | 单片机 | 树莓派 |
|---|---|---|
| 程序形态 | `loop()` **永远在转** | 一个**普通进程**，有开始有结束 |
| 操作系统 | 没有，你的代码就是全部 | 完整的 Linux |
| 想一直监测 | 写在 loop 里 | 自己写 `while True` 或做成定时任务 |

**由此引出一个学生最容易搞错的点**：
**程序结束不会自动复位引脚。** 真实板子上，程序退出后引脚保持最后状态 ——
不显式关掉，LED 就一直亮着。

所以「闪一下」这种函数必须**自己**把灯关掉。这是第 01 课的核心检查点，
也有专门的测试保护它（`tests/test_raspi.py`）。

（模拟器和单片机那条线一样，**管不了电路**：限流电阻、接线、I2C 地址冲突都发现不了。）

## 人工智能入门（纯 Python，零依赖）

用**标准库**从零实现算法 —— 不装 numpy / torch / sklearn。

这看起来是限制，但对**教 AI 原理**反而是优势：
用 `sklearn.fit()` 一行搞定，学生学不到任何东西；
自己写出最小二乘和梯度下降，才知道"学习"到底在干什么。

## 怎么验收这个项目（可重复）

```bash
python tests/验收.py        # 逐课跑一遍，报告真实通过率
```

这个脚本做了一件容易被忽略的事：**它自己准备输入** ——
先把 `*-solutions/` 里的参考答案复制进 `*-answers/`，再逐课跑检查。

为什么强调这一点：我手工验收时反复搞错 ——
用反面测试的坏答案覆写了答题文件，之后看到"未过 N 课"就以为课程有问题。
**验收脚本必须自己准备输入，不能依赖"上一步留下的状态"。**

（而且它第一次写的时候也有 bug：只覆盖同名文件，而不是先清空 ——
 于是"我以为准备好了输入，其实测的还是坏答案"。已修。）

### 已知的一处历史问题（已修，值得记）

`lessons/solutions/02_模块化/main.py` 曾经存的是**错的参考答案** ——
我把"只模块化一半"的版本（面积走模块、周长手算）归档成了标准答案。

## 开发约定

- **零第三方依赖**（连测试框架都用自带的）
- 注释用中文，**解释"为什么"而不是"是什么"**；踩过的坑必须写进注释
- 并行写课时：**一人一个文件，不碰别人正在写的文件**（`csharp/cpp-lessons/课程作者契约.md` 有完整规范）
- 课程文件可以被自动发现（靠特性 + 反射），所以**加一课不需要改任何中心文件**

## 关于这个项目是怎么做出来的

**本项目由 AI 协作完成**：人类定方向与验收，AI 负责实现、测试与文档。

具体分工（如实写，不夸大也不含糊）：

| 谁 | 做什么 |
|---|---|
| **人类** | 定目标与优先级 · 划边界（"零第三方依赖"是硬约束）· 定验收标准 · 决定发布与否 · 对结果说"行"或"不行" |
| **AI** | 读代码与实测现象来定位问题 · 写课程与实现 · 写检查逻辑 · 跑全部验收 · 做"改坏验证"（故意把例子改错，确认检查真的会红）· 记录踩过的坑 |

### 怎么保证"AI 写的"是可信的

这个项目**不靠"看起来对"**，靠三道可复查的关口：

1. **检查要能失败** —— 每课的验收都配一次"改坏实验"：故意把示例代码改错，
   确认验收**真的报错**，再还原。改不红的检查等于没有检查。
   （上文「怎么验收这个项目」一节里有实例：一条只验面积的检查漏掉了真错误。）
2. **换数据必须跟着变** —— 每课的检查都换一组数据再跑一遍。
   如果结果不变，说明检查是写死的、没真的在算。
   （这一条写在上文的验收表里，是有意设计的。）
3. **全部验收可重复** —— 一条命令跑完六条课程线，
   结果原样写进交付说明，**包括没通过的**。

### 也如实说明局限

- AI 会在**没有实测**的地方写出听起来很确定的结论。
  （本项目就发生过：注释里声称某处已经做了某件事，而实际没做 —— 后来靠实测抓出来并修正。）
  ⇒ 规矩是：**结论必须有运行输出支撑**，而不是"读起来合理"。
